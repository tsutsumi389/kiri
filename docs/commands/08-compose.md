# kiri compose

> [README](../../README.md) › [コマンド別ドキュメント](README.md) › kiri compose

**切り抜いた素材と文字を 1 枚へ組む。** EC の商品ページには商品そのもののほかに、
寸法や使い方を文字で説明する画像が並ぶ。note の見出し画像も同じ形をしている。

**組版器ではなく合成器である。** どこに何を置くかは spec が決め、kiri は置いて、
**測って、言う**。

```
$ kiri compose layout.json -o thumb.jpg
$ kiri compose layout.json -o thumb.jpg --dry-run --json   # 画素を書かずに幾何だけ
```

```json
{
  "canvas": { "width": 1280, "height": 670, "background": "#f5f2ec" },
  "font": { "family": "Noto Sans JP", "path": "fonts/NotoSansJP.ttf" },
  "safe_area": [0, 108, 1280, 454],
  "layers": [
    { "id": "subject", "type": "image", "role": "subject",
      "source": "out/product.png", "rect": [700, 85, 500, 500], "fit": "contain" },
    { "id": "heading", "type": "text", "role": "heading",
      "lines": ["素材を組み合わせる", "それだけをやる"],
      "rect": [80, 150, 560, 200],
      "size": 64, "weight": 700, "color": "#1f2328", "line_height": 1.3 }
  ]
}
```

素材とフォントのパスは **spec からの相対**で解く。spec の形は
`kiri schema --json` の `compose_spec[]` が配るので、**README を読ませる代わりに
それを引けばよい。**

## 書いた枠と、実際に置かれた矩形は違う

`rect` は枠である。画像はそこへ内接して縮むので、**枠を書いた側は仕上がりの寸法を
知らない**——素材の縦横比を知らないからである。`layers[].placed` が実際に置かれた
矩形を返す。

```
$ kiri compose layout.json -o thumb.png --dry-run --json | jq '.layers[] | {id, rect, placed}'
{ "id": "subject", "rect": [700, 85, 500, 500], "placed": [825, 85, 250, 500] }
```

## 透過の余白は切り詰めてから当てはめる（`trim`）

**`kiri cutout` の出力は、商品の外が透過の余白である。** `--canvas` は余白を
意図して足し、`--rotate` は回した四隅のぶんだけ余白を広げる。-91 度で回した
5788 x 4386 の出力では、商品は横幅の 24% しか占めない。これを余白ごと `contain`
で `[860, 40, 380, 590]` へ入れると、**商品は横 85px ほどの豆粒になる。**

画像の層は既定で、**不透明度が 0 でない画素の外接矩形で素材を切り詰めてから**
`fit` する。捨てるのは完全に透明な画素だけなので、`contain` では見た目は 1 画素も
消えない。不透明な写真（背景の層）では何も起きない。**`cover` と `exact` では
効き方が変わる**——`cover` で枠からはみ出して切り落とされるのは余白ではなく商品に
なり、`exact` が引き伸ばすのは素材のキャンバスではなく商品になる。

しきい値は不透明度 0 で、半透明の影や縁は残る。`cutout` は背景の不透明度を 0 へ
落とし切るので、遠くに薄い画素が残って矩形が素材いっぱいに広がることはない
（-91 度で回したリモコンと `--canvas 1400` の出力の 2 つで、矩形が商品に乗ることを
確かめた）。他のツールが作った素材で切り詰めが効かないときは、`opaque_rect` を見る。

| `trim` | 当てはめるもの |
|---|---|
| `"alpha"`（既定） | 不透明な画素の外接矩形 |
| `"none"` | 素材のキャンバスごと（余白も枠に内接させる） |

**互換への影響。** `trim` を足す前の compose は `"none"` の振る舞いだった。
透過の余白を持つ素材を置いていた spec は、**同じ `rect` でも商品が大きく置かれ、
`placed` が変わる。** 余白込みで位置を揃えた素材など、余白そのものを構図として
使っていた spec と、`cover` で余白のほうを切り落としたかった spec には
`"trim": "none"` を書く。不透明な素材を置く spec は 1 バイトも変わらない。

### 実際に商品が占める矩形（`opaque_rect`）

`layers[].opaque_rect` は、画像の**不透明な画素が実際に占める矩形**である。
`placed` は素材の矩形なので、`"trim": "none"` の素材では透過の余白まで含む。
値は画素の格子へ外向きに丸めた整数である。文字の層と、1 画素も不透明でない画像では null。

**`outside_safe_area` はこちらで判定する。** `--canvas 1400 --fill-ratio 0.9` で
作った素材を `[800, 0, 480, 670]` へ `"trim": "none"` で余白ごと置くと `placed` は `[800, 95, 480, 480]`
で safe_area `[0, 108, 1280, 454]` の上へ出るが、不透明な画素は内側にある。
見えない余白が外へ出ても表示で切られるものは無いので、`OUTSIDE_SAFE_AREA` は
出さない。描く画素が 1 つも無い画像は `false` である。

**`role: "decoration"` の画像は測らず、`outside_safe_area` は null である。**
`fit: cover` で全面に敷いた背景の写真は safe_area の外へ出るのが当然で、表示で
切られても欠ける情報は無い——図形の層と同じ理由である。測ると普通の構図が毎回
`OUTSIDE_SAFE_AREA` を出し、`--fail-on default` を落とす。切られては困る画像は
`role: "subject"` で置く。

## 縮めない、折り返さない

収まらない文字は**縮めも折り返しもせず**、`TEXT_OVERFLOW` で言う。どちらも
spec に書いた指定が黙って消える向きの親切で、`--fill-ratio` が商品を枠へ合わせる
のとは**約束の向きが逆**である。

日本語の自動折り返しは禁則処理（行頭に句読点を置かない、など）と字詰めを伴い、
それを持つと kiri は合成器ではなくなる。どこで割るかは文意の問題でもあるので、
**`lines` は行の配列で受け取る。割る材料（行ごとの実測幅）は返すが、割らない。**

**縮めないが、収まる範囲は言う。** `TEXT_OVERFLOW` は上から、縮小表示の `too_small`
は下から `size` を押さえる。両方を同時に満たす値は `--size-range` が層ごとに返す
（[収まる文字サイズの範囲を引く](#収まる文字サイズの範囲を引く--size-range)）。
`size` を書き換えるのは spec のままである。

## 無い字体は黙って代替しない

指定の family が見つからなければ `FONT_NOT_FOUND` で断り、**1 枚も書かない。**
代替へ落ちると、**同じ spec が機械ごとに違う絵になる**——`SEGMENT_UNAVAILABLE`
が feature の無い build で黙って off へ落ちないのと同じ向きである。

`font.path` を書けばそのファイルだけを読む。実際に使った字体のパスと SHA-256 は
結果 JSON の `font` に出るので、**後から「何で組まれたか」を辿れる。**

## 層ごとに字体を選ぶ

最上位の `font` は**既定**である。文字の層に `font` を書けば、その層だけ
それで組む（書かない層は最上位を継ぐ）。見出しを W8、補足を W4 にするような
強弱は、1 ウェイトのファイルを層ごとに指して付ける。

```json
{
  "font": { "family": "Hiragino Sans", "path": "fonts/ヒラギノ角ゴシック W4.ttc" },
  "layers": [
    { "id": "heading", "type": "text", "role": "heading", "lines": ["見出し"],
      "rect": [80, 150, 560, 120], "size": 96, "weight": 800, "color": "#1f2328",
      "font": { "family": "Hiragino Sans", "path": "fonts/ヒラギノ角ゴシック W8.ttc" } },
    { "id": "note", "type": "text", "role": "caption", "lines": ["補足"],
      "rect": [80, 300, 560, 60], "size": 40, "color": "#1f2328" }
  ]
}
```

全部の文字の層が自分の `font` を持てば、最上位の `font` は省ける（結果の最上位の
`font` は null になる）。層ごとに**実際に組んだ字体**は結果の `layers[].font` が
名乗る——その層の `weight` で引いた face のパスと SHA-256、それに**実際に描かれる
太さ**（`weight`）である。

## 太さも黙って代替しない

**`weight` に合う face が字体に無ければ、近い太さの face で描かれる。kiri も
組版の resvg も太さを合成しない。** 1 ウェイトのファイル（W4）を指して `weight` を
100 と 900 にすると、2 枚はバイト単位で一致する。そのときは
`FONT_WEIGHT_UNAVAILABLE` が層を名指しし、`data.requested`（指定）と
`data.actual`（実際に描かれる太さを 100 刻みへ丸めた値）を返す。**その層では `weight` を変えても絵が
変わらない**ので、太さを変えたければその太さのファイルを `layers[].font` で指す。

可変フォント（wght 軸を持つ字体）は、軸の範囲の中なら指定どおりの太さで描かれ、
警告は出ない。範囲の外は端で止まるので出る。

`weight` は **100〜900 の 100 刻み**で書く。それ以外（450 など）は `SPEC_INVALID`
で断る——組版の resvg は 9 つの値しか太さとして読まず、450 は黙って 400 で組まれる。

## 文字を縁取る（`stroke`）

```json
{ "id": "heading", "type": "text", "role": "heading", "lines": ["見出し"],
  "rect": [80, 150, 560, 120], "size": 100, "color": "#ffffff",
  "stroke": { "color": "#000000", "width": 6 } }
```

| キー | 型 | 意味 |
|---|---|---|
| `color` | `#rrggbb` | 縁の色。不透明のみ |
| `width` | px | **字の輪郭から外へ見える幅。** 1 以上 `size` 以下（外れたら `SPEC_INVALID`。1px 未満の縁は 1 画素も塗らないのに比を名乗るので断る） |

写真の上に置いた見出しでは、文字色も下地も選べないことが多い。サムネで普通に
使われる手の 1 つが縁取りである。

- **外側にだけ付く。** SVG の stroke は輪郭の内外に半分ずつ乗るので、`2 × width`
  で描いて塗りを上に重ねる。字は細らない。角は丸める
- **字は縁の幅だけ `rect` の内側へ寄せて組む。** `start` は右へ、`end` は左へ、
  最初の行は下へ `width` だけ寄り、`center` は左右に動かない。寄せないと縁が
  字頭と最初の行の天で必ず枠の外へ出て、どう `rect` を書いてもはみ出しが残る
- **縁は見える画素である。** `placed` は縁を含む外接矩形になり、`text_overflow` と
  `outside_safe_area` も縁を含めて判定する。ただし縁の無い層と同じく、字の輪郭が
  字の送りの矩形からわずかに出る分（0.1px ほど）は数えない——`placed` は字の送りの
  矩形を 4 辺とも `width` だけ広げた範囲で止まる。重なり（`layer_overlap`）と覆い
  （`text_obscured`）は縁まで数える
- **`text_contrast` は、塗りと縁の色の比と、塗りと縁の下の地の比の良いほう**に
  なる。縁は字のすぐ周りを必ず囲むので、字が接する背後は縁である（白に黒の縁
  なら 21）。ただし縁が塗りと同じ色なら縁は字を何からも分けておらず、分けて
  いるのは地なので、地とも比べる（黒地に白の字と白の縁は 1.0 ではなく 21）
- 縮小表示では、縁が縮めても残るかで比べる相手が変わる（下の
  [縮小表示での読みやすさ](#縮小表示での読みやすさ)）
- `stroke` を書かない層は今までと 1 画素も変わらない

## 帯や札を敷く（`"type": "shape"`）

```json
{ "id": "band", "type": "shape", "rect": [0, 400, 1280, 160],
  "color": "#000000", "opacity": 0.6, "radius": 0 }
```

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `id` / `type` / `rect` | | | 他の層と同じ |
| `color` | `#rrggbb` | 必須 | 塗りの色 |
| `opacity` | 0 < x ≤ 1 | 1 | 塗りの不透明度 |
| `radius` | px, ≥ 0 | 0 | 角の丸み。幅か高さの半分を超えれば半分で止まる（SVG の規則） |

**角を丸められる矩形だけを持つ。** 文字の下に敷く帯、座布団、丸い札はこれで書ける。

- **`role` は書けない**（`SPEC_UNKNOWN_FIELD`）。結果では `role: "decoration"`・
  `kind: "shape"` で、`placed` は `rect` そのもの。測りのキーは全部 null で、
  **`outside_safe_area` も null**——端まで敷いた帯が表示で切られても欠ける情報は無い
- **文字の前（配列の先頭側）に置けば、文字の背後になる。** 原寸の `text_contrast` も
  縮小表示の測りも、何もしなくても帯の上で測る
- **文字の後に置けば、文字を覆う。** 不透明度 0.5 以上の図形が文字に重なれば
  `TEXT_OBSCURED` が言う
- 描画は文字と同じく resvg で、縁のアンチエイリアスが文字とそろう

## 測って返す（`--fail-on`）

| 指標 | 警告 | 何を見るか |
|---|---|---|
| `text_overflow` | `TEXT_OVERFLOW` | 文字が `rect` からはみ出した量(px) |
| `text_contrast` | `TEXT_CONTRAST_LOW` | 文字と**その文字が実際に載っている背後**とのコントラスト比 |
| `layer_overlap` | `LAYERS_OVERLAP` | 文字が覆う画素のうち `subject` と重なった比 |
| `outside_safe_area` | `OUTSIDE_SAFE_AREA` | `safe_area` の外へ出たか（画像は `opaque_rect` で、文字は `placed` で判定。decoration の画像と図形は測らない） |

```
$ kiri compose layout.json -o thumb.png --fail-on default
$ kiri compose layout.json -o thumb.png --fail-on text_overflow>0,text_contrast<4.5
```

**コントラストは背後の実測である。** 背景色の指定から計算すると、下に画像が
敷いてある場合に必ず外れる——ちょうどそこが読めなくなる場所である。しきい値の
4.5 は WCAG 2.1 の AA で、kiri が決めた数ではない。

**1/64px 以下のはみ出しは 0 と数える。** 文字の外接矩形は f32 から上がって
くるので、y=190 に置いた字が 189.99998 になる、といった端数が出る。これを数えると
`text_overflow>0` が見た目に何も起きていない構図を落とす。`outside_safe_area` も
同じ幅を見逃す。1/64px を超えたはみ出しは、差し引かずに測ったとおりの量を返す。

**重なりは字が実際に覆う画素で数える。** 外接矩形で数えると、行間と字間の空白まで
商品に重なったことになる。

**`--fail-on` の指標は `kiri cutout` のものとは別である。** あちらは `mask.*` を
見る。同じ表に混ぜると `cutout --fail-on text_overflow` が書式として通り、cutout に
文字は 1 つも無いので**永久に発火しない門**になる。

## note の見出し画像を組む（`--profile note`）

```
$ kiri compose header.json -o header.png --profile note
$ kiri compose header.json -o header.png --profile note --fail-on default
```

**note の規定をキャンバスへ当て、一覧に縮んだときに読めるかを測る。** 原寸の
測りだけでは足りない——見出し画像が原寸で見られることはほとんど無く、note の
一覧では横 144〜192px に縮んで並ぶ。原寸で 4.5 を超えたコントラストも、64px の
見出しも、そこでは読めないことがある。

| 項目 | spec に書いてある | spec に無い |
|---|---|---|
| `canvas.width` / `height` | spec の値。比が 1280:670 から 0.5% 以上外れたら `PROFILE_ASPECT_MISMATCH` | 1280 x 670 |
| `safe_area` | spec の値 | 上下中央の `[0, 108, 1280, 454]`。キャンバスが違えば合わせる（下を参照） |

**`"safe_area": null` は書かなかったのと同じ**で、profile の範囲が入る。
キャンバスの比が規格と同じ（`PROFILE_ASPECT_MISMATCH` が出ない）なら範囲を比で
拡大する。外れていれば、**note が中央を規格の比へ切り取った後に残る範囲**を
使う——1280 x 720 なら上下 25px ずつ切られるので `[0, 133, 1280, 454]` になる。

**明示 > profile。** cutout の `--profile` と同じ約束である。1920 x 1006 は比が
同じ（0.1% 差）なので黙って通る。`canvas` の寸法を省けるのは `--profile` を
渡したときだけで、渡さずに省けば今までどおり `SPEC_INVALID` で断る。
書いたバイト数が 10MB（10,000,000 バイト）を超えたら
`PROFILE_MAX_BYTES_EXCEEDED` が出る。**`--dry-run` でも出る**——dry-run も
エンコードまでは通してバイト数を返している。

**cutout / lint の `--profile` とは別の表である。** `kiri compose --profile amazon`
も `kiri cutout --profile note` も書式の段階で断る。表そのもの（出典・安全領域・
上限・表示幅）は `kiri schema --json` の `compose_profiles[]` が配る。

### 縮小表示での読みやすさ

全層を重ね終えた**実際に見える絵**を、2 つの表示幅へ面積平均で縮めて、
文字の層ごとに測り直す。

| 表示 | 幅（CSS px） | 根拠 |
|---|---|---|
| `pc_list` | 192 | PC の一覧で最も多かった描画幅 |
| `mobile_list` | 144 | スマホの一覧で最も多かった描画幅 |

**表示幅は note が公表していない。** note.com を開いて測った値なので、改修で
変わりうる。結果の `profile.revision` が測った年月を言う。

```
$ kiri compose header.json -o header.png --profile note --json | jq '.layers[1].display'
[
  { "name": "pc_list",     "width": 192, "size_px": 9.6, "contrast": 11.2,
    "legible": false, "reasons": ["too_small"] },
  { "name": "mobile_list", "width": 144, "size_px": 7.2, "contrast": 6.69,
    "legible": false, "reasons": ["too_small"] }
]
```

| 理由 | いつ | 直し方 |
|---|---|---|
| `too_small` | `size_px`（= `size × 表示幅 / canvas の幅`）が 11 未満 | `size` を `11 × canvas の幅 / 表示幅` 以上にする（1280 幅なら mobile_list で 98） |
| `strokes_lost` | 縮めた被覆が 0.5 に届く画素が 1 つも無い（線が 1px 未満に潰れた） | `weight` を上げる。同じ層に `FONT_WEIGHT_UNAVAILABLE` が出ていれば `weight` は効かないので、太い face のファイルを `layers[].font` で指す |
| `low_contrast` | 縮めた絵での前景と背景のコントラスト比が 4.5 未満 | 文字色か、その文字が載っている下地を変える。変えられなければ `stroke` で縁取る（`width` は `canvas の幅 / 表示幅` 以上。1280 幅なら mobile_list で 9）か、文字の下に `shape` の帯を敷く |

1 つでも当たれば `legible: false` で、`TEXT_ILLEGIBLE_AT_DISPLAY` が出る。
11 は Apple の Human Interface Guidelines が本文の最小とする 11pt で、kiri が
決めた数ではない（4.5 が WCAG の数であるのと同じ扱い）。**大きさは em で測る**
——CSS の font-size と同じ量で、spec の `size` から逆算できる。

**原寸の `text_contrast` とは別の量である。** あちらは文字色と背後、こちらは
縮めた絵で見えている前景（その文字の被覆が 0.5 以上の画素）と背景（外接矩形の
中で 0.05 未満の画素）の相対輝度の中央値を比べる。中間色の地（#767676）に白の
100px は原寸で 4.54 だが、縮めると線が地の色と混ざって 3〜3.9 まで落ちる——
**原寸の値だけを読んだ呼び出し側は「読める」と判断する。**

**縁取りのある層は、背景を縁か地から選ぶ。** 外接矩形の中には縁と地の両方が
入るので、塗りの被覆に加えて塗り + 縁の被覆も同じ縮小で縮め、

1. 塗りが 0.05 未満で塗り + 縁が 0.5 以上の画素（**縮めても残った縁**）が 1 つでも
   あれば、それと比べる（`"against": "stroke"`）。比が 4.5 に届かなければ地とも
   比べ、良いほうを採る（塗りと同じ色の縁のため）
2. 無ければ、塗り + 縁が 0.05 未満の画素（**地**）と比べる（`"against": "ground"`）

**縁が縮小で潰れたら、縁が効いたとは言わない。** 1280 幅を 144 へ縮めると 1 画素は
原寸の約 8.9px 四方で、1〜2px の縁はそこで地に溶ける。#767676 の地に白 100px の
見出しは、黒の縁 8px で `pc_list` が 12.60（`stroke`）、縁 1px では 3.22（`ground`、
`low_contrast` のまま）になる（Arial Unicode MS、`start` 揃え）。`against` は縁取りのある層に
だけ出る。前景は縁の有無に依らず塗りの被覆で選ぶので、`strokes_lost` も変わらない。

**縁のある層の `low_contrast` には「縁取る」と言わない。** `against` が `ground` なら
縁を `canvas の幅 / 表示幅` px 以上へ太らせる手を、`stroke` なら文字色と縁の色を
離すか、`size` か `weight` を上げて塗りが縁に埋もれないようにする手を返す。
小さな字に太い縁を付けると、縮めた塗りが縁に埋もれて `stroke` と比べても足りなく
なる（44px のキャプションに縁 4px で `mobile_list` が 2.7）。

透過の画素は、出力が透過を保てるなら**白**（note の一覧の地）へ、保てないなら
潰す色へ重ねてから縮める。縮小は box（面積平均）で、Lanczos のように輪郭を
立たせて細い線を実際より読めるように見せることはしない。

測らないものは次の 3 つで、**測ったように見せない。**

- `role` が `decoration` の文字と画像の層——`display` のキーごと出ない
- **原寸で 1 画素も描かれなかった文字**——同じく `display` が無い（原因は
  `TEXT_NOT_RENDERED` が言う。縮めて線が潰れたのではない）
- **表示幅がキャンバスの幅以上の表示**——縮小にならないので測らず、`display[]` に
  行ごと出ない（1 つも測らなければ空の配列）

背景の画素が 1 つも無ければ `contrast` は null で、低コントラストとは言わない。
門の `display_*` は、測れた値が 1 つも無ければ `unmeasurable` になる。

`--fail-on` には縮小表示の指標が 3 つ増える。

| 指標 | 量 | `default` の門 |
|---|---|---|
| `display_text_size` | 全文字層・全表示での `size_px` の最小 | `< 11` |
| `display_contrast` | 同じく `contrast` の最小（null は数えない） | `< 4.5` |
| `display_strokes_lost` | `strokes_lost` に当たった表示があるか（旗） | 立ったら |

**`--profile` を渡さない `default` はこの 3 つを足さない。** 足すと、これまで
通っていた `--fail-on default` が「測っていない」で一斉に落ちる。明示して
書いた場合は、測っていないので `unmeasurable`（exit 5）になる。

### 縮小の絵を書き出す（`--preview`）

```
$ kiri compose header.json -o header.png --profile note --preview
```

**縮小表示の測りが見た絵を、そのまま PNG で書く。** 数だけでは「どこが潰れたか」が
分からない。出力の隣に `<出力の stem>.<表示名>.png`（`header.pc_list.png` /
`header.mobile_list.png`）ができる。

- 書くのは**測りが使った絵そのもの**（透過を白か潰す色へ重ね、面積平均で縮め、
  8bit へ丸めた RGB）で、別の縮小で作り直さない。画素から計算した相対輝度は
  測りの輝度と一致する
- 大きさは表示の CSS px（192 x 101 / 144 x 75）。拡大はしない
- 測らない表示（表示幅がキャンバスの幅以上）は書かない
- **`--profile` が要る**（無ければ exit 2）。**`--dry-run` とは併用できない**（exit 2。
  dry-run は 1 バイトも書かない約束である）
- **書く先は画素を描く前に全部確かめる。** 既存のファイルは `--force` が無ければ
  断り、ディレクトリは `--force` があっても断る。ここで断れば出力も含めて 1 つも
  書かない
- **全部をエンコードし終えてから書く。** 書く途中で失敗したら（ディスクが一杯、
  権限が途中で変わった、など）、この実行が新しく作ったファイルは消す。
  **`--force` で上書きしたファイルは戻せない**——前の中身を持っていないので、
  エラーの hint がどれを上書きしたかを言う

結果 JSON の最上位に `previews[]` が出る。`--preview` を渡さなければキーごと出ない。

```json
"previews": [
  { "display": "pc_list", "path": "header.pc_list.png", "width": 192, "height": 101 },
  { "display": "mobile_list", "path": "header.mobile_list.png", "width": 144, "height": 75 }
]
```

## 文字を置ける空きを引く（`--free-regions`）

```
$ kiri compose layout.json -o thumb.png --dry-run --free-regions --json | jq .free_regions
```

```json
{
  "within": [0, 108, 1280, 454],
  "margin": 24,
  "min_size": [196, 98],
  "cell": 8,
  "regions": [
    { "rect": [0, 108, 472, 454], "area_ratio": 0.369 },
    { "rect": [1072, 108, 208, 128], "area_ratio": 0.046 }
  ]
}
```

**どこへ置けばよかったかを、置く前に言う。** compose が言えるのは「置いた結果が
まずい」ことだけで、`rect` を当て推量で書くと `LAYERS_OVERLAP` や
`OUTSIDE_SAFE_AREA` が出てから書き直すことになる。`opaque_rect` は外接矩形に
すぎず、瓶の肩の横や、斜めに置いたリモコンの脇のように、**矩形の内側にも文字を
置ける場所が大きく残っている**。その空きは切り抜いた alpha の形で決まるので、
kiri にしか出せない。

「`--dry-run --free-regions` → 候補の 1 つを文字の `rect` に書く → 組む」の 2 手で
済む。**kiri は置かない**——候補を返すだけで、どれを使うかは spec が決める
（合成器であって組版器ではない）。

| キー | 意味 |
|---|---|
| `within` | 探した範囲。`safe_area` があればそれ（キャンバスへ切り詰め、画素の格子へ内向きに丸める）、無ければキャンバス全体 |
| `margin` | 障害物から空けた距離（px）。候補と障害物の画素の間に、少なくともこの数の画素が挟まる |
| `min_size` | これより小さい候補は捨てた `[幅, 高さ]` |
| `cell` | 探索の格子（8px、固定）。候補の座標は `within` の左上からこの倍数へ**内向きに**丸まる。右端と下端だけは `within` の端に一致しうる |
| `regions[].rect` | 空いている矩形 `[x, y, 幅, 高さ]`（整数）。**中のどの画素も、障害物の画素から `margin` を超えて離れている**（チェビシェフ距離。正方形の近傍で見る） |
| `regions[].area_ratio` | `within` に対する面積の比 |

並びは面積の大きい順で、同じなら `(y, x)` の小さい順、それも同じなら幅の小さい順
（同じ左上・同じ面積の縦長と横長は縦長が先）。最大 8 個。上の例は `--profile note` で、
傾けた楕円の商品を `[500, 40, 700, 600]` に置いた spec の実際の出力である。2 つ目は
商品の外接矩形の右上の内側にかかっている。`within` の縁は障害物ではないので、
そこからは `margin` を空けない。

### 何を避けるか

| 層 | 避ける形 | 理由 |
|---|---|---|
| 画像で `role` が `decoration` でないもの | **不透明度が 0 でない画素** | 外接矩形で数えると、瓶の肩の横のような空きが消える |
| 文字（すべての role） | `placed` の矩形 | 文字は行間ごと 1 つの塊として読まれる。グリフの画素だけを避けると、行間に別の文字を差し込む候補が出る |
| 図形 / `decoration` の画像 | 避けない | 帯や背景の写真は**文字を載せる下地**であって、避ける相手ではない |

**画像は不透明度が 1 でもあれば避ける。** 枠へ当てはめる Lanczos は縁の外に
不透明度 1〜3 の裾を数画素ぶん作り、目には見えないがそれも避ける——候補が商品に
近づく向きには倒れない。

**位置を決めたい文字の層は、spec から抜いて引く。** 文字はどの role でも `placed` で
避けるので、動かしたい見出しを残したまま引くと、その見出し自身が移動先を塞ぐ。
`jq` で層を外した spec を通せばよい。残した文字は障害物として扱われる。

```
$ jq 'del(.layers[] | select(.id == "heading"))' layout.json > probe.json
$ kiri compose probe.json -o thumb.png --dry-run --free-regions --json | jq .free_regions.regions
```

`probe.json` は素材のパスを spec からの相対で解くので、元の spec と同じ場所に置く。

`subject` 以外の画像（ロゴを `heading` で置いたものなど）も避ける。`layer_overlap` は
`subject` だけを数えるので、ここは線引きが違う。避けなくてよい画像は `decoration` と
書く。背景の写真の上で**読めるか**は見ていない——空いていても、ごちゃついた下地の
上では読めないことがある。

### 求め方

1. 障害物を原寸のビットマスクに持ち、`margin` だけ膨らませる（正方形の近傍）。
   膨らませたマスクは作らず、セルを `margin` だけ広げた範囲に障害物があるかを
   横と縦に分けた 2 回の累積で問う。増える確保は上限の 16384 x 16384 でも約 64MiB
2. 8px の格子へ**保守的に**畳む。セルに膨らませた障害物が 1 画素でも掛かれば、
   そのセルは埋まっている。格子は `within` の左上から引き、右端と下端の端数の
   セルは `within` の内側へ切り詰める（`within` の外の画素はセルに含めない）
3. 格子の上で**極大な空き矩形**（どの方向にも広げられない矩形）を全部並べる
   （行ごとのヒストグラムとスタック。セルの数に比例する手間）
4. `min_size` より小さいものを捨て、面積の大きい順に並べ、**既に残した候補の
   どれか 1 つに面積の 70% 以上が入るもの**を捨てて、8 個で止める

「重なったら捨てる」にしないのは、L 字型の空きでは横長と縦長の 2 つが角で重なり、
**どちらにも別の使い道がある**からである（横長は 1 行の見出し、縦長は箇条書き）。
格子に畳むのは、原寸のまま並べると切り抜きの縁の 1 画素ごとに矩形が生まれるため。
1280 x 670 で増える時間は 1ms 前後である（`--release`。本体だけで 1 回 0.6〜0.7ms）。

### 既定値

| 値 | 既定 | 根拠 |
|---|---|---|
| `margin` | `round(canvas の幅 × 24 / 1280)`（1280 幅で 24px）。`--free-margin <px>` で上書きでき、端数は切り上げる | 文字が商品に触れて見えない距離 |
| `min_size` の高さ | `--profile` があれば、最も狭い表示で 11px になる文字 1 行の高さ（`ceil(11 × canvas の幅 / 表示幅)`。note なら 98）。無ければ canvas の短辺の 8%（切り上げ） | 読めない大きさの文字しか入らない候補は、出しても使い道がない |
| `min_size` の幅 | 高さの 2 倍 | 2 文字を下回る幅に見出しは入らない |

- `--free-margin` は `--free-regions` が要る（無ければ exit 2）。負の値・有限でない値・
  キャンバスの辺の上限 16384 を超える値も exit 2（clap の引数検査で、kiri の code は付かない）
- キャンバスの辺より広い `--free-margin` は切り詰めずにそのまま空け、`margin` も渡した値
  （の切り上げ）のまま返す。障害物が 1 つでもあれば候補は無く、無ければ `within` そのもの
- **`--free-regions` を渡さなければ `free_regions` のキーごと出ない。** 障害物のマスクも
  作らないので、渡さない実行の費用も出力も変わらない
- 層が避ける相手を 1 つも持たなければ（図形と `decoration` だけ）、`within` そのものが
  1 つだけ返る

## 収まる文字サイズの範囲を引く（`--size-range`）

```
$ kiri compose layout.json -o thumb.png --dry-run --profile note --size-range --json \
    | jq -c '.layers[] | select(.kind == "text") | {id, size_range}'
```

```json
{"id":"heading","size_range":{"min":98,"max":62,"limited_by":"width"}}
{"id":"wide","size_range":{"min":98,"max":124,"limited_by":"width"}}
```

**`size` をどの範囲に書けば収まって読めるかを、組む前に言う。** はみ出しを
`TEXT_OVERFLOW` で知って `size` を下げると、今度は `too_small` が出る——当て推量で
`size` を書き換えると、この往復が続く。「`--dry-run --size-range` → 範囲の中の値を
`size` に書く → 組む」の 2 手で済む。**kiri は `size` を書き換えない。**

| キー | 意味 |
|---|---|
| `size_range.max` | この `rect`・`lines`・`weight`・`line_height`・`align`・`font`・`stroke` のまま、`text_overflow` が 0 になる最大の整数 `size`。収まる整数が無いか、上限が無ければ `null` |
| `size_range.min` | `--profile` の測る表示のうち最も狭い幅で、表示上 11px に届く最小の整数 `size`。`too_small` の hint が「size を N 以上に」と言う N と同じ式・同じ丸め。`--profile` が無いか、測る表示が 1 つも無ければ `null` |
| `size_range.limited_by` | 上限を決めた向き。`width`（最も長い行の幅）/ `height`（行の積み上げ）/ `none`（どれだけ大きくしても はみ出さない。`max` は `null`）。収まる整数が無ければ `null` |

上の例は冒頭の spec の `heading` に、1 行の `wide`（`rect` が `[80, 400, 1120, 200]`）を
足し、ヒラギノ角ゴシックで組んだ実際の出力である。**`heading` は範囲が空**（`min > max`）
で、64px のままでも幅で 16px はみ出す（最も長い行が 576px）。`size` をどう書いても はみ出しと `too_small` の
両方は消えないので、`lines` を割り直すか `rect` を広げる。`width` なら行を短く、
`height` なら行を減らすか `line_height` を詰める。

- **書いたら確実に収まる整数である。** `max` で組めば `text_overflow` は 0、`max + 1` で
  組めば 0 より大きい。`placed` の 4 辺は `size` の 1 次式なので、spec の `size` と
  `max(2 × size, 64)` の 2 点から見積もり、その値と + 1 を組み直して確かめる。
  外れていれば 1 ずつ 3 回まで歩き、それでも決まらなければ二分探索で詰める
  （縁取りの層では、縁の矩形と字の送りの矩形のどちらが外側かが `size` で入れ替わり、
  直線から外れることがある）
- **縁取りの幅は上限を下げる。** 縁は `size` に依らない幅で外へ出る。`stroke.width` を
  下回る値は spec に書けない（`SPEC_INVALID`）ので `max` には返さない。`min` は
  `too_small` の hint と揃えるため `stroke.width` を下回ることがあり、そのときは
  `stroke.width` 以上を書く。`max` も `limited_by` も null なら、どの整数も収まらない
  （縁が太すぎて 1 字も入らないなど）ので、`rect` を広げるか縁を細くする
- **下限が押さえるのは `too_small` だけである。** `strokes_lost` と `low_contrast` は
  縮めた絵を測らないと分からないので、範囲には入れない。`role` は問わない
- 今の `size` が範囲の中かどうかは出さない。spec の `size` と比べれば分かる
- 画像と図形の層には出ない。**`--size-range` を渡さなければ `size_range` のキーごと
  出ない**し、組み直しもしない。1280 x 670・文字 3 層で増える時間は 5ms 前後
  （`--release`。1 層あたり幾何だけの組み直しが普通 3 回）。見積もりが最も低く
  外れた層の最悪は 35 回（`s1`・候補・上へ 4 回・倍々 14 回・二分探索 15 回）。
  実の字体でそこまで外れる層は測った範囲では無く、二分探索に落ちた層でも 14 回だった
- はみ出しは `size` について単調（大きくするほど減らない）という前提で探す
- `--free-regions` の候補ごとの上限は返さない。候補の矩形を文字の `rect` に書いた spec で
  `--size-range` を引けばよい

## 持っていないもの

`--derive` / `--manifest` / `--max-bytes` は無い。1 枚を組んで 1 枚を書く
コマンドなので、派生が要るなら組んだ結果を `kiri convert` / `kiri resize` へ
渡せばよい。使えない項目をヘルプに並べると、**`kiri schema` が「指定できる」と
言った先に出口が無い**ことになる。
