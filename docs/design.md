# kiri 設計ドキュメント

最終更新: 2026-09-06

## 1. 目的

AIエージェントから使われることを前提とした画像編集CLI。EC商品画像の背景透過切り抜き・整形・Web配信形式への変換を一貫して行う。

既存ツール（ImageMagick + rembg 等）との差別化は次の3点に置く。

- **依存ゼロ**: Python環境も外部ツールもMLモデルも不要。単一バイナリで動く
- **起動が速い**: AIエージェントは同じCLIを何度も呼び出す。起動に秒単位かかると体感を殺す
- **構造化I/Oと決定的動作**: 同じ入力に対して常に同じ出力。結果はJSONで返り、AIが次の判断に使える

## 2. スコープ

### 2.1 対象

- **単色背景**（白・グレー等のスタジオ撮影背景）のEC商品画像
- 背景透過切り抜き / リサイズ / キャンバス配置 / 形式変換

### 2.2 非対象（v1で明示的に切る）

| 項目 | 理由 |
|---|---|
| 複雑背景（生活シーン・屋外撮影） | 古典的画素処理では品質が出ない。MLモデルが必要になり pure Rust 方針と衝突する |
| 髪の毛レベルの精密マッティング | 要求は「輪郭レベル」で足りると判断 |
| WebP 出力 | 実用的なロッシー圧縮には libwebp（C）が必要 |
| AVIF 入力 | デコードに dav1d（C）が必要 |
| MCPサーバーモード | CLIに専念する |

非対象の画像に対しては `kiri info` の `background.uniformity` で事前に検知し、警告を返す。AI側が「この画像は非対応」と判断できるようにする。

## 3. 技術選定

### 3.1 依存方針

**pure Rust のみ。C依存を持ち込むクレートは採用しない。**

理由は3つ。単一バイナリで配布できること、クロスコンパイルが素直に通ること、そしてビルドの容易さがOSSの採用障壁を直接下げること。この方針が対応形式の選択（WebP非対応）を規定している。

### 3.2 採用クレート

| クレート | バージョン | 用途 |
|---|---|---|
| `image` | 0.25 | JPEG/PNG のデコード、PNG/JPEG のエンコード |
| `ravif` | 0.13 | AVIF エンコード（内部で `rav1e` 0.8） |
| `fast_image_resize` | 6.1 | SIMD リサイズ（Lanczos3） |
| `kamadak-exif` | 0.6 | EXIF Orientation の読み取り |
| `clap` | 4.6 | CLI パーサ |
| `serde` / `serde_json` | 1.x | JSON 出力 |
| `rayon` | 1.x | バッチ処理の並列化 |

切り抜きアルゴリズムは全て自前実装する。ここがこのプロジェクトの本体である。

### 3.3 対応形式

- **入力**: JPEG, PNG
- **出力**: AVIF（既定）, PNG, JPEG

入出力が非対称だが、用途（撮影素材を受け取ってWeb配信形式で出す）を考えれば問題にならない。

**HEIC / HEIF は入力にできない。** HEVC のデコーダは pure Rust に存在せず、libheif や
libde265（いずれもC）が必要になる。EC の入稿素材は iPhone 撮影が多く、そのまま渡せば
HEIC で来るため実害はあるが、依存ゼロの前提を崩すほどではないと判断した。

代わりに**先頭の `ftyp` ボックスを自前で見て、原因と変換手順を返す**。`image` に任せると
形式の判別自体に失敗して「拡張子から判別できません」に落ちる。原因が HEIC だと分からない
メッセージでは、AI エージェントは別の拡張子を試すような無駄な再試行に入るためである。
ヒントには macOS の `sips`（追加インストール不要）と、ImageMagick / libheif の例を載せる。

AVIF は入力としては同じ扱い（デコードに dav1d が要る）だが、出力としては pure Rust で
エンコードできるため既定の出力形式である。

### 3.4 AVIF エンコード実測結果

pure Rust での AVIF エンコードが実用速度に収まるかが唯一の技術的不確定要素だったため、実装前に計測した。

計測環境: Apple M4 Pro（14スレッド）、`ravif` 0.13.0 / `rav1e` 0.8.1、release ビルド

| 設定 | 1000×1000（1.0 MP） | 2400×3200（7.7 MP） |
|---|---|---|
| speed 10 / q75 | 29 ms | 203 ms |
| **speed 6 / q75** | **57 ms** | **459 ms** |
| speed 4 / q75 | 114 ms | 687 ms |
| speed 1 / q75 | 1,381 ms | 9,835 ms |
| speed 1 / q85 | 5,736 ms | 40,296 ms |
| PNG（比較） | 5 ms | 22 ms |

**判明したこと**

1. C依存なしでビルドが通る（依存クレート込みで23秒）
2. アルファチャンネルは正しく保持される。macOS のデコーダで検証したところ `hasAlpha: yes`、完全透明 52.2% / 不透明 47.2% / 中間値 0.67%。境界のアンチエイリアスも保たれている
3. `speed 6` が最適点。これより遅くしてもサイズ削減が時間に見合わない
4. `speed 1` は崖。7.7MP で40秒に達するため使わせない
5. `quality` は 75 が境目。85 にするとサイズが約4倍に跳ねる

**決定**: AVIF をデフォルト出力形式とする。既定値は `quality 75` / `speed 6`。`--quality` と `--effort` で調整可能にする。

**この計測の限界**: テストに用いたのは合成画像で、実写より圧縮が効きすぎている（1MPで7KB）。**時間の数値は概ね代表的だが、ファイルサイズの絶対値は当てにならない。**実画像での再計測を実装フェーズで行うこと。

**実装時に検証すべき点**: 完全透明ピクセルにRGBデータが残っていた。`ravif` の `AlphaColorMode::UnassociatedClean` を指定すると透明部をクリーンにでき、透明領域が広い商品画像ではさらにサイズが縮む可能性がある。

### 3.5 色管理（埋め込み ICC → sRGB）

EC の入稿素材は iPhone 撮影が多く、Display P3 で入ってくる。これを sRGB として素通しすると
彩度の高い色ほど誇張されて出る。**「届いた商品が写真と違う」に直結するため、色変換は
品質の話ではなく正しさの話である。**

#### 対象を行列 + TRC 型に絞る

`lcms2` は C 実装なので使えない。自前で書くしかないが、ICC の全体を実装する必要は無い。
実写で問題になるのは Display P3 と AdobeRGB で、どちらも**行列 + TRC 型のディスプレイ
プロファイル**（`rXYZ` / `gXYZ` / `bXYZ` と `rTRC` / `gTRC` / `bTRC` を持つもの）に収まる。

| 型 | 扱い |
|---|---|
| 行列 + TRC（`curv` のガンマ1点・テーブルN点、`para` タイプ0〜4） | 変換する |
| LUT 型（`A2B0` 等のみで行列を持たない） | 変換せず、その旨を警告して sRGB として扱う |
| CMYK / Gray、PCS が Lab のもの | 同上 |
| 壊れた ICC | 同上（画像は読めているのに落とすのは筋が悪い） |

LUT 型まで背負うと補間器と CLUT の実装が要る。**得られるのは「稀な入稿素材でも色が合う」
だけで、対価としてバグの入る面積が数倍になる。** 割に合わないと判断した。

#### 変換の手順

TRC でデコード → 行列で XYZ(D50) → D50→D65 の白色順応 → XYZ→線形 sRGB → sRGB のガンマ。

**インテントは相対比色のみ。** EC 用途では白を白に保つことが最優先で、知覚的インテントに
必要な LUT はそもそも解釈対象外である。色域外はクランプする。

白色順応は **Bradford**。ICC の PCS は必ず D50 だが sRGB は D65 なので、間に必ず挟まる。
プロファイルの版や `chad` の有無によらず、**常に標準の Bradford で D50→D65 に戻す**。

**`chad` は使わない。** `chad` は「媒体の実測白色点 → D50」の行列で、その逆は
「D50 → 媒体の実測白色点」であって D65 ではない。相対比色では PCS の値も
`rXYZ`/`gXYZ`/`bXYZ` も既に媒体相対（媒体の白 = PCS の白 = D50）で表されているので、
`chad` を挟む余地がそもそも無い。挟むと、媒体白色点が D65 でないプロファイル
（D50 の ROMM / ProPhoto、DCI 白の DCI-P3、D60 の ACES）で白が白でなくなる。
`chad` が要るのは絶対比色のときだけである。

媒体白が D65 のプロファイル（Display P3 / AdobeRGB / ITU-709 / `Generic RGB Profile`）
では `invert(chad)` がたまたま Bradford の D50→D65 と一致するため、実写では気づけない。
なお v2 だから `chad` を持たないとも限らない（`Generic RGB Profile` は v2.2 かつ
`chad` あり）ので、版で分岐する設計そのものが誤りだった。

#### sRGB 相当は変換しない

原色が sRGB と一致し、**かつ** TRC も一致すれば、変換をスキップして
`color_space: "sRGB"` と報告する。往復の丸め誤差を足すだけで得るものが無いうえ、**既存の
sRGB 素材の出力バイト列が変わってしまうと、決定的動作という前提そのものが崩れる。**

**名前は見ない。** 「sRGB」を含む名前で中身が別物のプロファイル（sRGB 原色に
ガンマ 1.0 や 1.8 を載せたもの）は実在し、名乗りを信じると 8bit で 60 / 18 レベル
ずれた画像をそのまま素通しさせる。実プロファイルの側にも名乗りへ頼る理由は無く、
macOS の `sRGB Profile.icc` の `curv[1024]` は解析式との差が 7.6e-6 で、TRC の
一致だけで通る。素通しした場合も ICC 自身の名乗りは `color_profile` に残す。

#### 表で引く

`powf` を画素ごとに呼ぶと 12MP で桁が変わる。TRC のデコードは 8bit 入力の 256 エントリ表
（入力が 8bit しか取り得ない以上、表を引けば結果は厳密に一致する）、sRGB のエンコードは
線形値を 4096 分割した表と線形補間で引く。sRGB のガンマは暗部で最も曲がるが、そこでも
補間誤差は 8bit の 0.01 段に収まる。

実測（Apple M4 Pro、12MP、release）: 変換そのものが **5ms 前後**、CLI 全体のピーク RSS の
増加が **2MB**。画像を複製せずその場で書き換えるため、メモリはほぼ増えない。

#### 検証

合成 ICC（Display P3 / sRGB / AdobeRGB / ROMM RGB / DCI(P3) / LUT 型 / CMYK）をテスト内で
組み立て、P3 の原色が sRGB でクランプされること・中性グレーが中性のまま L* を保つこと・
sRGB では恒等になることを固定している。実写では、Display P3 の格子画像を kiri と
ColorSync（`sips --matchTo`）の両方で sRGB 化して突き合わせ、**全 8427 色で最大チャンネル
差 1、平均 ΔE 0.035** を確認した（未変換のままだと平均 ΔE 5.5、最大 18.8 ずれる）。

合成 ICC は自分が書いた前提しか踏まない。実ファイルには rTRC/gTRC/bTRC のオフセット共有、
31 言語を持つ `mluc`、v2 なのに `chad` を持つ並びといった、合成では思いつかない組み合わせが
ある。そのため、インストール済みの ColorSync プロファイル（sRGB / Display P3 / AdobeRGB /
Generic RGB / ROMM / DCI(P3)）をそのまま読み、グレー階調が ColorSync と littleCMS 2.17 の
両方が返した値と 1 以内で一致することも固定している。**プロファイル自体はリポジトリに
置かない**（Apple / Adobe / HP の著作権表示があり再配布に懸念があるため）。見つからない
環境では黙って飛ばす。

**ColorSync と一致しないものが 1 つある。** `ITU-709.icc` は `para` タイプ 3 の
Rec.709 曲線を持つが、ColorSync はこれを純ガンマ 2.4 として扱う（グレー 128 が
kiri 140 / ColorSync 121）。littleCMS は kiri と同じ 140 を返すので、これは
プロファイルの記述どおりに解釈しているか、名前付きビデオ色空間として別の
転送関数を当てているかの違いであり、kiri 側の誤りではない。

## 4. 切り抜きアルゴリズム

### 4.1 方針

MLモデルを使わず、**外周からの連結フラッドフィル**を主アルゴリズムとする。単色背景に限定したことでこれが成立する。

### 4.2 処理手順

1. **読み込みと正規化** — EXIF Orientation を必ず適用する。これを怠るとAIが見ている画像の向きと生ピクセルの座標系がずれ、bbox指定が全てずれる
2. **背景色推定** — 画像外周の1〜2px幅の帯からサンプリングし、中央値を背景色とする。同時に分散から `uniformity`（背景の均一度）を算出する。あわせて外周の広めの帯（短辺の3%）で勾配の分布 `texture` を測り、堤防を張れる素材かどうかを判断する（4.3）
3. **背景マスク生成** — 外周の全ピクセルをシードとしたフラッドフィル。色距離は CIE Lab 空間で評価し（知覚的距離のほうがしきい値の直感と一致するため）、`--tolerance` と比較する。**到達できた領域のみを背景とする**。あわせて勾配がしきい値を超える画素への侵入を禁じる（後述のエッジ堤防）。4近傍で塗り広げる。8近傍だと斜めの隙間から商品内部へ漏れるため。フィル自体は芯・拡張・影の 3 段に分かれる（4.3）
    - **狭い隙間からの浸水の遮断** — 続けて、背景マスクを `--seal` px 収縮し、外周に連結する成分だけ残して同じだけ膨張させる（測地的オープニング）。幅 2N px 以下の隙間を通ってしか外周につながらない領域を前景へ戻す
4. **bbox適用** — `--bbox` が指定されていれば、その外側を無条件に背景として扱う
5. **孤立ノイズ除去** — 連結成分の面積が `(2*cleanup+1)^2 * (長辺/1000)^2` に満たないものを消す。オープニングは使わない（4.6 を参照）。クロージングによる穴埋めも行わない
6. **境界帯のアルファ再推定とデスパイル** — 境界に帯を張り、帯の各画素で近傍の確定前景色 F と確定背景色 B を集め、観測色 C を F–B 直線へ射影してアルファを求める。同じ F・B から商品色も復元する（4.7）。`--no-refine` で旧来のフェザリング + 大域背景色でのデスパイルへ戻せる
7. **孤立ノイズ除去（2回目）** — 帯の推定で縁が透明へ戻った後こそが、成分の大きさを正しく測れるタイミングである
8. **キャンバス配置** — `--canvas` / `--fill-ratio` に従って配置する
9. **背景合成** — `--background` が指定されていれば指定色で合成する
10. **エンコード**

sRGB → XYZ → Lab の色変換は自前実装する（数十行）。

### 4.3 白背景 × 白い商品への対処

ECで最頻出かつ最難の状況（白背景の白いスニーカー、シルバーの時計など）。単純な色距離判定では商品内部に穴が空く。

**解決は手順3の「連結性」にある。** フラッドフィルを画像外周から到達可能な領域に限定すれば、商品内部の白は外周から到達できないため生き残る。これが第一の武器であり、実装コストに対して効果が最も大きい。

#### エッジ検出による堤防（実装済み・実測あり）

連結性だけでは足りない場面がある。落ち影を消すには許容量を広く取る必要があるが、
広く取ると淡い色の商品が背景ごと飲み込まれる。この衝突は色差だけでは解けない。

**解は勾配にある。** 商品の輪郭は 1px で十数以上の急峻な変化を示すのに対し、
落ち影は数十 px かけて 1px あたり 1-2 程度しか変化しない。Sobel の勾配強度を
「1px あたりの輝度変化量」に正規化し、これがしきい値（既定 8）を超える画素へは
フラッドフィルを侵入させない。

実測（白背景 250,250,249 に ほぼ白い商品 242,242,240 を置いた画像、既定 tolerance 12）:

| 条件 | 前景比率 | 検出された前景範囲 |
|---|---|---|
| 堤防あり（既定） | 25.2% | `[299, 419, 901, 1171]` |
| 堤防なし | 3.4% | `[432, 660, 768, 840]` |
| 商品の実位置 | — | `[300, 420, 900, 1170]` |

堤防がなければ、商品本体は背景として消え、濃いラベル部分だけが残る。
同じ設定で濃い色の商品を処理した場合も落ち影は除去されたままであり、
両立できていることを確認した。

#### 背景そのものがざらついている場合（テクスチャ検知）

堤防には裏がある。**背景の素材が 1px あたり十数の変化を持っていると、堤防は
背景の中で壁になる。** 不織布・キャンバス地・段ボール・畳がそれで、実写
（4284x5712 の不織布の上に黒いリモコン）では外周の帯の 26% が堤防の画素になり、
4 近傍のフィルは外周から数 px も進めなかった。前景比率 0.94、つまり「ほとんど
何も消えない」結果になる。

逃げ道は `--edge-threshold 0` だが、**それを知らなければ救えない。** kiri は AI
エージェントが使う道具であり、知識ではなく既定値で解けることを優先する。

**解は「堤防を張れる高さ」を背景から測ることにある。** 外周から短辺の 3% の帯で
Sobel の勾配強度（堤防のしきい値と同じ「1px あたりの輝度変化量」）の分位を取り、
`--edge-threshold` が明示されていない場合に限り、しきい値を引き上げる
（`background.texture` として JSON にも出す）。

**発火するかどうかは p50 で、どこまで上げるかは p90 で決める。** 条件は
「p50 が既定の堤防（8）以上」で、上げ先は「p90 の 1.5 倍」である。

| 素材 | p50 | p90 | 効いた堤防 | 結果 |
|---|---|---|---|---|
| スタジオ背景（合成 S1-S10） | 0.0 | 1.0 | 8（既定のまま） | 指標は一切変わらない |
| 織り目のある背景（合成 S11） | 10.3 | 14.0 | 21.0 | 前景比率 0.375（正解）。堤防を 8 に固定すると 0.85 |
| 織り目 + 淡色商品（合成 S12） | 10.3 | 14.0 | 21.0 | 欠け 0%・縁の残り 0%。堤防 8 で縁 100%、堤防 0 で欠け 100% |
| 不織布（実写 IMG_0251） | 11.3 | 27.9 | 41.8 | 前景比率 0.204、halo_ratio 0.003 |
| 下端で見切れた柄物の商品（合成 H1） | 0.4 | 19.2 | 8（既定のまま） | 背景はきれいなので触らない |

**発火条件に p90 を使ってはならない。** p90 は「背景がざらついている」と「帯に
ざらついた物が写り込んでいる」を区別できない。EC で頻出する「商品が画面の下端で
見切れている」構図では外周の帯の 1 辺がまるごと商品の内部になり、その商品が
無地でなければ p90 だけが跳ねる。上の H1 がその実測で、p90 発火の実装では堤防が
8 から 28.9 まで上がっていた。堤防が守るはずだった淡色商品（S3）が耐えられるのは
25 までなので、これは堤防を切ったのと同じ結果（境界近傍の欠け 38.7%）になる。

p50 は「帯の半分がこれを超える」水準なので、**典型的な外周の画素そのものが
堤防の画素かどうか**を言う。壁になるのはまさにこの状態である。実写の帯は 26% が
堤防の画素で、非極大抑制が 3 本に 1 本しか残さないことを踏まえると抑制前は
帯の 8 割が 8 を超えていたことになり、p50 11.3 > 8 と符合する。両側の余裕も広い。

| 外周の帯 | p50 | 発火 |
|---|---|---|
| 平坦な背景 JPEG q25〜q95 | ≤ 0.7 | しない |
| 外周まで届く落ち影 | 0.8 | しない |
| 下端で見切れた無地の商品 | 0.0 | しない |
| 下端 5〜25% が柄物の商品 | ≤ 0.8 | しない |
| センサーノイズ ±12 | 6.6 | しない |
| 織り目（周期 6px・振幅 11、堤防が壁になり始める点） | 9.6 | する |
| 不織布（実写） | 11.3 | する |

**引き上げ幅まで p50 基準にはしない。** 実写に 1.5 倍を p50 へ掛けると 17 に
しかならず、前景比率は 0.69 で正解（0.51、堤防を切った場合と同じ）に届かない。
壁の濃さを決めるのは分布の上の裾であって中央値ではない。

**無効化ではなく引き上げにしたのは、堤防の役目を残すためである。** 織り目の上に
載った淡い商品は、輪郭の勾配が織り目より大きい限り守られる。実写では 1.0 倍で
halo_ratio 0.0073、1.5 倍で 0.0059、堤防を切った場合が 0.0058 で、1.5 倍は
「切ったのと同じ結果」に達している。1.5 倍という値はここから来ている。p90 は
「帯の 1 割がこれを超える」水準なので、そのまま堤防にすると背景の 1 割が
侵入禁止になって壁として立つが、1.5 倍まで上げると残るのは数 % で、点在する
だけになり経路を塞がない。

上げ過ぎても下げ過ぎても駄目であることは合成 S12 が固定している。織り目
（p90 14.0）の上に輪郭の段差 28 の淡色商品を置くと、堤防を切れば商品はまるごと
飲まれ、既定の 8 では織り目が壁になる。両立するのは 12〜24 の窓だけで、
1.5 倍（21）はその中にある。

**黙って値を変えない。** 効いた値は `settings.edge_threshold` に、変えた理由と
根拠の数値は `warnings` に出す。明示指定には手を出さない。0 を指定した利用者は
無効化を、8 を指定した利用者は 8 を望んでいる。

測る帯を外周に限るのは費用の問題である。12MP で画像全体の Sobel を取ると輝度・
強度・向きの表で 150MB を積むが、帯だけなら f32 一本（帯 90px で 121 万標本 =
4.9MB）で済む。器は走査範囲から決まる数ちょうどに確保する。分位も完全整列では
なく `select_nth_unstable` で必要な順位だけ確定させる。12MP での追加コストは
17ms（全体の 2%）で、ピーク RSS は計測を外しても動かない。

帯を横切るだけの商品なら p50 も p90 も動かない。輪郭は曲線なので帯の面積に対して
1 次元でしか効かず、商品の内側は一様で勾配を下げるためである。帯の 1 辺が
まるごと商品になっても、上で見たとおり p50 は動かない。逆に **外周まで織り目で
埋まった商品**（畳んだ布そのものを撮る等）は区別できない。その場合は
`--edge-threshold` を明示する。

#### その他の補助手段

- **前景シード指定**: `--fg-seed x,y` で「ここは絶対に商品」を指定して保護する。
  半径 5px の円を前景として固定し、フラッドフィルの侵入を防ぐ。
  種の色から領域を推定して救い出す方式は、種が背景と同色だった場合に背景全体を
  巻き込む危険があるため採らない。挙動が予測できることを優先している

#### 堤防だけでは足りない（フィルの 3 段化）

堤防は「勾配がしきい値を超える画素には入らない」という規則なので、
**局所的にコントラストが足りない場所が 1 箇所でもあればそこから内部へ流れ込む**。
商品の内部は一様なので、入られたら許容量いっぱいまで削られる。連結性以外に
守りが無いのが問題だった。実測では、輪郭のコントラストが ΔE 9.5 の淡色商品で
境界近傍の 61.9% が消えた。

さらに Sobel の勾配は輪郭の**両側**に立つため、背景側の画素まで背景候補から外れ、
前景の外に「色は完全に背景だが不透明」という 1px の縁が残っていた。

**解はフィルを 3 段に分けることにある（ヒステリシス）。**

1. **芯** — 厳しい許容量 `core_tolerance` で、外周（または bbox の縁）から届く
   範囲だけを塗る。値は外周 ΔE の p90 の 2 倍を基準に、下限 1.0・上限
   `tolerance/3` で決める。CLI では公開しない。「どこまでを背景と言い切れるか」は
   画像ごとに違い、その答えは外周の分布が持っているためである。ただし
   `tolerance` は決して超えない（`--tolerance 0` を芯が破らないため）
2. **拡張** — 芯から `tolerance` の範囲へ広げる。ただし 1px あたりの色差が
   `--step-tolerance`（既定 2.2）以下の滑らかな経路でしか進めない。
   **芯に入れる色の画素は段差の検査を免除する。** 背景と言い切れる色である以上、
   JPEG のブロックノイズで隣と段差があっても背景であることに変わりはなく、
   この免除があるおかげで `step_tolerance` を小さく取っても背景が残らない
3. **影** — 4.4 を参照

段差の検査は 1px の色差だけでは足りない。落ち影の裾は最も急なところで 1px あたり
ΔE 1.9 変化し、淡色商品の輪郭（総コントラスト ΔE 3.6）はアンチエイリアスで 2px に
広がると 1px あたり ΔE 1.8 になる。**数値が同じ以上、片方だけを止めるしきい値は
存在しない。** そこで進行方向の 1px 先・2px 先を覗き、そこで続いている変化量と
比べる。落ち影は裾から芯まで変化し続けるのに対し、商品の輪郭は 1-2px で終わって
一様な面に入る。この違いだけが両者を分ける。

進行方向の先を覗く都合上、**画像の端から 2px の帯では段差の検査が働かない**。
先が画像の外に出る向きでは「いくらでも変化が続いている」とみなして検査を見送る。
端で止めると、見切れた商品の周りに背景が残るほうが害が大きいためである。

堤防そのものも非極大抑制で 1px の稜線に細めた。稜線が 1px でも斜めにつながって
いれば 4 近傍のフィルは越えられないので、堤防としての働きは失われない。これにより
停止位置が 1px 外側へずれる副作用は解消した（S1 の境界ずれは ±0.00px）。

#### 狭い隙間からの浸水の遮断

3 段に分けても、輪郭の破れをゼロにはできない。破れは圧縮ノイズや微細な傷で生じ、
通路は必ず細い。そこで**フィル後の背景を k px 収縮し、外周に連結する成分だけ残して
k px 膨張させ、元の背景マスクと交差させる**（測地的オープニング）。幅 2k 以下の
隙間を通ってしか外周につながらない領域は前景へ戻る。

既定の k=1 は、1-2px の破れからの浸水を止めつつ、取っ手の内側のような正当な隙間を
塞がない幅である。収縮の芯が取れなくても外周に接する背景は残す。商品が画面いっぱいに
写り背景が 1px の縁しかない場合に、その縁まで前景へ塗り替えないためである。

**収縮に掛ける前に、堤防が食べた分を戻す。** 堤防は隙間の両側を 1px ずつ背景候補から
外すので、そのままだと物理的に 3px ある通路が背景マスクの上では 1px になり、半径 1 の
収縮で消えてしまう。実効の封鎖幅が `2k` ではなく `2k+2` になり、「幅 2k px 以下」という
約束と食い違っていた（櫛状の合成シーンでの実測: 隙間 1px 抜け 5%、2px 6%、3px 7%、
4px 100%）。戻すのは「色だけで見れば背景に十分近く、かつ背景に隣接している」画素に
限る。堤防で外された背景色の画素はこれに当たるが、輪郭そのもの（商品の色をした画素）は
当たらないので、1px の破れは通路が広がらず従来どおり塞がる。戻した分は収縮の入力にしか
使わず、最後に元の背景マスクと交差させるので、出力に背景が増えることもない。

#### 実測（合成シーン、既定値）

`eaten` は境界の内側 6px 帯のうち削れた画素の割合、`影残存` は落ち影のうち前景として
残った割合。`cargo test --release --test edge_quality -- --ignored --nocapture` で
再現できる。

| シーン | eaten | 影残存 |
|---|---|---|
| S1 濃色商品 / 白背景 / JPEG q90 | 0.0% → 0.0% | — |
| S2 同上 PNG | 0.0% → 0.0% | — |
| S3 淡色商品（輪郭 ΔE 9.5） | 61.9% → **1.9%** | — |
| S4 8px で溶ける輪郭 | 0.0% → 0.0% | — |
| S5 / S5b ストラップ | 残存 100% → 100% | — |
| S6 落ち影 | 0.0% → 0.0% | 55.9% → **0.0%** |
| S7 中間グレー商品 + 影 | 0.0% → 0.0% | 62.6% → **7.0%** |
| S8 黒商品 + 影 | 0.0% → 0.0% | 49.6% → **0.0%** |
| S9 明度が背景を横切る淡色商品 | 61.9% → 66.1%（未解決、4.5） | — |
| S11 織り目のある背景 | 0.0% | — |
| S12 織り目のある背景 + 淡色商品 | 0.0%（堤防を切ると 100%） | — |

alphaMAE・rim・ハロー・境界ずれは S1/S2/S4/S5/S5b で変わっていない。

12MP（3000x4000・既定オプション・`/usr/bin/time -l`・Apple M4 Pro）の実測は
**780ms / ピーク RSS 311MB**（3 回の中央値。1MP なら 60ms / 28MB）。

**内訳は足し算では書かない。** 段ごとの境界は綺麗に切れておらず、以前ここに
並べていた「679ms + 82ms + 15ms」は合計と合っていなかった。代わりに、切り離して
測れるものだけを挙げる。外周のテクスチャ計測（4.3）は `estimate_background` 全体で
17ms、全体の 2% にあたる。ピーク RSS は計測を外しても 311MB のままで動かない
（帯の標本は 4.9MB で、ピークを作る画素ごとの表と生存期間が重ならないため）。

**メモリは意図して抑えている。** 素直に書くと 12MP では画素ごとの表が積み上がって
569MB に達し、`batch` は既定で CPU 数ぶん並列に走るので 10 コアの機械では 5.7GB を
要求することになる。そこで、稜線は真偽値 1 本（12MB）、Lab は 1/256 刻みの固定小数
（72MB、刻みは判定のしきい値より 3 桁小さい）、画素の素性は 1 バイトのフラグ 1 本
（12MB）に畳み、稜線と Lab の表は生存期間が重ならないように作る順序を決めてある。

### 4.4 影の扱い

**落ち影は背景として消す。** EC用途では商品単体の切り抜きが求められることが多く、
複数商品の見た目も揃うため。`--shadow-tolerance 0` で残せる。

かつては `--tolerance` を広めに取ることで影も飲み込む設計だったが、これは成立して
いなかった。影の濃い部分は ΔE 20-30 あり、そこまで許容量を広げると淡い色の商品が
まるごと消える。実測では tolerance 12 で影の 55.9% が商品の直下に残っていた。

**解は専用の判定を置くことにある。** Lab で背景との彩度差が小さく
（a\*b\* 平面での距離が 4 以下）、明度だけが低い（0 < L\* の落ち込み ≤
`--shadow-tolerance`、既定 35）画素を影候補とする。無彩色の面に落ちた影は光量だけが
減るので彩度がほとんど動かない、という物理から来ている。茶色い革や紺の布は彩度が
動くので取り違えない。

影候補はフィルの第 3 段でのみ吸収され、第 2 段と同じ段差の検査を通る。中間グレーや
黒の商品も「背景より暗い無彩色」なので条件だけなら影候補になるが、輪郭の段差で
フィルが止まるため消えない。

第 3 段だけは堤防を適用しない。Sobel は一定の傾斜に対して 1px あたりの変化量の
**2 倍**を返す（中央差分を 2px の間隔で取るため）。落ち影の裾は 8bit へ量子化されると
1px あたり 5-6 の階段になり、勾配としては 10 前後と報告される。既定のしきい値 8 では
商品の輪郭と区別がつかず、実測で影の 28.8% が取り残された。代わりに**第 2 段の背景
からの測地距離**で進める範囲を切る（画像の短辺の 1/24、最低 16px）。落ち影は物理的に
数十 px で背景色へ戻るのに対し、輪郭の破れからの浸水は商品が続く限りどこまでも進む。
距離を切ることで、判定を誤ったときの被害を輪郭沿いの数十 px に閉じ込められる。
比例だけでは 3000px 級の素材で 125px まで伸びてしまうので、上限 64px を置く
（2400px の無彩色商品で商品の 2.4% が削れていた）。

**背景より明るい反射は対象外とする。** グレー背景での映り込みや光沢は明度が上がる
方向に出るが、それを影と同じ規則で飲み込むと白背景の白い商品のハイライトまで消える。
明るい映り込みは `--bbox` で範囲を切って対処する。

### 4.5 既知の限界

- **輪郭のコントラストが ΔE 9 を下回ると守れない。** 落ち影の裾（1px あたり ΔE 1.9）と
  区別できないためである。角の丸みや JPEG の滲みで段差が 3-5px に広がると、
  1px あたりの変化量はさらに下がるので、この下限は上がる
- **商品の明度が背景色を横切る場合は解けない。** 上を明るく照らされた淡色商品は、
  明度が変化する途中で背景と完全に同じ色になる行を持つ。そこには色の手がかりが
  1bit も無く、いったん入られると商品の内部は一様なのでフィルが広がる。
  合成シーン S9 で境界近傍の 66% が削れる
- 背景と商品が同色で、かつ商品が画像外周に接している場合は分離できない
- 商品と背景の色差が小さい（ΔE 6 程度）場合、境界のアルファを色から決められず
  幾何的フェザーに落ちる。堤防も商品の内側で止まるため縁が削れる
- 幅 1px の構造（髪の毛、ワイヤー、細い罫線）ではアルファを決められない。
  4.7 の推定は「近傍に被覆率 1 の画素がある」ことを前提にするが、1px の構造には
  それが存在しないので、半分だけ覆った線と、完全に覆った薄い色の線を区別できない。
  帯そのものは張るので周囲の画素は色から決め直されるが、線の上は不透明のまま残る
- 背景より明るい映り込み（グレー背景の光沢）は影の判定の対象外
- **外周まで織り目で埋まった商品**（畳んだ布そのものを撮る等）では、背景の
  テクスチャと商品のテクスチャを区別できない。帯の半分以上が商品になると p50 も
  上がるので、堤防が不必要に引き上がる。`--edge-threshold` を明示すること（4.3）
- **無彩色の商品を、柔らかい輪郭（8px 級）で、高解像度で撮ると影に食われる。**
  中間グレーは「背景より暗い無彩色」そのもので、影の条件を満たしてしまう。
  柔らかい輪郭は堤防にも段差の検査にも引っかからないので、影の段はそこを
  通り抜ける。進める距離の上限（64px）で被害は抑えるが消えず、2400px の
  合成シーンで商品の 5.4% が削れる（上限が無いと 9.5%）。
  `--shadow-tolerance 0` で影の判定を切れば 0% になる
- 半透明な商品（ガラス瓶、透明パッケージ）は正しく扱えない
- グラデーション背景は `uniformity` が下がり、精度が落ちる

これらは `--json` の `warnings` で明示し、AI側が検知できるようにする。
いずれも `--bbox` や `--fg-seed` で範囲を教えれば救済できる。

### 4.6 孤立ノイズは太さではなく面積で消す

当初はオープニング（収縮 → 膨張）で孤立点を消していた。しかしオープニングは
**構造要素より細いものをすべて消す**。半径 2 のオープニングは幅 5px 未満の構造を
無条件に落とすため、ストラップ・持ち手・ケーブルといった商品の一部を巻き添えにする。

孤立点と細い構造を分けているのは太さではなく面積なので、連結成分の面積で選ぶ。
連結は 8 近傍で見る。4 近傍だと斜めに走る 1px の構造が細切れになり、面積で判定した
途端にすべて消えてしまうためである。

**面積の下限は解像度に比例させる。** 当初は `(2*cleanup+1)^2` の固定値にしていた。
「面積で判定するなら長辺に比例させる動機は消える」と考えたためだが、これは実写で
覆った。**ゴミの大きさそのものが解像度に比例する。** 同じ被写体を 4 倍で撮れば、
同じ大きさに見えるゴミは 16 倍の画素を占める。20MP の不織布では織り目の 1 粒が
150px² あり、固定の 25px² では一つも消えなかった。

そこで `--cleanup` を「**長辺 1000px 換算での半径 px**」と読み替え、下限を
`(2*cleanup+1)^2 * (長辺/1000)^2` とする。長辺 1000px 以下では倍率を 1 に留める。
そこを下回るのはサムネイルやテストの合成画像であり、既に妥当な値で運用されて
いるものを動かす理由が無いためである。実写（長辺 5712px）の既定 `--cleanup 2` は
面積 816px² に相当し、`--cleanup 8`（旧換算で 289px²）を手で渡していたのと
同じ効果が既定で得られる。

合成シーン S1-S10（400〜1600px）の指標はこの変更で一切動かない。1600px の S10 で
下限は 25 から 64 へ上がるが、そこに該当する大きさの成分がそもそも存在しない。

**上限は 64 に置く**（`MAX_CLEANUP`。`batch` の spec も同じ関門を通す）。換算値
64 は面積 16,641px²、20MP なら 54 万px² にあたり、これを超えると商品そのものが
「孤立ノイズ」になる。消す道具ではなく全消しの道具になってしまう。入口で断つのは
意味の話だけでなく、`2 * cleanup + 1` が `u32::MAX` 付近で溢れるのを防ぐためでもある。

**換算値をそのまま実寸の距離として使わない。** 境界の色差（`separability`）を
測るときの探索深さは「前景の外側に残る背景色の縁を跨げるだけ」で決めるが、
ここに換算値を足すと 20MP で実寸 13px 相当のものを 2px として扱うことになり、
高解像度ほど縁を跨げなくなる。面積の下限から実効半径を逆算した
`morphology::speck_radius` を使う。

面積フィルタは 2 回掛ける。1 回目は境界帯の推定をノイズの一つ一つに走らせないため、
2 回目は**堤防が成分を 1px ほど太らせるため**である。3x3 のゴミは堤防のせいで 5x5 に
見え、面積 25 の下限をちょうど超えて生き残る。帯の推定で縁が透明へ戻った後が、
成分の大きさを正しく測れる唯一のタイミングになる。

クロージング（穴埋め）はパイプラインから外した。前景は「外周から到達できなかった
領域」として定義されるので、到達できない穴はそもそも前景になっている。残るのは
細い隙間を通って外周とつながった領域だけで、それを埋めるのは形の改変にあたる。
穴を埋める効果より、商品の隙間（取っ手の内側など）を塞ぐ害のほうが大きい。

### 4.7 境界のアルファは形ではなく色から決める

フィルが返すのは 0/255 の二値マスクである。ここに階調を与えるのにマスクをぼかす
（フェザリング）のは筋が悪い。**それはマスクの形から作ったアルファであって、画像に
写っている本当のエッジ位置とは無関係**だからである。実測で 2 つの破綻が出た。

1. 堤防が残す 1px の縁は色が完全に背景なので、半透明にしても復元式
   `F = (C - (1-a)B) / a` は背景色を返す。白い下地では気づかないが、黒地に載せると
   輪郭が光る（黒地合成での輝度 55.7）
2. 8px かけて背景へ溶ける輪郭では堤防が混色のかなり背景寄りで止まるため、
   遷移全体がほぼ不透明のまま残る（アルファ誤差 0.50、境界位置が 5px 外側）

**解は合成式そのものを解くことにある。** 境界に帯を張り、帯の各画素で近傍の
確定前景色 F と確定背景色 B を集め、観測色 C を F–B 直線へ射影する。

```text
a = clamp( (C-B)・(F-B) / |F-B|^2 , 0, 1 )
F̂ = B + (C-B) / max(a, 0.05)
```

計算は線形 RGB で行う。合成は光の量の足し算であり、ガンマの掛かった sRGB 値のままでは
混色が直線に乗らないためである。`F̂` は局所前景色と観測色が挟む範囲へクランプする。
`a` が小さいところで誤差が何十倍にも増幅されるのを抑えるためで、これがないと
ほぼ透明な画素の色が飛ぶ。デスパイルは別処理ではなく、同じ推定の裏返しになった。

帯の幅は輪郭ごとに測る。境界画素から法線方向に外へ進んで色が背景に収束（ΔE<2）する
距離と、内へ進んで商品色に収束する距離の大きいほう（下限 2px、上限 10px）を採る。
くっきりした輪郭に広い帯を張れば商品の内側まで巻き込み、柔らかい輪郭に狭い帯では
遷移を跨げない。収束の参照色に大域の背景色ではなく「その方向で実際に観測される色」を
使うのは、落ち影や照明ムラのある場所で永久に収束せず帯が最大幅に張り付くのを
避けるためである。

帯が構造そのものより太い場合（幅 3px のストラップなど）、確定前景が 1 画素も
取れない。そのときは窓の中でマスクに入っている画素のうち背景から最も遠い色を
前景の代わりにする。遠くの本体から F を持ってくると、そこだけハローが残る。

F と B の色差が小さい画素（線形 RGB のユークリッド距離で 0.06 未満）では、この射影は
雑音を拾うだけで何も決められない。そこだけ従来の幾何的フェザーへ落とす。淡い色の
商品を色で分離できないのはアルゴリズムの限界であって、境界処理で解ける問題ではない。

合成画像（真の被覆率が解析的に分かるもの）での実測:

| シーン | アルファ誤差 | 背景色のまま不透明な縁 | 黒地ハロー輝度 | 境界位置 |
|---|---|---|---|---|
| 濃色商品 / 白背景 / JPEG q90 | 0.189 → 0.007 | 12.2% → 0.0% | 55.7 → 0.6 | +1.0px → 0.0px |
| 8px で溶ける輪郭 | 0.502 → 0.139 | 42.7% → 0.0% | — | +5.0px → +1.0px |
| 3px のストラップ（堤防なし） | 残存 2% → 100% | | | |

所要時間は画像の面積ではなく、**帯の面積（周長 × 帯幅）** で決まる。滑らかな
シルエットなら帯は輪郭に沿った細いリングでしかないが、メッシュ・レース・ニット・
ワイヤーラック・文字のように構造が帯より細い素材では帯が面ごと埋まり、桁が変わる。

12MP（3000x4000）での追加コスト（`--no-refine` との差）は**形状によって桁が
変わる**。角丸矩形のような滑らかなシルエットなら数十 ms、帯が面ごと埋まる
櫛状 6px 周期でも 1 秒未満に収まる。絶対値の表は載せない。同じ機械でも
`--no-refine` 側の実測が倍近く振れるため、形状どうしの順序すら再現しないためである。
数字が要るなら下の計測テストをその場で回すこと。

窓の合計は積分画像から O(1) で引く。帯画素ごとに窓を全走査すると計算量が
「帯の面積 × 窓²」になり、櫛状では数秒の桁に膨らんだ。全面の積分画像は
8 面 × 12MP × f64 で 768MB になって持てないので、帯の周りをタイル(128px)に切り、
タイルごとに「帯の外接矩形 + 窓の余白」だけを覆う局所の積分画像を作り直している。

計測は `cargo test --release --test edge_quality -- --ignored --nocapture` で
再現できる。CI では同じ形の小さい画像で、`--no-refine` との時間比に緩い上限を
置いた回帰テスト（`refine_does_not_scale_with_the_area_of_the_window`）が走る。
絶対時間は機械によって何倍も違うが、比なら安定して崩れを検出できる。

## 5. CLI 設計

### 5.1 コマンド体系

ハイブリッド方式を採る。`cutout` が切り抜きからリサイズ・キャンバス配置・形式変換までを内包し、1回の呼び出しで完結する（AIが中間ファイルの後始末を忘れる問題を回避するため）。加えて切り抜き不要なケース向けに `resize` / `convert` を用意する。

```
kiri info    <input>                    画像情報と背景推定を JSON で返す
kiri cutout  <input> -o <output> [...]  切り抜き（全部入り）
kiri resize  <input> -o <output> [...]  リサイズのみ
kiri convert <input> -o <output> [...]  形式変換のみ
kiri batch   <spec.json>                仕様ファイルによる一括処理
```

### 5.2 cutout

```
kiri cutout in.jpg -o out.avif \
  [--bbox x1,y1,x2,y2] [--normalized] [--fg-seed x,y] \
  [--tolerance 12] [--edge-threshold 8|auto] [--step-tolerance 2.2] \
  [--shadow-tolerance 35] [--seal 1] \
  [--cleanup 2] [--feather 1] [--no-refine] [--no-despill] \
  [--canvas 1000x1000] [--fill-ratio 0.85] \
  [--background "#FFFFFF"] \
  [--quality 75] [--effort 6] \
  [--json] [--debug-mask mask.png] [--force]
```

**bbox は任意**。未指定なら全自動で切り抜く。指定された場合はその外側を強制的に透明化する。これによりバッチ処理が本命の使い方になり、AIは「全件の座標を出す」のではなく「失敗した数枚だけ救済する」役割を担う。

座標は左上原点のピクセル値 `x1,y1,x2,y2`。`--normalized` を付けると 0〜1 の正規化座標として解釈する（ビジョンモデルは正規化座標を返すことが多いため）。

`--edge-threshold` は**「未指定」と「8 を明示」を区別する**。未指定なら背景のテクスチャに応じて引き上がり（4.3）、明示すればその値に従う。同じ区別を `batch` の spec キーにも持たせている。

### 5.3 info

AIが座標を出す前に画像の寸法を知る必要があるため必須のコマンド。

```json
{
  "width": 2400, "height": 3200, "format": "jpeg",
  "exif_orientation": 6,
  "color_space": "Display P3", "color_converted": true, "icc_profile": true,
  "background": {
    "rgb": [248, 248, 247], "uniformity": 0.97,
    "perimeter_delta_e": { "p50": 0.4, "p90": 1.2, "max": 2.8 },
    "texture": { "p50": 0.0, "p90": 1.0 }
  },
  "warnings": []
}
```

`uniformity` により、AI側が「この画像は単色背景なので処理可能」「複雑背景なので非対応」を事前判断できる。`texture` は別の軸で、**背景がざらついていないか**を言う。`p50` が `edge_threshold`（既定 8）に達していれば、その背景は堤防を張れない素材である（4.3）。`p90` だけが高い場合は背景ではなく、**帯に写り込んだ物**（画面の端で見切れた柄物の商品など）を指している。

### 5.4 batch

「AIが画像ごとに座標を出す」設計はバッチと本質的に相性が悪い（画像ごとに引数が異なる）。JSON仕様ファイルを流し込む形で解決する。AIはJSONの生成が得意なため、これが最もAIネイティブな形になる。

```json
{
  "defaults": { "canvas": "1000x1000", "fill_ratio": 0.85, "format": "avif" },
  "items": [
    { "input": "a.jpg", "output": "a.avif" },
    { "input": "b.jpg", "output": "b.avif", "bbox": [200, 150, 1100, 1600] }
  ]
}
```

`rayon` で並列実行する。結果の並びは仕様ファイルの順序を保つ。

**1 件の失敗で全体を止めない。** 数百点を回すバッチでは、失敗した項目を報告しつつ
残りを処理し切るほうが有用であるため。失敗があった場合は終了コード 4 で知らせ、
詳細は `results[]` の各項目に入れる。

**仕様の誤りは黙って無視しない。** 綴り違いのキーはエラーとし、編集距離から候補を
提示する。無視すると「指定したはずの設定が効いていない」という最も気づきにくい
失敗を生むため。serde の `flatten` は `deny_unknown_fields` と併用できないので、
キーの検証は自前で行っている。

相対パスは既定で**仕様ファイルのある場所**を基準に解決する。AI は画像の隣に仕様を
書き出すのが自然であり、実行時のカレントディレクトリに依存しないほうが再現性が
高いため。`--base-dir` で上書きできる。

### 5.5 共通規約

- **stdout は JSON のみ**、ログと進捗は全て stderr に出す
- **デフォルト非破壊**。既存ファイルの上書きは `--force` を必須とする
- **メタデータはデフォルトで除去**（`--keep-metadata` でオプトイン）。Web配信ではサイズと個人情報の両面で不要
- **リサイズは既定で拡大禁止**（`--allow-upscale` でオプトイン）。素材を勝手に拡大してぼかす事故を防ぐ
- **色空間**: 埋め込み ICC を既定で sRGB へ変換する（`--no-color-convert` でオプトアウト、`batch` では `color_convert`）。変換の範囲と根拠は 3.5 を参照

### 5.8 キャンバス配置

`--canvas WxH` で、切り抜いた商品を指定サイズの中央に配置する。`--fill-ratio` は
商品がキャンバスの何割を占めるかを決め、既定は 0.85（EC プラットフォームで広く
求められる占有率）。

配置の手順は、マスクのアルファが 0 を超える範囲で商品を切り詰め、占有率の枠に
収まる倍率で拡縮し、中央に合成する。切り詰めに前景判定(128以上)ではなく
アルファ 0 超を使うのは、フェザリングされた薄い縁を落とさないため。

余白は既定で透明。`--flatten` を付けると `--background` の色で塗り潰す。
これにより透過 PNG が使えないプラットフォーム向けの白背景 JPEG も同じ経路で出せる。

**キャンバス配置では拡大を禁止しない**（`resize` とは扱いが異なる）。`resize` では
利用者が出力寸法そのものを指定しているためエラーが妥当だが、キャンバス配置では
指定しているのは枠であり、拡縮はその結果として決まる。要求を満たすために必要な
拡大まで拒否するのは筋が悪い。代わりに倍率を添えて警告し、`--json` の
`canvas.scale` でも確認できるようにしている。

### 5.9 リサイズの当てはめ方

`--width` / `--height` の一方だけを指定した場合はアスペクト比を保つ。両方指定した場合は
`--fit` が挙動を決める。

| `--fit` | 挙動 |
|---|---|
| `contain`（既定） | 枠に収まるよう縮小する。結果は枠以下 |
| `cover` | 枠を覆うよう縮小し、はみ出しを中央で切り取る。結果は枠ちょうど |
| `exact` | アスペクト比を無視して枠ちょうどに変形する |

**拡大は既定で拒否し、エラーとする**（`--allow-upscale` でオプトイン）。黙って縮小に
倒すと出力寸法が要求と食い違い、バッチ処理でそれに気づけないため。エラーであれば
AI エージェントが `--allow-upscale` を付けるか元素材を見直すかを判断できる。

補間は Lanczos3。透過画像は事前乗算つきで補間する。これを怠ると切り抜き済み画像の
境界に背景色がにじむ。

### 5.6 JSON 出力

処理結果には「実際に何が起きたか」を含める。AIが結果を検証して次の手を打てるようにするため。

```json
{
  "input": "in.jpg", "outputs": [{ "path": "out.avif", "bytes": 31200 }],
  "source": { "width": 2400, "height": 3200 },
  "color_space": "Display P3", "color_converted": true,
  "mask": {
    "foreground_ratio": 0.34,
    "bbox": [130, 95, 880, 1380],
    "touches_edge": false,
    "holes_filled": 3
  },
  "background": {
    "rgb": [248, 248, 247], "uniformity": 0.97,
    "perimeter_delta_e": { "p50": 0.4, "p90": 1.2, "max": 2.8 },
    "texture": { "p50": 0.0, "p90": 1.0 }
  },
  "settings": {
    "tolerance": 12, "edge_threshold": 8,
    "step_tolerance": 2.2, "shadow_tolerance": 35, "seal": 1,
    "cleanup": 2, "feather": 1, "despill": true, "refine": true
  },
  "elapsed_ms": 142,
  "warnings": []
}
```

`foreground_ratio` が極端な値（0.02 や 0.98）であれば失敗を検知でき、`touches_edge` は商品の見切れを示す。

ただし `foreground_ratio` は「どれだけ残ったか」しか言わず、その輪郭が妥当かを語らない。そこで `mask.separability`（切り抜き境界の内側で測った商品と背景の色差）と `background.perimeter_delta_e`（外周の色差の分布）を併せて返す。

`background.texture`（外周の帯で測った勾配の分位）は、`perimeter_delta_e` では区別できないものを言う。**なだらかな照明ムラとざらついた織り目は、背景色からの色差では同じ値になる。** 前者は `--tolerance` で吸収できるが、後者は堤防を誤発火させてフィルを止める。分けられるのは 1px あたりの変化量だけである。

`settings` には**実際に効いた**設定を並べる。結果が期待と違ったとき、指定が効いたのか既定のまま走ったのかは画像を見ても分からない。バッチでは `defaults` と項目の継承が絡むぶん、なおさら結果側に答えが要る。`edge_threshold` は背景のテクスチャに応じて自動で引き上がることがあるので（4.3）、指定値ではなく**引き上げ後の値**が入り、`warnings` に理由と根拠の数値が 1 行出る。**黙って設定を変えるのは、指定が無視されるのと同じくらい追いにくい失敗である。**

`separability` は境界の**内側**を測るため、前景の外側に張り付いた背景色の縁を検出できない。そこで縁そのものを測る `mask.halo_ratio`（境界近傍で不透明なのに、元画素の色が局所背景と ΔE≤3 の画素の割合）と、境界の階調を測る `mask.edge_width`（アルファが 0.9 から 0.1 へ落ちるまでの幅の中央値 px）を加える。

- `halo_ratio` が 0.10 を超えると警告する。この縁は白背景では見えず、納品先が黒や色付きの下地だったときに初めて輪郭の光として現れる。**書き出しの時点で知らせなければ、エージェントは検証しようがない**
- 診断はデスパイル後ではなく**元画像**で測る。デスパイル後の画像では「背景色を消したから縁が見えなくなった」だけの状態を good と誤判定する

- `separability` が `perimeter_delta_e.p50` を下回るなら、背景を飲み込める tolerance は商品も飲み込む。**両立する値が存在しないため、パラメータ調整では改善しない。** この判定を返すことで、AIが無駄な再試行ループに入るのを防ぐ
- しきい値を定数で置かず背景自身のばらつきと比べるのは、「どこまで許容すべきか」が画像ごとに違うため。均一な背景では `p50` がほぼ 0 になるので、白背景×白商品の看板ケースでは発火しない

数値で判断できない場合に備えて `--preview` を持つ。原寸の出力（数千px・数十MB）は視覚モデルに渡せないため、「元画像 | マスク | 結果」を1枚に並べた小さな画像を書き出す。外部ツールを挟まずに完結させるのは、依存ゼロという前提を崩さないためである。3面に分けるのは、結果だけを見ても失敗の原因が分からないためである。

### 5.7 exit code

| コード | 意味 |
|---|---|
| 0 | 成功 |
| 1 | 一般エラー |
| 2 | 引数不正 |
| 3 | 入力ファイル異常（存在しない、破損、非対応形式） |
| 4 | 処理失敗（背景を検出できない等） |

エラー時も `--json` 指定時は JSON で返す。

```json
{ "error": { "code": "BACKGROUND_NOT_UNIFORM", "message": "...", "hint": "..." } }
```

## 6. AIエージェントとの分担

| 担当 | 役割 |
|---|---|
| **AI** | 意味理解。どれが商品か、どこにあるか。結果JSONの検証と、失敗画像の救済 |
| **kiri** | 画素処理。背景色推定、輪郭の確定、整形、エンコード |

AIに輪郭のポリゴン頂点列を出させる案は採らない。ビジョンモデルは bbox はそこそこ出せるが、輪郭を数十点で正確になぞるのは苦手で、フラッドフィルより精度が落ちるため。

想定される典型的なループ:

1. AIが `kiri batch` で全件を自動処理
2. 結果JSONの `foreground_ratio` や `warnings` を見て失敗を検出
3. 失敗した画像だけ `kiri info` で確認し、`--bbox` や `--tolerance` を調整して再実行
4. それでも直らない画像は `kiri cutout --preview` で目視して判断する

3 までは画像を開かずに回ることを前提とする。4 は救済フェーズの道具であり、`batch` は既定でプレビューを書き出さない。数百点を回す通常の経路で全件の画像を吐けば無駄なI/Oになるためである。

## 7. 未決事項 / v2以降の候補

- LUT 型 ICC の解釈（現状は警告して sRGB 扱い）。稀な入稿素材でしか効かないため優先度は低い
- HEIC 入力（pure Rust の HEVC デコーダが現れたら再検討する）
- グラデーション背景への対応（局所適応しきい値）
- 半透明商品の扱い
- `AlphaColorMode::UnassociatedClean` によるファイルサイズ削減の検証
- crates.io への公開名（`kiri` は既存クレートに取られている。`kiri-cli` + `[[bin]] name = "kiri"` が有力）

## 8. 主要な決定と根拠

| 決定 | 根拠 |
|---|---|
| Rust / pure Rust（C依存なし） | 単一バイナリ配布、クロスコンパイルの容易さ、OSS採用障壁の低減 |
| WebP 非対応 | 実用的なロッシー圧縮に libwebp（C）が必要 |
| HEIC 入力 非対応（ただし手順を返す） | HEVC デコーダが pure Rust に無い。読めない事実より、原因が分からないメッセージのほうが害が大きいため |
| ICC は行列 + TRC 型だけ解釈する | 実写で問題になる Display P3 と AdobeRGB がこの型に収まり、LUT 型まで背負うと得るものに対してバグの入る面積が大きすぎるため |
| 色変換を既定で有効にする | iPhone 素材が Display P3 で入るのが常態で、素通しは彩度の誇張として必ず出るため |
| sRGB 相当は変換しない | 往復の丸め誤差を足すだけで、既存素材の出力バイト列を動かす理由が無いため |
| 白色順応に Bradford / 相対比色 | PCS が D50 で sRGB が D65 なので順応は必須。EC では白を白に保つことが最優先で、知覚的インテントに必要な LUT は解釈対象外であるため |
| AVIF をデフォルト出力 | pure Rust で実装でき、実測で 1MP/57ms と実用速度。透過の扱いも良好 |
| 単色背景のみ対応 | MLモデルなしで品質を担保できる範囲に限定するため |
| 影は消す | EC用途では商品単体の切り抜きが求められることが多く、見た目も揃うため |
| フィルを 3 段に分ける | 堤防は 1 箇所の破れで内部まで浸水する。連結性以外の守りが要るため |
| 芯の許容量を利用者に見せない | 「どこまでを背景と言い切れるか」は画像ごとに違い、外周 ΔE の分布が答えを持つため |
| 段差の判定に「先の変化量」を使う | 落ち影の裾と淡い輪郭は 1px あたりの変化量が同じで、局所値だけでは分けられないため |
| 影を専用に判定する | 影は ΔE 20-30 あり、色の許容量を広げて飲み込もうとすると淡色商品も消えるため |
| 影の吸収を距離で切る | 影は数十 px で背景へ戻るが、輪郭の破れからの浸水は商品が続く限り進むため |
| 背景より明るい映り込みは消さない | 白背景の白い商品のハイライトと区別がつかないため |
| 測地的オープニングを掛ける | 破れをゼロにするより、細い通路を通った浸水を後から見分けるほうが確実なため |
| bbox は任意（自動が既定） | 単色背景限定により自動で大半が処理可能になり、バッチ処理が実用的になるため |
| EC整形機能を内蔵 | 切り抜きだけでは納品できない。実装コストが小さく実用価値が大きい |
| 診断値を結果に含める | `foreground_ratio` だけでは「輪郭が妥当か」が分からず、AIが直らない画像で再試行を繰り返すため |
| 判定を背景自身のばらつきと比べる | 許容できる色差は画像ごとに違い、定数のしきい値では実写で外れるため |
| 境界のアルファを色から推定する | マスクの形から作ったアルファは真のエッジ位置と無関係で、背景色の縁がそのまま残るため |
| アルファの計算を線形 RGB で行う | 合成は光の量の足し算であり、sRGB 値のままでは混色が直線に乗らないため |
| 孤立ノイズを面積で消す | オープニングは太さで消すため、細い商品の一部（ストラップ・ケーブル）を巻き添えにするため |
| 面積の下限を解像度に比例させる | ゴミの大きさ自体が解像度に比例し、固定値では 20MP の織り目（150px²）が消えないため |
| 背景のテクスチャで堤防を自動調整する | 布や段ボールは背景自身が 1px あたり十数の変化を持ち、堤防が背景の中で壁になるため |
| 発火は p50、引き上げ幅は p90 で決める | p90 だけでは「背景がざらついている」と「帯に見切れた柄物が写っている」を区別できず、後者で堤防が無意味な高さまで上がるため |
| 堤防を無効化ではなく引き上げにする | 織り目の上に載った淡い商品を守る役目を残すため。実測では引き上げでも無効化と同じ結果に達する |
| クロージングを外す | 外周から到達できない穴はそもそも前景であり、埋める対象が原理的に存在しないため |
| `halo_ratio` を返す | `separability` は境界の内側を測るので、外側に残った背景色の縁を検出できないため |
| プレビューを内蔵（外部ツールに任せない） | 原寸出力は視覚モデルに渡せず、縮小に外部ツールが要れば依存ゼロの前提が崩れるため |
