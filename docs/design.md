# kiri 設計ドキュメント

最終更新: 2026-09-06

## 1. 目的

AIエージェントから使われることを前提とした画像編集CLI。EC商品画像の背景透過切り抜き・整形・Web配信形式への変換を一貫して行う。

既存ツール（ImageMagick + rembg 等）との差別化は次の3点に置く。

- **依存ゼロ**: Python環境も外部ツールもMLモデルも不要。単一バイナリで動く
- **起動が速い**: AIエージェントは同じCLIを何度も呼び出す。起動に秒単位かかると体感を殺す
- **構造化I/Oと決定的動作**: 同じ入力に対して常に同じ出力。結果はJSONで返り、AIが次の判断に使える

## 2. スコープ

### 2.1 対象

- **単色背景**（白・グレー等のスタジオ撮影背景）のEC商品画像
- 背景透過切り抜き / リサイズ / キャンバス配置 / 形式変換

### 2.2 非対象（v1で明示的に切る）

| 項目 | 理由 |
|---|---|
| 複雑背景（生活シーン・屋外撮影） | 古典的画素処理では品質が出ない。MLモデルが必要になり pure Rust 方針と衝突する |
| 髪の毛レベルの精密マッティング | 要求は「輪郭レベル」で足りると判断 |
| WebP 出力 | 実用的なロッシー圧縮には libwebp（C）が必要 |
| AVIF 入力 | デコードに dav1d（C）が必要 |
| MCPサーバーモード | CLIに専念する |

非対象の画像に対しては `kiri info` の `background.uniformity` で事前に検知し、警告を返す。AI側が「この画像は非対応」と判断できるようにする。

## 3. 技術選定

### 3.1 依存方針

**pure Rust のみ。実行時に C のライブラリを引くクレートは採用しない。**

理由は3つ。単一バイナリで配布できること、クロスコンパイルが素直に通ること、そしてビルドの容易さがOSSの採用障壁を直接下げること。この方針が対応形式の選択（WebP非対応）を規定している。

検査できる形で言い直すと、**`cargo tree -e normal` に `*-sys` クレートが 1 つも現れない**
ことである。`-sys` クレートは C のライブラリに橋を架けるためだけに存在するので、
その不在がそのまま「実行時に C を引いていない」の証明になる。

#### 「C 依存が無い」はビルド時の話ではない

**ビルド中に C コンパイラが動くことはある。** `tract-linalg` は `build.rs` で `cc` を
呼び、arm64 / x86 の手書きアセンブリを組み込む。`rav1e`（AVIF）も同じ経路で `cc` を
使っており、**セグメンテーションを足す前から `cc` は依存に入っていた**ので、
Phase 5 が新しく持ち込んだ悪化ではない。

区別が要るのは、守りたいものが「配った 1 つのバイナリがどこでも動くこと」だからである。
`cc` はビルド機械に要るだけで、成果物には何も外部ライブラリを残さない。対して
`*-sys` は実行時に共有ライブラリを探しに行くか、少なくとも C のソースを抱え込む。
**前者は単一バイナリを壊さず、後者は壊す。**

#### 「ML なし」は手段であって目的ではない

1 節は「MLモデルも不要」と書いているが、**守りたかったのは C 依存なし・Python なし・
単一バイナリの 3 つ**である。pure Rust の推論エンジン（`tract-onnx`）を使えば
3 つとも守れるので、この禁止は目的を取り違えていた。Phase 5 でセグメンテーション
モデルを**任意の feature**として足したのはそのためで、3.6 に位置づけを書く。

**既定では 1 行も走らない。** モデルは別ファイルで、リポジトリにも配布物にも含めない。
取得していなければ従来どおり動く。

### 3.2 採用クレート

| クレート | バージョン | 用途 |
|---|---|---|
| `image` | 0.25 | JPEG/PNG のデコード、PNG/JPEG のエンコード |
| `ravif` | 0.13 | AVIF エンコード（内部で `rav1e` 0.8） |
| `fast_image_resize` | 6.1 | SIMD リサイズ（Lanczos3） |
| `kamadak-exif` | 0.6 | EXIF Orientation の読み取り |
| `clap` | 4.6 | CLI パーサ |
| `serde` / `serde_json` | 1.x | JSON 出力 |
| `rayon` | 1.x | バッチ処理の並列化 |

切り抜きアルゴリズムは全て自前実装する。ここがこのプロジェクトの本体である。

### 3.3 対応形式

- **入力**: JPEG, PNG
- **出力**: AVIF（既定）, PNG, JPEG。どの形式も sRGB を名乗る（PNG / JPEG は ICC、AVIF は AV1 の色情報。3.5 の末尾を参照）

入出力が非対称だが、用途（撮影素材を受け取ってWeb配信形式で出す）を考えれば問題にならない。

**HEIC / HEIF は入力にできない。** HEVC のデコーダは pure Rust に存在せず、libheif や
libde265（いずれもC）が必要になる。EC の入稿素材は iPhone 撮影が多く、そのまま渡せば
HEIC で来るため実害はあるが、依存ゼロの前提を崩すほどではないと判断した。

代わりに**先頭の `ftyp` ボックスを自前で見て、原因と変換手順を返す**。`image` に任せると
形式の判別自体に失敗して「拡張子から判別できません」に落ちる。原因が HEIC だと分からない
メッセージでは、AI エージェントは別の拡張子を試すような無駄な再試行に入るためである。
ヒントには macOS の `sips`（追加インストール不要）と、ImageMagick / libheif の例を載せる。

AVIF は入力としては同じ扱い（デコードに dav1d が要る）だが、出力としては pure Rust で
エンコードできるため既定の出力形式である。

### 3.4 AVIF エンコード実測結果

pure Rust での AVIF エンコードが実用速度に収まるかが唯一の技術的不確定要素だったため、実装前に計測した。

計測環境: Apple M4 Pro（14スレッド）、`ravif` 0.13.0 / `rav1e` 0.8.1、release ビルド

| 設定 | 1000×1000（1.0 MP） | 2400×3200（7.7 MP） |
|---|---|---|
| speed 10 / q75 | 29 ms | 203 ms |
| **speed 6 / q75** | **57 ms** | **459 ms** |
| speed 4 / q75 | 114 ms | 687 ms |
| speed 1 / q75 | 1,381 ms | 9,835 ms |
| speed 1 / q85 | 5,736 ms | 40,296 ms |
| PNG（比較） | 5 ms | 22 ms |

**判明したこと**

1. C依存なしでビルドが通る（依存クレート込みで23秒）
2. アルファチャンネルは正しく保持される。macOS のデコーダで検証したところ `hasAlpha: yes`、完全透明 52.2% / 不透明 47.2% / 中間値 0.67%。境界のアンチエイリアスも保たれている
3. `speed 6` が最適点。これより遅くしてもサイズ削減が時間に見合わない
4. `speed 1` は崖。7.7MP で40秒に達するため使わせない
5. ~~`quality` は 75 が境目。85 にするとサイズが約4倍に跳ねる~~
   **——Phase 26 の実写再計測で否定された。3.4.1 を見ること。**

**決定**: AVIF をデフォルト出力形式とする。既定値は ~~`quality 75`~~ / `speed 6`。`--quality` と `--effort` で調整可能にする。**`quality` の既定は Phase 26 で 90 へ改めた**（3.4.1）。`speed 6` は据え置き。

**この計測の限界**: テストに用いたのは合成画像で、実写より圧縮が効きすぎている（1MPで7KB）。**時間の数値は概ね代表的だが、ファイルサイズの絶対値は当てにならない。**実画像での再計測を実装フェーズで行うこと。

**実装時に検証すべき点**: 完全透明ピクセルにRGBデータが残っていた。`ravif` の `AlphaColorMode::UnassociatedClean` を指定すると透明部をクリーンにでき、透明領域が広い商品画像ではさらにサイズが縮む可能性がある。

#### 3.4.1 実写での再計測（Phase 26）

**上の「実画像での再計測を実装フェーズで行うこと」を、ここで回収する。** 宿題は
Phase 1〜25 を通って未回収のままだった。その間、既定 `quality 75` は**合成画像の
サイズ曲線から決まった値**として効き続けていた。

計測環境: Apple M4 Pro、release ビルド、kiri は Phase 25 完了時点。素材は 2 枚とも実写で、
`remote.jpg`（4284x5712）と `keyboard.jpg`（3024x4032）。**どちらも 4.12 の
「素材を固定する」の表にある SHA-256 と同じバイト列である**——実写の数値は素材の
バイト列に紐づくので、そこを外すと突き合わせられない。
PSNR は同じ経路で書いた PNG を基準にした。**リモコンは商品領域だけを測る**
（`canvas.offset` + `canvas.content` の矩形。画像の 24% しかなく、残りは純白なので
全面で測ると 42 dB に化ける）。キーボードは切り抜かずに全面。

| q | リモコン 商品領域 jpeg | キーボード 全面 jpeg | リモコン avif |
|---|---|---|---|
| 75 | 36.07 dB / 150 KB | 35.92 dB / 555 KB | 36.22 dB / 52 KB |
| 80 | 36.94 dB / 164 KB | 36.93 dB / 637 KB | 36.98 dB / 60 KB |
| 84 | 37.84 dB / 181 KB | 37.93 dB / 729 KB | 38.35 dB / 76 KB |
| 86 | 38.41 dB / 190 KB | 38.55 dB / 781 KB | 39.73 dB / 94 KB |
| 88 | 39.07 dB / 203 KB | 39.27 dB / 853 KB | 40.81 dB / 109 KB |
| **90** | **39.90 dB / 219 KB** | **40.14 dB / 940 KB** | **42.16 dB / 129 KB** |
| 92 | 40.95 dB / 238 KB | 41.24 dB / 1043 KB | 43.89 dB / 155 KB |
| 94 | 42.37 dB / 272 KB | 42.68 dB / 1227 KB | 46.03 dB / 191 KB |

**「85 で 4 倍」がなぜ外れたか。** 合成画像は 1MP で 7KB まで潰れる。そこまで潰れた
ものを基準にすると、少し情報が残るだけで比率が跳ね上がる。実写の周波数分布では
起きない——AVIF で 52 → 94 KB の 1.8 倍、キーボードでも 304 → 484 KB の 1.6 倍である。
**この外し方は次の較正の材料なので消さない**: 合成画像で決めてよいのは
「時間」と「設定どうしの相対」であって、**サイズの絶対値と、そこから導く境目ではない。**

**既定を 90 にした根拠は 3 本。**

1. 既定 75 の画質は商品領域で 36.07 dB。視覚的無損失の目安 40 dB に 4 dB 足りない。
   **単一の既定として 40 dB に最も近づくのは 90 である**——上の表で 40 dB に届く
   最小の q は測った 3 通りで 92 / 90 / 88 で、90 では 3 通りのうち 2 通りが届き、
   残る 1 通り（リモコンの商品領域 jpeg）も 39.90 dB と 0.10 dB 差にある。
   92 へ上げるとバイトが更に 8%（219 → 238 KB）増え、94 でも 42.37 dB に
   しかならないので、そこまでは払わない
2. kiri が純白に塗った背景に、自分のエンコーダがリンギングを乗せる。商品の外側 24px の
   帯のうち基準画像で純白だった画素だけを見ると、**q75 では最大 17 階調ずれる**
   （q90 で 11、q92 で 9）。偏差 5 超の画素は 0.37% → 0.13% へ減る。`kiri lint` の
   背景検査は外周の**中央値**を見るので合否には出ないが、拡大したときに「あらい」と
   見えるものの一部はこれである
3. 既定 75 の唯一の根拠（上の「4 倍」）が実写では成り立たない

**形式では分けない。** 同じ q でほぼ同じ PSNR が出る（AVIF がわずかに良い）ので分ける
理由が無く、分けると `kiri schema` が配る `--quality` の `default` が単一の数で表せなくなる。
「AVIF のサイズ曲線」を理由に JPEG まで 75 に縛るのも筋が通らない——**AVIF が「急増」した
先は JPEG より小さい**（q90 で AVIF 129 KB 対 JPEG 219 KB）。

**払うもの。** バイトは 1.5〜1.8 倍。時間はほぼ変わらない（12.2MP で AVIF 0.95 → 1.06 秒の
11% 増、JPEG 0.19 → 0.20 秒）。バイトを詰めたい実行には `--max-bytes` がある。

**梯子は 1 段も動かさない。** `QUALITY_LADDER`（85 / 75 / 65 / 55 / 45 / 35 / 25）は
「降りる先」の集合で、出発点が上がったことと段の位置は別の話である。変わったのは
**梯子の全体が要求品質より下に来た**ことで、既定から降りる段は 5 → 7、要求品質そのものを
入れたエンコード回数は 6 → 8 になる。既定が最上段 85 より上にあるので、**この 8 が
`--max-bytes` の上限でもある**（`--quality 100` でも 8 を超えない）。

### 3.5 色管理（埋め込み ICC → sRGB）

EC の入稿素材は iPhone 撮影が多く、Display P3 で入ってくる。これを sRGB として素通しすると
彩度の高い色ほど誇張されて出る。**「届いた商品が写真と違う」に直結するため、色変換は
品質の話ではなく正しさの話である。**

#### 対象を行列 + TRC 型に絞る

`lcms2` は C 実装なので使えない。自前で書くしかないが、ICC の全体を実装する必要は無い。
実写で問題になるのは Display P3 と AdobeRGB で、どちらも**行列 + TRC 型のディスプレイ
プロファイル**（`rXYZ` / `gXYZ` / `bXYZ` と `rTRC` / `gTRC` / `bTRC` を持つもの）に収まる。

| 型 | 扱い |
|---|---|
| 行列 + TRC（`curv` のガンマ1点・テーブルN点、`para` タイプ0〜4） | 変換する |
| LUT 型（`A2B0` 等のみで行列を持たない） | 変換せず、その旨を警告して sRGB として扱う |
| CMYK / Gray、PCS が Lab のもの | 同上 |
| 壊れた ICC | 同上（画像は読めているのに落とすのは筋が悪い） |

LUT 型まで背負うと補間器と CLUT の実装が要る。**得られるのは「稀な入稿素材でも色が合う」
だけで、対価としてバグの入る面積が数倍になる。** 割に合わないと判断した。

#### 変換の手順

TRC でデコード → 行列で XYZ(D50) → D50→D65 の白色順応 → XYZ→線形 sRGB → sRGB のガンマ。

**インテントは相対比色のみ。** EC 用途では白を白に保つことが最優先で、知覚的インテントに
必要な LUT はそもそも解釈対象外である。色域外はクランプする。

白色順応は **Bradford**。ICC の PCS は必ず D50 だが sRGB は D65 なので、間に必ず挟まる。
プロファイルの版や `chad` の有無によらず、**常に標準の Bradford で D50→D65 に戻す**。

**`chad` は使わない。** `chad` は「媒体の実測白色点 → D50」の行列で、その逆は
「D50 → 媒体の実測白色点」であって D65 ではない。相対比色では PCS の値も
`rXYZ`/`gXYZ`/`bXYZ` も既に媒体相対（媒体の白 = PCS の白 = D50）で表されているので、
`chad` を挟む余地がそもそも無い。挟むと、媒体白色点が D65 でないプロファイル
（D50 の ROMM / ProPhoto、DCI 白の DCI-P3、D60 の ACES）で白が白でなくなる。
`chad` が要るのは絶対比色のときだけである。

媒体白が D65 のプロファイル（Display P3 / AdobeRGB / ITU-709 / `Generic RGB Profile`）
では `invert(chad)` がたまたま Bradford の D50→D65 と一致するため、実写では気づけない。
なお v2 だから `chad` を持たないとも限らない（`Generic RGB Profile` は v2.2 かつ
`chad` あり）ので、版で分岐する設計そのものが誤りだった。

#### sRGB 相当は変換しない

原色が sRGB と一致し、**かつ** TRC も一致すれば、変換をスキップして
`color_space: "sRGB"` と報告する。往復の丸め誤差を足すだけで得るものが無いうえ、**既存の
sRGB 素材の出力バイト列が変わってしまうと、決定的動作という前提そのものが崩れる。**

**名前は見ない。** 「sRGB」を含む名前で中身が別物のプロファイル（sRGB 原色に
ガンマ 1.0 や 1.8 を載せたもの）は実在し、名乗りを信じると 8bit で 60 / 18 レベル
ずれた画像をそのまま素通しさせる。実プロファイルの側にも名乗りへ頼る理由は無く、
macOS の `sRGB Profile.icc` の `curv[1024]` は解析式との差が 7.6e-6 で、TRC の
一致だけで通る。素通しした場合も ICC 自身の名乗りは `color_profile` に残す。

#### 表で引く

`powf` を画素ごとに呼ぶと 12MP で桁が変わる。TRC のデコードは 8bit 入力の 256 エントリ表
（入力が 8bit しか取り得ない以上、表を引けば結果は厳密に一致する）、sRGB のエンコードは
線形値を 4096 分割した表と線形補間で引く。sRGB のガンマは暗部で最も曲がるが、そこでも
補間誤差は 8bit の 0.01 段に収まる。

実測（Apple M4 Pro、12MP、release）: 変換そのものが **5ms 前後**、CLI 全体のピーク RSS の
増加が **2MB**。画像を複製せずその場で書き換えるため、メモリはほぼ増えない。

#### 検証

合成 ICC（Display P3 / sRGB / AdobeRGB / ROMM RGB / DCI(P3) / LUT 型 / CMYK）をテスト内で
組み立て、P3 の原色が sRGB でクランプされること・中性グレーが中性のまま L* を保つこと・
sRGB では恒等になることを固定している。実写では、Display P3 の格子画像を kiri と
ColorSync（`sips --matchTo`）の両方で sRGB 化して突き合わせ、**全 8427 色で最大チャンネル
差 1、平均 ΔE 0.035** を確認した（未変換のままだと平均 ΔE 5.5、最大 18.8 ずれる）。

合成 ICC は自分が書いた前提しか踏まない。実ファイルには rTRC/gTRC/bTRC のオフセット共有、
31 言語を持つ `mluc`、v2 なのに `chad` を持つ並びといった、合成では思いつかない組み合わせが
ある。そのため、インストール済みの ColorSync プロファイル（sRGB / Display P3 / AdobeRGB /
Generic RGB / ROMM / DCI(P3)）をそのまま読み、グレー階調が ColorSync と littleCMS 2.17 の
両方が返した値と 1 以内で一致することも固定している。**プロファイル自体はリポジトリに
置かない**（Apple / Adobe / HP の著作権表示があり再配布に懸念があるため）。見つからない
環境では黙って飛ばす。

**ColorSync と一致しないものが 1 つある。** `ITU-709.icc` は `para` タイプ 3 の
Rec.709 曲線を持つが、ColorSync はこれを純ガンマ 2.4 として扱う（グレー 128 が
kiri 140 / ColorSync 121）。littleCMS は kiri と同じ 140 を返すので、これは
プロファイルの記述どおりに解釈しているか、名前付きビデオ色空間として別の
転送関数を当てているかの違いであり、kiri 側の誤りではない。

#### 出力は sRGB を名乗る

入力を sRGB へ揃えても、出力が何も名乗らなければ閲覧側はモニタの色空間と取り違え得る。
そこで既定で sRGB を名乗らせ、何を名乗ったかを `outputs[].icc`（`embedded` / `nclx` /
`none`）で返す。

- **プロファイルは自前で組む。** 行列 + TRC 型の v2 で 516 バイト。`color::icc` が読む形の
  逆向きで、TRC は 32 点の `curv` を定数で持つ（`powf` を呼ばないので libm で揺れない）。
  HP / ICC 配布の sRGB を同梱しないのは、依存と権利を軽くするため。kiri に読み戻すと
  sRGB 相当と判定されることをテストで固定している——外れると、kiri の出力を kiri に戻す
  たびに色変換が走る
- **PNG / JPEG は ICC を埋める。** 書くのは `image` の `set_icc_profile`（0.25.6 以降）で、
  PNG は IHDR の直後の `iCCP` 1 個だけ（`sRGB` チャンクは併記しない。png クレートが排他に
  しており、PNG 3 も併存を勧めない）、JPEG は APP0（JFIF）の直後の APP2 1 個である
- **AVIF は ICC を入れない。** ravif は AV1 シーケンスヘッダの色情報（原色 BT.709 /
  転送特性 sRGB / 行列 恒等 / full range）で sRGB を名乗り、ICC を渡す口を持たない。
  `colr` ボックスは既定値と同じなので avif-serialize が省き、コンテナには現れない。
  非対称だが、どちらも sRGB を言い切っている点は同じである
- **`--no-color-convert` で変換しなかった画素には名乗らせない。** 名乗りが嘘になるため、
  PNG / JPEG は ICC を埋めず `none` を返し、`ICC_NOT_EMBEDDED` で理由を言う。AVIF は名乗りを
  外す手段が無いので `nclx` のまま、警告だけを出す。LUT 型や uncalibrated は既に「sRGB と
  して扱う」と宣言しているので名乗らせる

### 3.6 セグメンテーションモデルの位置づけ

**色では原理的に解けない素材がある。** 暗い机の上の黒いキーボード（実写）は、
切り抜き境界で測った色差 13.8 が背景自身のばらつき 21.6 を下回る。kiri 自身が
`NOT_SEPARABLE` を返す状態で、しきい値をどう選んでも両立する値は存在しない。
4.9 の空間的な指示はこれを人／AI の手で埋める道だったが、埋める材料——
「どこが商品か」という**意味の事前知識**——は kiri の中には無い。

#### 候補の比較（2026-09）

| 候補 | ライセンス | 構造 | pure Rust |
|---|---|---|---|
| **ISNet（DIS general-use）** | Apache-2.0（コード・重みとも） | U²-Net 系、畳み込みのみ、44M params、ONNX fp32 176MB | **tract-onnx で動く**（実測） |
| BiRefNet_lite | MIT（コード）。重みの学習データ DIS5K に商用制限 | Swin-T + ASPPDeformable | candle 実装があるが `candle-core` にパッチ依存。tract では deformable conv が通らない見込み |
| U²-Net / u2netp | Apache-2.0 | 畳み込みのみ | tract で動く。品質は ISNet 以下 |
| RMBG-1.4 / 2.0 | CC BY-NC 4.0 | — | **商用不可。採用しない** |

**採用は ISNet。** 重みまで Apache-2.0 で、畳み込みだけで組まれているため実行の
確実性が高い。BiRefNet は次候補だが、条件が 2 つある——candle のパッチ依存が
解消されること、**重みのライセンス（DIS5K の商用制限）を利用者に明示できる形に
なること**。ライセンスが曇ったモデルを既定の経路へ入れる利得は無い。

#### 既存の Rust クレートは採れない

`rembg-rs` / `rmbg` / `rust-background-removal` はいずれも `onnxruntime`（C）に
依存しており、3.1 の方針と真っ向から衝突する。`tract-onnx`（Sonos、MIT OR
Apache-2.0）は pure Rust で、実測でも `cargo tree -e normal` に `*-sys` は
1 つも現れない。ビルド中に `cc` が動くことについては 3.1 を参照。

#### ライセンスは 1 つだけ色が違う

推論の依存に **`dyn-eq` 0.1.3（MPL-2.0）** が 1 つ入る（`tract-core` 経由）。
MPL-2.0 はファイル単位のコピーレフトで、そのファイルを改変しなければ MIT の
成果物に静的リンクしてよい。**kiri は `dyn-eq` を改変しない**ので配布物の
ライセンスは MIT のままだが、`--features segment` で建てたバイナリを再配布する
利用者は知っておく必要がある。残る 100 余りの依存は MIT / Apache-2.0 / BSD で、
copyleft はこれ 1 つだけである（`cargo metadata` の `license` を全件走査して確認）。

#### feature を既定オフにした理由

**2 つある。どちらも単独で決定的である。**

1. **MSRV。** `tract-onnx` 0.23.7 の `rust-version` は 1.91 で、kiri の 1.85 を
   超える。既定で有効にすると `cargo +1.85 check` が引数の綴りすら見ずに落ちる。
   MSRV は「この版の rustc で使える」という約束なので、推論のために黙って上げない
2. **費用。** 素の kiri は clean build 50 秒 / 3.26MB で建つ（Phase 4 の
   3.21MB に対して +48KB。feature を切っても、`segment/` のうちモデルを
   要さない部分——3 値・トライマップ化・モデルの表・SHA-256——は入る）。
   tract を足すと **200 秒 / 19.26MB**（+150 秒 / +16.0MB）になる。目安に
   置いた +30 秒 / +10MB のどちらも大きく超える。依存クレートは 97 → 175 に増え、
   リリースプロファイルの `lto = true` / `codegen-units = 1` が tract 全体に
   掛かるのが効いている。切り抜きの大半（単色背景の EC 素材）はモデルを
   要しないので、その費用を全員に負わせる理由が無い

**依存クレートの数え方を書いておく。** 数え方で 1 割ずれるので、方法を添えない
数字は照合できない。

```
cargo tree -e normal --prefix none | sed 's/ (\*)$//' | sort -u | wc -l
```

`(*)`（同じ枝を再掲した印）を落としてから重複を潰す。これで 97（無効）→ 175
（`--features segment`）になる。**kiri 自身を含み、2 つの版が同居するクレートは
2 つと数える**（`syn` / `thiserror` / `itertools` / `miniz_oxide` / `pastey` /
`thiserror-impl` の 6 つがそれに当たる）。`sed` を省くと `(*)` 付きの行が別物として
残り、110 → 211 と出る——同じ木を数えていても、方法を書かなければ別の数字になる。

無効な build で `--segment isnet` を渡すと `SEGMENT_UNAVAILABLE` で断る。
**黙って `off` に落とさない**——エージェントは「モデルを使った結果」だと
思ったまま数値を読み、切り抜きが悪いのをモデルのせいだと結論する。

## 5. CLI 設計

### 5.1 コマンド体系

ハイブリッド方式を採る。`cutout` が切り抜きからリサイズ・キャンバス配置・形式変換までを内包し、1回の呼び出しで完結する（AIが中間ファイルの後始末を忘れる問題を回避するため）。加えて切り抜き不要なケース向けに `resize` / `convert` を用意する。

```
kiri schema                             オプションと code の一覧（契約）を返す
kiri info    <input>                    画像情報と背景推定を JSON で返す
kiri cutout  <input> -o <output> [...]  切り抜き（全部入り）
kiri resize  <input> -o <output> [...]  リサイズのみ
kiri rotate  <input> -o <output> [...]  回転のみ
kiri convert <input> -o <output> [...]  形式変換のみ
kiri batch   <spec.json>                仕様ファイルによる一括処理
```

`schema` だけが画像を取らない。**README は 1000 行あり、エージェントの文脈に丸ごと
載せられる長さではない。** 必要なのは「どう呼ぶか」と「返ってきた code が何を意味
するか」だけなので、それを 1 コマンドで配る。中身は clap のパーサと 2 つの code の
カタログから組み立てるので、手で書いた一覧のように実装から離れることがない。

### 5.2 cutout

```
kiri cutout in.jpg -o out.avif \
  [--bbox x1,y1,x2,y2] [--normalized] [--fg-seed x,y] \
  [--trimap trimap.png] [--fg-mask fg.png] [--bg-mask bg.png] \
  [--fg-polygon x1,y1,x2,y2,...] [--bg-polygon x1,y1,x2,y2,...] \
  [--tolerance 12] [--edge-threshold 8|auto] [--step-tolerance 2.2] \
  [--shadow-tolerance 35] [--seal 1] \
  [--cleanup 2] [--feather 1] [--no-refine] [--no-despill] \
  [--optimize] \
  [--shadow synth] [--shadow-offset 0,12] [--shadow-blur 10] \
  [--shadow-color "#000000"] [--shadow-opacity 0.25] \
  [--reflect on] [--reflect-height 150] [--reflect-opacity 0.25] [--reflect-gap 0] \
  [--canvas 1000x1000] [--fill-ratio 0.85] \
  [--background "#FFFFFF"] \
  [--quality 90] [--effort 6] [--max-bytes 500k] \
  [--json] [--debug-mask mask.png] [--force]
```

**bbox は任意**。未指定なら全自動で切り抜く。指定された場合はその外側を強制的に透明化する。これによりバッチ処理が本命の使い方になり、AIは「全件の座標を出す」のではなく「失敗した数枚だけ救済する」役割を担う。

座標は左上原点のピクセル値 `x1,y1,x2,y2`。`--normalized` を付けると 0〜1 の正規化座標として解釈する（ビジョンモデルは正規化座標を返すことが多いため）。

`--edge-threshold` は**「未指定」と「8 を明示」を区別する**。未指定なら背景のテクスチャに応じて引き上がり（4.3）、明示すればその値に従う。同じ区別を `batch` の spec キーにも持たせている。

`--trimap` / `--fg-mask` / `--bg-mask` / `--fg-polygon` / `--bg-polygon` は、bbox と同じ「どこが商品か」を、矩形より細かい形で渡すための入口である（4.9）。`--normalized` は bbox・種・多角形のすべてに効く。

`--optimize` は `tolerance` / `bbox` / `background-model` の組を kiri 自身に総当たりさせる（4.13）。**明示した値は探索の軸から外れる**ので、`--tolerance 30 --optimize` は「30 に固定して残りを探す」の意味になる。試した候補とその指標は `optimize.candidates[]` に、選ばれた設定は `optimize.chosen` と `settings` に出る。

`--shadow-tolerance` と `--shadow` は**向きが逆**である。前者は実写に写っている影を背景として消す側（4.4）、後者は消した後のアルファから影を作り直す側（4.14）。名前が並ぶので、`--help` の 1 行目でも「消す」「合成する」を書き分けている。`--shadow-offset` / `--shadow-blur` は長辺 1000px 換算で、基準は**最終画像の長辺**（`--canvas` があればキャンバスの長辺）。実際に効いた px は `shadow` ブロックに出す。

`--reflect` は同じ px@1000 の基準で、商品の鏡像を下に敷く（4.16）。**`--shadow` とは
写すものが違う**——影はアルファを `--shadow-color` で塗るが、反射は商品の画素（RGB も）を
そのまま写すので色のノブが無い。併用すると層は「下地 → 影 → 反射 → 商品」で、反射の
材料は商品だけである。実際に効いた px は `reflect` ブロックに出す。

### 5.3 info

AIが座標を出す前に画像の寸法を知る必要があるため必須のコマンド。

```json
{
  "width": 2400, "height": 3200, "format": "jpeg",
  "exif_orientation": 6,
  "color_space": "Display P3", "color_converted": true, "icc_profile": true,
  "background": {
    "rgb": [248, 248, 247], "uniformity": 0.97,
    "perimeter_delta_e": { "p50": 0.4, "p90": 1.2, "max": 2.8 },
    "texture": { "p50": 0.0, "p90": 1.0 }
  },
  "warnings": []
}
```

`uniformity` により、AI側が「この画像は単色背景なので処理可能」「複雑背景なので非対応」を事前判断できる。`texture` は別の軸で、**背景がざらついていないか**を言う。`p50` が `edge_threshold`（既定 8）に達していれば、その背景は堤防を張れない素材である（4.3）。`p90` だけが高い場合は背景ではなく、**帯に写り込んだ物**（画面の端で見切れた柄物の商品など）を指している。

### 5.4 batch

「AIが画像ごとに座標を出す」設計はバッチと本質的に相性が悪い（画像ごとに引数が異なる）。JSON仕様ファイルを流し込む形で解決する。AIはJSONの生成が得意なため、これが最もAIネイティブな形になる。

```json
{
  "defaults": { "canvas": "1000x1000", "fill_ratio": 0.85, "format": "avif" },
  "items": [
    { "input": "a.jpg", "output": "a.avif" },
    { "input": "b.jpg", "output": "b.avif", "bbox": [200, 150, 1100, 1600] }
  ]
}
```

`rayon` で並列実行する。結果の並びは仕様ファイルの順序を保つ。

**1 件の失敗で全体を止めない。** 数百点を回すバッチでは、失敗した項目を報告しつつ
残りを処理し切るほうが有用であるため。失敗があった場合は終了コード 4 で知らせ、
詳細は `results[]` の各項目に入れる。

**仕様の誤りは黙って無視しない。** 綴り違いのキーはエラーとし、編集距離から候補を
提示する。無視すると「指定したはずの設定が効いていない」という最も気づきにくい
失敗を生むため。serde の `flatten` は `deny_unknown_fields` と併用できないので、
キーの検証は自前で行っている。

相対パスは既定で**仕様ファイルのある場所**を基準に解決する。AI は画像の隣に仕様を
書き出すのが自然であり、実行時のカレントディレクトリに依存しないほうが再現性が
高いため。`--base-dir` で上書きできる。

### 5.5 共通規約

- **stdout は JSON のみ**、ログと進捗は全て stderr に出す
- **デフォルト非破壊**。既存ファイルの上書きは `--force` を必須とする
- **メタデータはデフォルトで除去**。Web配信ではサイズと個人情報の両面で不要。常に生の画素から再エンコードするので、EXIF などは自然に落ちる。**例外は sRGB の ICC** で、色の名乗りとして既定で埋める（3.5 の末尾を参照）
- **リサイズは既定で拡大禁止**（`--allow-upscale` でオプトイン）。素材を勝手に拡大してぼかす事故を防ぐ
- **色空間**: 埋め込み ICC を既定で sRGB へ変換する（`--no-color-convert` でオプトアウト、`batch` では `color_convert`）。変換の範囲と根拠は 3.5 を参照

### 5.8 キャンバス配置

`--canvas WxH` で、切り抜いた商品を指定サイズの中央に配置する。`--fill-ratio` は
商品がキャンバスの何割を占めるかを決め、既定は 0.85（EC プラットフォームで広く
求められる占有率）。

配置の手順は、マスクのアルファが 0 を超える範囲で商品を切り詰め、占有率の枠に
収まる倍率で拡縮し、中央に合成する。切り詰めに前景判定(128以上)ではなく
アルファ 0 超を使うのは、フェザリングされた薄い縁を落とさないため。

#### 占有率は「見える範囲」で数える

**切り詰める範囲と、占有率を数える範囲は別である。** 切り詰めはフェザーを
落とさないためにアルファ 0 超まで含めるが、アルファが 1 から十数までの
立ち上がりは**下地へ落とせば下地の色そのもの**で、書き出したファイルからは
背景と区別できない。`--fill-ratio` のヘルプは「商品がキャンバスの何割を
占めるか」と言っており、見えない縁は商品ではない。

そこで、書き出したファイルが不透明になる実行（`--flatten`、または透過を
扱えない形式）では、下地へ落としたときに背景との ΔE76 が `UNIFORM_DELTA_E`
(5.0) を超える範囲を別に測り、`canvas::plan` へ渡す占有率を
`切り詰めた範囲 ÷ 見える範囲` 倍する。透過を残す実行では補正しない——
`kiri lint` もそこではアルファの外接矩形で測るので、切り詰めた範囲が
そのまま正しい。

**これは拡大したときにだけ現れる不具合を直したものである。** 見えない縁の
厚みは px で決まる（フェザー半径と境界帯の幅で決まり、素材の大きさに依らず
片側 5〜6px）ので、比率としての不足は倍率に比例する。`--profile amazon`
(1600px / 占有率 0.86) へ合成シーンを通した実測:

| 素材の 1 辺 | 倍率 | 見えない縁(幅/高さの合計 px) | 書いたものの占有率 | `kiri lint` |
|---|---|---|---|---|
| 2023 | 0.99 | 11 / 10 | 0.860 | 0.876 pass |
| 1349 | 1.49 | 7 / 7 | 0.859 | 0.876 pass |
| 1011 | 1.97 | 11 / 11 | 0.849 | 0.873 pass |
| 506 | 3.90 | 15 / 7 | 0.842 | 0.864 pass |
| 300 | 6.37 | 11 / 12 | 0.820 | **0.837 fail** |

補正後は同じ 5 枚で 0.864〜0.886 に収まり、倍率との相関が消える。

**前景の芯（アルファ `FOREGROUND_THRESHOLD` 以上）は、下地の上で見えなくても
数える。** 床が無いと、胴体が背景と同じ色の商品で矩形が点まで縮む——400x400 の
白地に ΔE 1.7 の矩形と 20px の黒い点を置いた画像では、占有率が 1.0 で止まって
`content` が 1376x1376 ではなく 1600x1600（余白ゼロ）になった。補正が受け持つのは
芯の外にあるフェザーだけである。

**`FILL_RATIO_MARGIN`（0.01）では直せない。** 不足は倍率に比例して増えるので
どんな定数でも足りない倍率が必ずあり、倍率 6 を飲む定数は拡大しない実行の
商品まで一律に大きくする。**`kiri lint` の閾値を下げるのも採らない**——
`UNIFORM_DELTA_E` は `cutout` が「背景と同じ色」と言うのに使っている数
そのもので、下げれば切り抜き自体が変わる。そもそもアルファ 3 の画素を
白へ落としたものは白であり、lint の測りは正しい。

`canvas.fill_ratio` が返すのは**補正前**の数、つまり「見える商品がキャンバスの
何割を占めるか」である。`canvas.content` は**置いた矩形**（縁を含む）なので、
`content ÷ width` はこれより大きくなりうる。補正後を返すと、`align: "bbox"` の
`set` で `f_i = T` が成り立たなくなり `set.fill_ratio` と食い違う（`commands::batch`
がその一致を規約として書いている）。

`batch` の `set` も同じ 1 つの数を通るので、**揃うのは見える範囲**である。
下地を塗った出力では、縁の厚みが点ごとに数 px 違うぶん**置いた矩形の高さは
点ごとにずれる**——揃えたいのは並べたときの見た目なので、揃える対象は
見える範囲のほうが正しい。透過を残す出力では補正が掛からないので、
置いた矩形がそのまま揃う。

余白は既定で透明。`--flatten` を付けると `--background` の色で塗り潰す。
これにより透過 PNG が使えないプラットフォーム向けの白背景 JPEG も同じ経路で出せる。

**キャンバス配置では拡大を禁止しない**（`resize` とは扱いが異なる）。`resize` では
利用者が出力寸法そのものを指定しているためエラーが妥当だが、キャンバス配置では
指定しているのは枠であり、拡縮はその結果として決まる。要求を満たすために必要な
拡大まで拒否するのは筋が悪い。代わりに倍率を添えて警告し、`--json` の
`canvas.scale` でも確認できるようにしている。

#### 5.8.1 profile が決めるキャンバス（Phase 26）

`--profile` は `--canvas` を指定しない実行でキャンバス寸法を決める。Phase 22 から
Phase 25 までそれは `1600x1600` の固定値だった。**固定値である限り、入力が
大きければ情報を捨て、小さければ捏造する。**

**以下の倍率はすべて `--profile amazon --optimize --rotate auto` で測った。**
商品の長辺は切り抜きの結果なので、フラグを揃えないと 1〜2px 動き、倍率もそのぶん
動く（700x525 の素材は `--rotate auto` の無い実行では長辺 519px・倍率 2.6513 になる）。
**条件を書かない実測値は、次に測る人が再現できない。**

- 4284x5712 の実写（`remote.jpg`）は商品の長辺が 4103px で、倍率 0.3354 まで
  潰れる。拡大が始まるのは canvas 約 4771 からで、1600 はそこからはるかに手前である
- 700x525 の入力（商品の長辺 521px）では倍率 2.6411 で拡大される。Amazon の
  規格文（G1881）は「小さい画像を人工的に拡大しないでください」と書いており、
  既定で拡大するのは規格に反する側である

**決め方は「占有率を通したときに拡大にならない最大の段」**を梯子
`1000 / 1500 / 2000 / 2500 / 3000` から選ぶ。`canvas::plan` が正方キャンバスで
決める倍率は `canvas × fill_ratio ÷ 商品の長辺` なので、拡大にならない条件は
`canvas × fill_ratio ≤ 商品の長辺` である。

**商品の長辺は切り抜き後のアルファの外接矩形であって、画像の長辺ではない。**
商品が小さく写っている素材で拡大を見逃さないため（上の 4284x5712 でも、切り抜いた
商品の長辺は 4103px である）。

**段に丸めるのは、同じ撮影セットなら同じ段に落ちて寸法が揃うようにするため。**
入力ごとに連続の値を返すと、`--fill-ratio` が揃えようとしているものが崩れる。

**揃うのは同じ段に落ちる限りである。段の境界を跨ぐ素材が混ざると揃わない。**
条件が `段 × 占有率 ≤ 商品の長辺` なので、占有率 0.86 では寸法の動く境界が
1290 / 1720 / 2150 / 2580 px の 4 本あり、**商品の長辺が 1289px なら 1000、
1290px なら 1500 になる。** 長辺は切り抜きの結果なので、`--tolerance` も
`--feather` も `--rotate auto` の角度も 1 画素動かせば飛ぶ。境界が段数より
1 つ少ないのは最小段が「どの段も拡大になる」ときの落とし先でもあるためで、
その下側（860px）では canvas は 1000 のまま倍率だけが動く。**寸法を必ず揃えたい
実行は `--canvas` を明示すること**——段に丸めるのは「連続の値よりは揃いやすい」
までで、揃うことの保証ではない。

天井 3000 の根拠は、占有率 0.86 を通すと商品の長辺が 2580px になり、4K
ディスプレイの短辺 2160px で全画面表示しても等倍を割らないこと——これ以上
大きくしても見る側の画素数を超えるだけである。加えて 9MP は Shopify の 25MP
上限に余裕があり、現在のどのプリセットの上下限にも素で収まる。下限 1000 の根拠は
Amazon の「1,000px 以上でズーム機能が有効」。

**最小段でも拡大になる素材は、拡大したうえで `CANVAS_UPSCALED` で報せる。**
上の「キャンバス配置では拡大を禁止しない」は変えない。変わるのは倍率で、
700x525 の実測は 2.6411 → 1.6507 に下がる。

選んだ段は最後に `Rules` の `longest_side_min` / `longest_side_max` /
`max_pixels` へ押し込む。**`Rules` に矛盾する canvas は出ない**という Phase 22
からの不変条件はそのままである。

**`PROFILE_OVERRIDDEN`（canvas）の出る位置だけが変わる。** `--canvas` を明示した
実行はこの警告で「profile が求めた値」と「実際に効いた値」を並べるが、前者が
**切り抜いた後にしか分からなくなった。** そのため canvas の 1 件だけが warnings
の先頭（指示についての警告の並び）ではなく、結果の警告の後・キャンバス配置の
警告の前に来る。他の項目の並びは変えない——canvas が外れるのは、それが指示では
なく**結果が出てから分かる事実**になったからである。

`--canvas` を明示した実行と `--profile` を渡さない実行は、Phase 25 までと
1 バイトも変わらない（実測で確認済み）。

### 5.9 リサイズの当てはめ方

`--width` / `--height` の一方だけを指定した場合はアスペクト比を保つ。両方指定した場合は
`--fit` が挙動を決める。

| `--fit` | 挙動 |
|---|---|
| `contain`（既定） | 枠に収まるよう縮小する。結果は枠以下 |
| `cover` | 枠を覆うよう縮小し、はみ出しを中央で切り取る。結果は枠ちょうど |
| `exact` | アスペクト比を無視して枠ちょうどに変形する |

**拡大は既定で拒否し、エラーとする**（`--allow-upscale` でオプトイン）。黙って縮小に
倒すと出力寸法が要求と食い違い、バッチ処理でそれに気づけないため。エラーであれば
AI エージェントが `--allow-upscale` を付けるか元素材を見直すかを判断できる。

補間は Lanczos3。透過画像は事前乗算つきで補間する。これを怠ると切り抜き済み画像の
境界に背景色がにじむ。

### 5.6 JSON 出力

処理結果には「実際に何が起きたか」を含める。AIが結果を検証して次の手を打てるようにするため。

すべての結果 JSON は `schema_version` を名乗る（失敗の JSON も同じ）。**キーが増えた
だけでは上げない。** 既存のキーの意味や型が変わったとき、つまり今までの読み方が
誤読になるときだけ上げる。版を名乗らなければ、契約が動いたときに古い読み手が黙って
誤読する。

`dry_run` も常に出す。省いて「無ければ書いた」にすると、古いバージョンで走った結果と
書いた結果が同じ形になり、成果物が無いのにあるものとして次へ進む事故を防げない。

```json
{
  "input": "in.jpg",
  "outputs": [{ "path": "out.avif", "bytes": 31200, "icc": "nclx",
               "quality_used": 90.0, "attempts": 1 }],
  "source": { "width": 2400, "height": 3200 },
  "color_space": "Display P3", "color_converted": true,
  "mask": {
    "foreground_ratio": 0.34,
    "bbox": [130, 95, 880, 1380],
    "touches_edge": false,
    "separability": 68.3, "halo_ratio": 0.0, "edge_width": 1.0,
    "contour_roughness": 0.006, "rim_contamination": 0.001
  },
  "background": {
    "rgb": [248, 248, 247], "uniformity": 0.97,
    "perimeter_delta_e": { "p50": 0.4, "p90": 1.2, "max": 2.8 },
    "texture": { "p50": 0.0, "p90": 1.0 }
  },
  "settings": {
    "tolerance": 12, "edge_threshold": 8,
    "step_tolerance": 2.2, "shadow_tolerance": 35, "seal": 1,
    "cleanup": 2, "feather": 1, "despill": true, "refine": true
  },
  "elapsed_ms": 142,
  "warnings": []
}
```

**この中の数はキーの形と型を示すための例示値で、特定の実行を写したものではない**（`bytes` も `quality_used` も `elapsed_ms` も同じ）。実測が要る数はそれを名指しした節に置く——ここに混ぜると、形の説明を読みに来た人が測り直すべき数に気づかない。

`foreground_ratio` が極端な値（0.02 や 0.98）であれば失敗を検知でき、`touches_edge` は商品の見切れを示す。

ただし `foreground_ratio` は「どれだけ残ったか」しか言わず、その輪郭が妥当かを語らない。そこで `mask.separability`（切り抜き境界の内側で測った商品と背景の色差）と `background.perimeter_delta_e`（外周の色差の分布）を併せて返す。

`background.texture`（外周の帯で測った勾配の分位）は、`perimeter_delta_e` では区別できないものを言う。**なだらかな照明ムラとざらついた織り目は、背景色からの色差では同じ値になる。** 前者は `--tolerance` で吸収できるが、後者は堤防を誤発火させてフィルを止める。分けられるのは 1px あたりの変化量だけである。

`settings` には**実際に効いた**設定を並べる。結果が期待と違ったとき、指定が効いたのか既定のまま走ったのかは画像を見ても分からない。バッチでは `defaults` と項目の継承が絡むぶん、なおさら結果側に答えが要る。`edge_threshold` は背景のテクスチャに応じて自動で引き上がることがあるので（4.3）、指定値ではなく**引き上げ後の値**が入り、`warnings` に理由と根拠の数値が 1 行出る。**黙って設定を変えるのは、指定が無視されるのと同じくらい追いにくい失敗である。**

`separability` は境界の**内側**を測るため、前景の外側に張り付いた背景色の縁を検出できない。そこで縁そのものを測る `mask.halo_ratio`（境界近傍で不透明なのに、元画素の色が局所背景と ΔE≤3 の画素の割合）と、境界の階調を測る `mask.edge_width`（アルファが 0.9 から 0.1 へ落ちるまでの幅の中央値 px）を加える。

- `halo_ratio` が 0.10 を超えると警告する。この縁は白背景では見えず、納品先が黒や色付きの下地だったときに初めて輪郭の光として現れる。**書き出しの時点で知らせなければ、エージェントは検証しようがない**
- 診断はデスパイル後ではなく**元画像**で測る。デスパイル後の画像では「背景色を消したから縁が見えなくなった」だけの状態を good と誤判定する

この 2 つは**実写の布ですり抜けた**（4.8）。`mask.contour_roughness`（二値輪郭が、それを滑らかにした参照輪郭からどれだけ離れているかの平均。単位は長辺 1000px 換算の px）と `mask.rim_contamination`（境界の内側の帯で、元の色が局所前景より局所背景にはっきり近い画素の割合）を加える。しきい値はそれぞれ 0.16 と 0.02 で、越えると `CONTOUR_ROUGH` / `RIM_CONTAMINATED` が出る。**どちらも `null` を取りうる**（測れる輪郭が無い／帯の半分以上で判定できなかった）。

- `separability` が `perimeter_delta_e.p50` を下回るなら、背景を飲み込める tolerance は商品も飲み込む。**両立する値が存在しないため、パラメータ調整では改善しない。** この判定を返すことで、AIが無駄な再試行ループに入るのを防ぐ
- しきい値を定数で置かず背景自身のばらつきと比べるのは、「どこまで許容すべきか」が画像ごとに違うため。均一な背景では `p50` がほぼ 0 になるので、白背景×白商品の看板ケースでは発火しない

`--optimize` を渡すと `optimize` ブロックが増える（渡さなければキーごと現れない。`segment` と同じ規約）。`candidates[]` は**探索段の順位のまま**並び、原寸でも回した候補は `stage` が `"final"` になる。

```json
"optimize": {
  "searched_at": 1500,
  "candidates": [
    { "tolerance": 45, "bbox": [0, 2022, 4213, 3828], "background_model": "auto",
      "stage": "final", "foreground_ratio": 0.2037, "touches_edge": false,
      "separability": 53.8151, "halo_ratio": 0.0295,
      "contour_roughness": 0.2541, "rim_contamination": 0.0613,
      "warnings": ["EDGE_THRESHOLD_RAISED", "CONTOUR_ROUGH"], "collapsed": false,
      "score": { "fatal": 0, "unmeasured": 0, "quality": 4.9493,
                 "separability": 53.8151 },
      "chosen": true }
  ],
  "chosen": { "...": "同じ形" },
  "elapsed_ms": 13682
}
```

**`stage` が `"search"` の候補の数値は参考値である。** その候補は縮小版を
`refine` 抜きで回したものなので、halo・輪郭の粗さ・縁の汚染・`touches_edge` は
原寸のそれと比べられない（4.13）。探索段の順位に効いているのは
`FOREGROUND_TOO_SMALL` 系の致命と `collapsed`、そして `separability` だけである。

**選ばれなかった候補も見せる。** エージェントが「2 位のほうが自分の目的に合う」と判断して明示指定へ切り替えられるようにするためで、そのときは候補の値をそのまま `--tolerance` / `--bbox` / `--background-model` へ写せばよい（`bbox` は `stage` に関わらず原寸の画素座標で出す）。`settings.optimize` は**常に**出す——この 1 行が `settings.tolerance` / `settings.background_model` / `applied_bbox` の出所を変えるためである。

数値で判断できない場合に備えて `--preview` を持つ。原寸の出力（数千px・数十MB）は視覚モデルに渡せないため、「元画像 | マスク | 結果」を1枚に並べた小さな画像を書き出す。外部ツールを挟まずに完結させるのは、依存ゼロという前提を崩さないためである。3面に分けるのは、結果だけを見ても失敗の原因が分からないためである。

### 5.7 exit code

| コード | 意味 |
|---|---|
| 0 | 成功 |
| 1 | 一般エラー |
| 2 | 引数不正 |
| 3 | 入力ファイル異常（存在しない、破損、非対応形式） |
| 4 | 処理失敗（背景を検出できない等） |

エラー時も `--json` 指定時は JSON で返す。

```json
{ "schema_version": 2, "error": { "code": "NO_FOREGROUND", "message": "...", "hint": "..." } }
```

## 6. AIエージェントとの分担

| 担当 | 役割 |
|---|---|
| **AI** | 意味理解。どれが商品か、どこにあるか。結果JSONの検証と、失敗画像の救済 |
| **kiri** | 画素処理。背景色推定、輪郭の確定、整形、エンコード |

AIに輪郭のポリゴン頂点列を出させる案は採らない。ビジョンモデルは bbox はそこそこ出せるが、輪郭を数十点で正確になぞるのは苦手で、フラッドフィルより精度が落ちるため。

想定される典型的なループ:

0. 初回だけ `kiri schema --json` で呼び方と code の意味を引く
1. AIが `kiri batch` で全件を自動処理
2. 結果JSONの `foreground_ratio` や `warnings` を見て失敗を検出
3. 失敗した画像だけ `kiri info` で確認し、`--bbox` や `--tolerance` を調整して再実行。
   **この探索は `--dry-run` で回す**（成功している他の項目の成果物を壊さないため）
4. それでも直らない画像は `kiri cutout --preview` で目視して判断する

3 までは画像を開かずに回ることを前提とする。4 は救済フェーズの道具であり、`batch` は既定でプレビューを書き出さない。数百点を回す通常の経路で全件の画像を吐けば無駄なI/Oになるためである。

## 7. 未決事項 / v2以降の候補

- LUT 型 ICC の解釈（現状は警告して sRGB 扱い）。稀な入稿素材でしか効かないため優先度は低い
- HEIC 入力（pure Rust の HEVC デコーダが現れたら再検討する）
- グラデーション背景への対応（局所適応しきい値）
- 半透明商品の扱い
- `AlphaColorMode::UnassociatedClean` によるファイルサイズ削減の検証
- crates.io への公開名（`kiri` は既存クレートに取られている。`kiri-cli` + `[[bin]] name = "kiri"` が有力）

## 8. 主要な決定と根拠

| 決定 | 根拠 |
|---|---|
| Rust / pure Rust（C依存なし） | 単一バイナリ配布、クロスコンパイルの容易さ、OSS採用障壁の低減 |
| WebP 非対応 | 実用的なロッシー圧縮に libwebp（C）が必要 |
| HEIC 入力 非対応（ただし手順を返す） | HEVC デコーダが pure Rust に無い。読めない事実より、原因が分からないメッセージのほうが害が大きいため |
| ICC は行列 + TRC 型だけ解釈する | 実写で問題になる Display P3 と AdobeRGB がこの型に収まり、LUT 型まで背負うと得るものに対してバグの入る面積が大きすぎるため |
| 色変換を既定で有効にする | iPhone 素材が Display P3 で入るのが常態で、素通しは彩度の誇張として必ず出るため |
| sRGB 相当は変換しない | 往復の丸め誤差を足すだけで、既存素材の出力バイト列を動かす理由が無いため |
| 出力に sRGB の ICC を埋める | 名乗りの無い出力は閲覧側がモニタの色空間と取り違え得る。入力を sRGB へ揃えた意味が、出力で名乗らなければ届かないため |
| AVIF には ICC を入れない | AV1 の色情報だけで sRGB を言い切れ、ravif に ICC を渡す口も無いため |
| sRGB のプロファイルは自前で組む | 配布プロファイルの同梱は権利の確認が要り、色管理ライブラリは C 依存を持ち込む。行列 + TRC 型なら数百バイトで組めるため |
| 白色順応に Bradford / 相対比色 | PCS が D50 で sRGB が D65 なので順応は必須。EC では白を白に保つことが最優先で、知覚的インテントに必要な LUT は解釈対象外であるため |
| AVIF をデフォルト出力 | pure Rust で実装でき、実測で 1MP/57ms と実用速度。透過の扱いも良好 |
| 単色背景のみ対応 | MLモデルなしで品質を担保できる範囲に限定するため |
| 影は消す | EC用途では商品単体の切り抜きが求められることが多く、見た目も揃うため |
| フィルを 3 段に分ける | 堤防は 1 箇所の破れで内部まで浸水する。連結性以外の守りが要るため |
| 芯の許容量を利用者に見せない | 「どこまでを背景と言い切れるか」は画像ごとに違い、外周 ΔE の分布が答えを持つため |
| 段差の判定に「先の変化量」を使う | 落ち影の裾と淡い輪郭は 1px あたりの変化量が同じで、局所値だけでは分けられないため |
| 影を専用に判定する | 影は ΔE 20-30 あり、色の許容量を広げて飲み込もうとすると淡色商品も消えるため |
| 影の吸収を距離で切る | 影は数十 px で背景へ戻るが、輪郭の破れからの浸水は商品が続く限り進むため |
| 背景より明るい映り込みは消さない | 白背景の白い商品のハイライトと区別がつかないため |
| 測地的オープニングを掛ける | 破れをゼロにするより、細い通路を通った浸水を後から見分けるほうが確実なため |
| bbox は任意（自動が既定） | 単色背景限定により自動で大半が処理可能になり、バッチ処理が実用的になるため |
| EC整形機能を内蔵 | 切り抜きだけでは納品できない。実装コストが小さく実用価値が大きい |
| 診断値を結果に含める | `foreground_ratio` だけでは「輪郭が妥当か」が分からず、AIが直らない画像で再試行を繰り返すため |
| 判定を背景自身のばらつきと比べる | 許容できる色差は画像ごとに違い、定数のしきい値では実写で外れるため |
| 数値ノブではなく空間の指示を増やす | 最良設定の周りで 4 ノブを振っても指標が 1 桁目まで動かず、AI が得意なのは「どこが商品か」の判断のほうであるため |
| 指示の内部表現を 1 つに畳む | 入口ごとに経路を作ると、フィル・診断・プレビューの 3 箇所で同じ判断を書き直すことになるため |
| 確定背景をフィルの種にする | 外周から届かない囲まれた背景は、種にしない限りどんな色の規則でも消せないため |
| 指示の重なりをエラーにする | 黙ってどちらかを選ぶと「指定が効いていない」という最も追いにくい失敗になるため |
| マスクの寸法を合わせに行かない | 拡縮すると指示した境界が輪郭から半画素ずれたまま、結果だけがそれらしく返るため |
| 境界のアルファを色から推定する | マスクの形から作ったアルファは真のエッジ位置と無関係で、背景色の縁がそのまま残るため |
| アルファの計算を線形 RGB で行う | 合成は光の量の足し算であり、sRGB 値のままでは混色が直線に乗らないため |
| 孤立ノイズを面積で消す | オープニングは太さで消すため、細い商品の一部（ストラップ・ケーブル）を巻き添えにするため |
| 面積の下限を解像度に比例させる | ゴミの大きさ自体が解像度に比例し、固定値では 20MP の織り目（150px²）が消えないため |
| 背景のテクスチャで堤防を自動調整する | 布や段ボールは背景自身が 1px あたり十数の変化を持ち、堤防が背景の中で壁になるため |
| 背景を照明場として持つ | 紙や布の外周 ΔE は織り目を消しても 11 残る。1 色 + tolerance で飲むには淡色商品ごと飲む値が要るため |
| 均一な背景では 1 色のまま | 場を常に使うと解けている画像の数値が微妙に動き、「何が原因の差か」が分からなくなるため |
| 場を格子 + 双線形で持つ | 全解像度の Lab 表は 12MP で 72MB あり、フィルが持つ画素ごとの Lab と二重に積めないため |
| セルの値を平均ではなく中央値にする | 商品の縁が掛かったセルで平均が引きずられ、商品の真上の背景色が商品側へ寄るため |
| 埋めた値を次の回の材料に戻す | 「届いた順に確定」させると σ が変わった境目に場の段差が残り、その線でフィルが止まるため |
| 1 回目のフィルの結果で場を作り直す | 外周の帯と矩形だけでは、商品が中央を大きく占める画像で場の内側がほとんど外挿になるため |
| 主体の検出だけは 1 色で行う | 商品が外周の帯を大きく占めると場が商品の色を背景として学び、取りこぼしが leftover に残らなくなるため |
| 発火は p50、引き上げ幅は p90 で決める | p90 だけでは「背景がざらついている」と「帯に見切れた柄物が写っている」を区別できず、後者で堤防が無意味な高さまで上がるため |
| 堤防を無効化ではなく引き上げにする | 織り目の上に載った淡い商品を守る役目を残すため。実測では引き上げでも無効化と同じ結果に達する |
| クロージングを外す | 外周から到達できない穴はそもそも前景であり、埋める対象が原理的に存在しないため |
| `halo_ratio` を返す | `separability` は境界の内側を測るので、外側に残った背景色の縁を検出できないため |
| プレビューを内蔵（外部ツールに任せない） | 原寸出力は視覚モデルに渡せず、縮小に外部ツールが要れば依存ゼロの前提が崩れるため |
| 契約を `kiri schema` で配る | README は 1000 行あり、エージェントの文脈に載せられない。必要なのは呼び方と code の意味だけであるため |
| しきい値も `fields[]` で配る | 警告はしきい値を越えたときにしか出ず、越えていない値の良し悪しはしきい値を知らなければ判断できないため |
| 単一のしきい値で決まる警告だけ載せる | `NOT_SEPARABLE` のように画像ごとの値と比べる条件に `threshold` を付けると、その数値が嘘になるため |
| しきい値の定数を 1 箇所へ寄せる | 配るには定数化が要る。`foreground_ratio` の 0.01 / 0.99 は 3 箇所に散っており、片方だけ動かせば「警告は出ないのに切り抜けていない」が成立するため |
| schema をパーサとカタログから組み立てる | 手で書いた一覧は必ず実装から離れ、離れた一覧は「指定したのに効かない」という最も追いにくい失敗を招くため |
| code を 1 つの表から生成する | 警告もエラーもそこへ足す以外に作る方法が無くなり、「載っていない code が飛んでくる」が構造的に起こらなくなるため |
| exit code を code から引く | 呼び出し側が分類を選べる形だと、同じ code が場所によって違う番号を返しうる。「この失敗なら何番」の分岐が成立しなくなるため |
| 結果 JSON に `schema_version` を入れる | 契約が動いたときに古い読み手が黙って誤読する。黙って間違えるのが最も高くつくため |
| `--dry-run` を持つ | 救済フェーズは同じ画像へ何度もパラメータを振る。成果物を守るために `--force` を常用させるのは順序が逆で、探索そのものが書かなければよいため |
| dry-run でもエンコードする | `bytes` を見積もりにすると、品質と形式の判断が本番実行を挟まないと下せなくなるため |
| dry-run でもプレビューは書く | 本出力は成果物だが、プレビューは検証用の付随物であり、「本番を壊さずに目で確かめる」ことが dry-run の用途そのものであるため |
