## 4.8 輪郭の粗さと縁の汚染を測る

### 合格を返す指標の下で欠陥が残っていた

実写（白い不織布の上の黒いリモコン、4284x5712）を最良設定
（`--bbox` + `--tolerance 60`）で切り抜くと、`halo_ratio` 0.0011 /
`separability` 54.7 / `edge_width` 6.0 と**どの指標も合格を返す**。それでも
拡大すると上辺・下辺がギザギザで、不織布の灰色の粒が輪郭に張り付いている。

指標が欠陥を見ていなかった。原因は 2 つとも構造的である。

- `halo_ratio` は「局所背景と ΔE≤3」という**絶対的な基準**で縁を数える。
  繊維のばらつきが ΔE 5〜10 ある布では、張り付いた繊維がその基準を外れる。
  白いスタジオ背景（ばらつき ΔE 0.4）を前提に置いた値だった
- `edge_width` はアルファ**遷移の幅**しか見ない。輪郭が輪郭に沿って 1〜3px で
  蛇行しても、各点の遷移幅は変わらないので値が動かない

**測れないものは改善できない。** 後続の Phase（トライマップ入力、matting と
境界平滑化、照明場の背景モデル）はこの 2 つが改善したかで合否を決めるので、
まずここを測れるようにする。

### `contour_roughness` — 自分自身を滑らかにしたものを正解の代わりにする

実素材に正解の輪郭は無い。だが「**自分自身をぼかしたもの**」なら必ず作れる。

1. 二値マスク M の輪郭画素 P を取る（画像の外周と `--bbox` の辺に由来する
   境界は数えない。`boundary_separability` と同じ理由）
2. M を σ = 2.0 × scale px 相当（箱ぼかし 3 回、半径 r）でぼかし、0.5 で
   再二値化した参照 Q の輪郭を取る
3. P の各画素から Q の輪郭までの距離（3-4 チャンファー）を、**平滑化が届く
   距離 3r で頭打ちにして**平均し、scale で割って返す

滑らかな輪郭はぼかしても 0.5 の等高線が動かないので 0 になり、蛇行していれば
その分がそのまま距離として出る。

**中央値ではなく平均を採る。** チャンファー距離は 1px 刻みでしか測れないので、
中央値は「0 か 1px か」の 2 値にしかならず、値の分布に段ができる。しきい値を
その段の上に置くと、しきい値が解像度の関数になってしまう——0.15 は
「中央値 1px ÷ scale」が 0.15 を超える範囲、すなわち長辺 6600px までの素材でしか
発火しない、という具合である。平均なら「輪郭画素の何割が参照から離れているか」が
連続量として出る。

**ただし平均には罠がある。** 距離は u8 に畳んであるので 85px で飽和する。
平滑化で参照輪郭がまるごと消えた画素——細いストラップ、背景を飲み込んで崩れた
マスク——では、距離が近傍に参照を持たないまま伸びて飽和値に達し、そのまま平均に
入る。S9（明度が背景を横切る淡色商品）が 35.026 と出ていたのがこれで、
**輪郭の粗さではなく u8 の上限を報告していた**。平滑化が届く距離は箱ぼかし
3 回ぶんの `3r` しかないのだから、それより遠い距離に情報は無い。画素ごとに
3r で頭打ちにしてから平均する。S9 は 2.493、R4 既定は 13.996 から 2.442 へ
落ち、飽和していなかった点（クリーン側の全部）は 1 ビットも動かない。

頭打ちに掛かる輪郭画素の割合は、**クリーン側の 13 点すべてで 0.0%**（実写の
照明を持つ R7 assisted も 0.0%）、壊れた切り抜きでは S9 41.2% / R4 既定 45.3% /
R1 既定 11.9% になる。抑えているのは欠陥側の暴走だけである。

`scale = max(1, 長辺 / 1000)` で割るのが要点である。**EC の納品先は長辺 1000px
前後**なので、20MP で 1px のギザギザは縮めれば 0.18px となって見えない。逆に
1000px の素材で 1px なら見える。知りたいのは「縮めたときに見える大きさ」である。

### `rim_contamination` — 絶対値ではなく 2 択で問う

`halo_ratio` の基準が絶対値だから布で破れた。ならば**どちらに近いかだけ**を問えばよい。

境界の内側 3px（換算）の帯にある前景画素 C について、窓（半径 8px 換算）内の
完全に透明な画素の平均 μ_B と標準偏差 σ_B、完全に不透明かつ帯より内側の μ_F と
σ_F を取り、

```text
d_B = |C − μ_B| / (σ_B + σ0)      d_F = |C − μ_F| / (σ_F + σ0)
汚染 ⇔ d_B × 2.0 < d_F
```

で数える。`|·|` は**線形 RGB** 3 チャンネルのユークリッド距離、σ は 3 チャンネルの
分散の平均の平方根、σ0 = 0.015 は JPEG のノイズ床である。
`|μ_F − μ_B| < 2.0 × (σ_B + σ_F + 2σ0)` の画素は判定しない（淡色商品 × 白背景では
2 択そのものが雑音になる。`refine` の `min_separation` と同じ思想）。

**散らばりで割るのが設計の肝である。** 平均色までの距離をそのまま比べていた頃、
この指標は**定義上ほとんど 0 になっていた**。`refine` は色から解いたアルファで縁を
半透明にするので、最終マスクで 128 以上の帯画素は「refine 自身が F/B から読んだ
アルファが 0.5 以上」の画素に限られる。そこへ同じ発想の物差しを当てても、
**refine が既に一貫させたものを同じ物差しで測り直す**ことにしかならない。正解が
「帯の半分は純粋な背景」と言う R1 assisted で 0.028 しか出なかった。

見落としていたのは、不織布の**暗い孔・繊維の影**である。黒い商品との混色
（アルファ 0.3〜0.6）と、平均色からの距離では区別がつかない。区別できるのは
「その色は背景テクスチャの**散らばりの範囲内**か」だけである。σ で割ると繊維の影は
d_B が小さくなり、正しい混色はどちらの分布からも離れているので大きくなる。
同じ R1 assisted が 0.251 へ、20MP の実写リモコンが 0.019 から 0.096 へ上がった。

**σ0 が無いとクリーンな背景で壊れる。** 単色で撮れた背景は σ が 0 になり、正しい
混色画素まで「散らばりの外」へ出て、判定が平均色の最近傍へ退化する。

**2 倍の要求は σ で割っても残す。** 正規化が効くのは σ が素材ごとに違うとき
（布の繊維は σ が大きく、無地の紙は σ0 に埋もれる）であって、クリーンな合成背景では
合成式 C = aF + (1-a)B の境目がちょうど a = 0.5 ——帯の画素がいちばん集まって
いるところ——に来て、**正しく混色している画素が軒並み汚染に転ぶ**（8px かけて
溶ける輪郭、合成 S4、正解では汚染 0% で 26.3%）。2 倍を要求すると条件は
「色から読めるアルファが 1/3 を下回る」になり、同じシーンが 0.0% へ落ちる。
**倍率で余裕を作る話と、何を物差しにするかの話は別である。**

### なぜ線形 RGB か

**「アルファが 1/3 未満」という読み替えは線形でしか成り立たない。** 黒い商品
（線形 0.017）と白い背景（線形 0.94）を真アルファ 0.5 で混ぜた画素は sRGB 188 に
来て、背景まで 67・前景まで 188 と**背景に 2.8 倍近く**見える。ガンマが暗部を
引き伸ばすからで、そのまま 2 倍を掛ければ正しい混色が汚染に転ぶ。Lab の ΔE も
同じ理由で使えない（`ΔE(C,B)/ΔE(C,F) = a/(1−a)` が成り立たない）。

両方を実装して 27 点で比べた。**暗い商品で偽の信号が 6 分の 1 になり、窓は
3 倍広く取れる。**

| | sRGB (σ0 = 4) | 線形 (σ0 = 0.015) |
|---|---|---|
| クリーン側の最大 | 0.007（R7 assisted） | 0.005（S10） |
| 欠陥側の最小 | 0.042（R7 既定） | 0.091（R7 既定） |
| 窓 | [0.014, 0.021] | [0.011, 0.045] |
| Spearman vs 正解 | 0.858 | 0.891 |
| S8 黒商品（正解 0.000） | 0.006 | 0.001 |
| R4 既定（正解 0.224） | 0.220 | 0.222 |
| 20MP 実写リモコン（最良設定） | 0.102 | 0.096 |

σ0 は JPEG のノイズ床（sRGB でおよそ 4 階調）を**中間調で線形へ読み替えた**値で
ある。線形の 1 階調ぶんは明るさで変わる（sRGB 35 付近で 0.0044、128 付近で
0.015、250 付近で 0.036）ので、1 つの数では全部の明るさに合わない。0.005 /
0.01 / 0.015 / 0.02 を較正表で比べると、大きいほどクリーン側の偽の信号が速く
落ちて欠陥側はゆるやかにしか落ちないので、素直な読み替えがそのまま窓の広い側に
あった。線形値は 14bit の固定小数で持つ——箱和の足し引きを f32 でやると桁落ちが
走査順に依存しうるが、整数なら引いた値は足した値とビット単位で一致する。

### 判定できなかった画素を、黙って分母から外さない

分母は「判定できた画素」である。それ自体は正しい——F と B が散らばりの中で
重なっていればどちらに近いかは答えようがない——が、**判定不能が帯の大半を
占めたまま割合を返すと、残りについて「汚染されていない」と言ったことになる。**
R4（暗い机 + 白商品）の既定値がそれで、帯 14,160 画素のうち真に背景の 3,172 画素が
全部判定不能に落ち、残りから 0.000（＝合格）を返していた。

1. **窓に確定前景が無ければ、いちばん近い「前景を持つ格子セル」から借りる。**
   局所前景 F は「窓の中の、帯より深い完全不透明画素」なので、細い構造や背景を
   薄く飲み込んだ舌のような領域には定義上 1 つも無い。そこで諦めると
   **欠陥が大きいほど判定不能が増えて値が下がる**という逆立ちが起きる。
   借りてよいのは 16 窓（換算 128px）までで、それより遠い F は照明も
   シェーディングも別物なので使わない
2. **それでも判定できた画素が帯の半分に満たなければ `None` を返す。**
   S9（明度が背景を横切る淡色商品）がこれで、借りられる範囲に前景が無く 44% しか
   判定できない。実写リモコンの tolerance 12 も同じく `None` になる

**片側判定（B の分布だけで「背景の散らばりの内側か」を問う）は採らなかった。**
実装して測ると、R4 既定の真に背景な画素は局所背景の平均から 2〜6σ 離れている
——フィルはそこで止まったのだから当然である——のに対し、S9 の**真に商品**な
画素は 0.5σ しか離れていない。順序が逆転しているので、係数をどう選んでも R4 を
拾えば S9 が誤警報する（実測 0.326、正解 0.000）。借りた F にも
`MIN_RIM_SEPARATION_SIGMA` が掛かるので、F と B が見分けられない場所は判定
不能のままになる——これが片側判定に無い安全装置である。

### 局所平均は縮めた格子で取る

局所の平均と分散は `scale` で縮めた格子の上で箱和として取り、帯画素からは最近傍で
引く。帯画素ごとに窓を全走査すると 20MP で 10⁹ に達する。二乗和は 3 チャンネル
まとめて 1 本しか持たない——欲しいのは「3 チャンネルの分散の平均」で、
`(Σ(r²+g²+b²)/n − (μr²+μg²+μb²))/3` と書けるためである。全面の積分画像
（8 面 × 12MP × f64 = 768MB）は持たない——4.7 でタイルに切ったのと同じ制約である。

### 較正

`tests/real_backgrounds.rs` の 27 点で較正した。実写の背景写真
（`tests/fixtures/backgrounds/`）の上に、正解の被覆率が解析的に分かる合成商品を
**線形 RGB で**載せたシーン（R1〜R7）を、`defaults` と `assisted`
（bbox + hint に従って上げた tolerance）の 2 通りで回す。合成背景の S1〜S12 と
同じ表に並べ、正解由来の `contour_error`（真の輪郭からの距離の平均）と
`rim_truth`（帯の前景画素のうち真の被覆率が 0 の割合）と突き合わせる。

**どのシーンがクリーンかは、指標ではなく正解が決める。** 受け入れ基準が名指しする
シーンをクリーン側に置くと、較正がテストを見てテストが較正を見ることになる。
母集団は正解由来の値だけで分ける。

| 指標 | クリーン側 | 欠陥側 | どちらでもない |
|---|---|---|---|
| `contour_roughness` | `contour_error < 1.0`（13 点） | `≥ 3.0`（14 点） | S3 1.30 / S7 1.11 |
| `rim_contamination` | `rim_truth < 0.01`（13 点） | `≥ 0.10`（13 点） | R4 assisted 0.031 |

境目にも理由がある。輪郭誤差の 1.0 は「納品寸法で 1px を切るずれは見えない」、
3.0 はこの節の冒頭で「1000px の素材で 3px なら見える」と書いた、その 3px で
ある。帯の 1% は点々としか残らないが、10% は帯（換算 3px）の 1 割が純粋な背景
ということで、輪郭ぐるりに 0.3px の縁が乗っているのと同じになる。

**R7 はクリーン側の対照である。** 他の R シーンはすべて欠陥側にあり、誤警報の
較正が合成の S シーンだけに依っていた。手持ちに「きれいなスタジオ背景の実写」が
無いので、`fabric_b` を σ 6px 相当でぼかして繊維だけを消し、振幅 1.5 の
センサーノイズを乗せ直したものを使う。照明勾配と実写のノイズ床は残る。

規則は「**クリーンなシーンの最大値の 2 倍以上、かつ欠陥シーンの最小値の 1/2 以下**」。

| | クリーン側の最大 | 欠陥側の最小 | 群間比 | 窓 | 採用 |
|---|---|---|---|---|---|
| `contour_roughness` | 0.082（S5 3px ストラップ） | 0.316（R7 既定） | 3.9 倍 | [0.163, 0.158] | 0.16 |
| `rim_contamination` | 0.005（S10） | 0.091（R7 既定） | 17.0 倍 | [0.011, 0.045] | 0.02 |

両側の余裕:

| | 値 | しきい値との比 |
|---|---|---|
| 粗さ・クリーン最大 S5（3px ストラップ） | 0.082 | 1.96 倍 |
| 粗さ・クリーン 2 番目 S3（淡色商品） | 0.062 | 2.58 倍 |
| 粗さ・欠陥最小 R7 既定 | 0.316 | 1.97 倍 |
| 粗さ・実写リモコン（最良） | 0.391 | 2.44 倍 |
| 汚染・クリーン最大 S10 | 0.005 | 3.76 倍 |
| 汚染・実写の照明を持つ R7 assisted | 0.003 | 6.7 倍 |
| 汚染・欠陥最小 R7 既定 | 0.091 | 4.53 倍 |
| 汚染・実写リモコン（最良） | 0.096 | 4.8 倍 |

**粗さの窓は 3% だけ空かない。** 規則が要求するのは [0.163, 0.158] で、
両側の比を最大にする値（幾何平均）0.16 を採っても 1.96 倍 / 1.97 倍にしかならない。
それでもこの値を残すのは、(1) 27 点のどれ 1 つも誤分類しない——クリーン側の最大
0.082 と欠陥側の最小 0.316 のあいだに値を持つ点が無い——こと、(2) 届かない原因が
S5 ただ 1 点に特定できており、それが幅 3px、**平滑化参照の σ = 2px より細い構造**
だからである。指標の分解能より細いものを 1 つ含んだために余裕が 1.96 倍になった、
という状態で警告そのものを外すと、実写で見えている欠陥（0.391）を誰も報せなく
なる。規則どおりに外すべきときは、群間比が 2 倍を割ったとき——2 つの群が
そもそも分離していないとき——である。

正解との順位相関（Spearman）:

| | 全点 | `defaults` 除外 |
|---|---|---|
| `contour_roughness` | ρ=0.833（27 点） | ρ=0.759（20 点） |
| `rim_contamination` | ρ=0.891（26 点） | ρ=0.844（19 点） |

**`defaults` を除いた側も見る。** R シーンの既定値は切り抜きそのものが失敗して
いる壊滅ケースで、そこだけで順位が付いてしまうと「実用域で正解と同じ向きに動くか」を
確かめたことにならない。標本が 3 分の 2 に減り、値の幅も桁で狭まるぶん同着が
増えるので、下限は全点の 0.7 に対して 0.5 に置いてある。

実写リモコンの実測（`--bbox 0,0.354,0.9834,0.662 --normalized`）:

| tolerance | `halo_ratio` | `contour_roughness` | `rim_contamination` | 発火 |
|---|---|---|---|---|
| 12 | 0.163 | 1.663 | null | HALO_REMAINS / CONTOUR_ROUGH / SUBJECT_TOUCHES_EDGE |
| 40 | 0.177 | 1.214 | 0.161 | HALO_REMAINS / CONTOUR_ROUGH / RIM_CONTAMINATED |
| 60（最良） | 0.001 | 0.391 | 0.096 | CONTOUR_ROUGH / RIM_CONTAMINATED |

**最良設定でも 2 つとも発火する。** これが Phase 1 の成果である——旧来の指標は
同じ画像を「合格」と呼んでいた。tolerance 12 で汚染が `null` になるのは、背景を
大きく飲み込んだ結果、帯の半分以上で判定できなくなるためである（下記）。

### 縁の汚染が見落とすもの

**局所前景そのものが背景であるとき、2 択は答えを持たない。** マスクが背景を大きく
飲み込むと、窓の中の「確定前景」が背景色になり、帯の画素は素直に前景寄りと出る。
R7 既定（正解 0.655 に対し 0.091）がこれで、値は出るが正解よりずっと小さい。
飲み込みが極端なら判定できる画素が帯の半分を割って `None` になる。どちらの場合も
`BBOX_RECOMMENDED` / `HALO_REMAINS` / `contour_roughness` の側で捕まる。

同じ理由で、**手持ちの実写背景はどれも `defaults` ではクリーンな点にならない**。
照明の起伏が大きく（R7 の外周 ΔE は p90 16.7 / max 33.2）、既定の tolerance 12 は
推定背景色からの絶対的な色差の上限なので背景の隅まで届かない。R7 既定でも
前景比率 0.469（正解 0.375）、`contour_error` 65.1 で切り抜きそのものが失敗して
いる。ぼかしを σ 24 まで強めても、`fabric_a` に替えても、700/500/400px へ
切り出しても結論は変わらなかった。**クリーン側の対照として使えるのは
`assisted` の側だけである。**

`CONTOUR_ROUGH` に `hint` は付けない。今の kiri に粗さを直すノブが無く、
**実行できない助言は助言が無いより悪い**（信頼度 low で bbox を勧めないのと
同じ判断）。`RIM_CONTAMINATED` の hint は **`HALO_REMAINS` が一緒に出ている
ときだけ**付ける。縁が「背景色のまま」残っているなら tolerance を上げれば減るが、
汚染だけが出ている状態は別物で、S7（中間グレー商品 + 落ち影）は tolerance を
どちらへ動かしても値が動かない——縁に乗っているのが背景色そのものではなく、
影や繊維との混色だからである。文面は `HALO_REMAINS` と同じにする。同じ原因に
別の言い方をすると、エージェントは手が 2 つあると読む。

### 所要時間と確保量

12MP（3000x4000）での `diagnose()` は **129.5ms → 150.9ms**（M4 Pro, release、
5 回の最短）。内訳は `halo_ratio` 34.4ms / `edge_width` 8.2ms / 新しい 2 つ
108.4ms である。

**「着手前より速い」は誤りだった。** 同じ場所で `halo_ratio` の「境界近傍か」の
判定を 7x7 の数え上げからチェビシェフ距離変換へ置き換えたので、**その関数は
120.7ms から 34.4ms へ 3.5 倍速くなった**（値は 1 ビットも変わらない）。だが
新しい 2 つが 108ms を足すので、**全体では +21ms** である。速くなった部分だけを
見て全体を語っていた。

確保するものは次のとおり。`diagnose()` は 3 つを順に回すので、ピークは同時に
生きているものの和であって、表の合計ではない。

| 確保するもの | 大きさ | 12MP・商品が 38% の場合 |
|---|---|---|
| 前景でない画素からの距離（`halo_ratio`） | 全面 × 1B | 12.0MB |
| 平滑化する二値マスク（粗さ） | 全面 × 1B | 12.0MB |
| 距離場（粗さ、輪郭の枠 + 3r+2） | 枠 × 1B | 4.8MB |
| 距離場（汚染、輪郭の枠 + 帯 + 1） | 枠 × 1B | 4.7MB |
| 局所色の格子 2 面（汚染） | (枠 ÷ scale)² × 24B × 2 | 14.9MB |
| 最近セルの伝播（汚染、一時） | (枠 ÷ scale)² × 8B | 2.5MB |

**距離場と格子は面積ではなく商品の大きさで決まる。** ぼかしも距離変換も輪郭の
外接矩形を必要な余白だけ広げた枠の中で閉じる。全面を確保していた頃は
12MP で 12MB × 2 だった。

`diagnose()` の前後で `ps` を読むと RSS の増分は **0MB** と出る。これは
「増えなかった」ではなく「`cutout()` が確保して解放したページを使い回した」の
意味である——アロケータは解放したページを OS へ返さないので、切り抜きの後に
測るかぎりこれ以上のことは分からない。サンプラーでピークを追っても同じ理由で
0 になる。

計測は `cargo test --release --test edge_quality -- --ignored --nocapture` の
`print_the_refine_cost_on_large_inputs` が出す。較正の表は
`cargo test --release --test real_backgrounds -- --ignored --nocapture` である。

## 4.13 探索を kiri 側に持たせる

エージェントが実写を切るには `info` → `cutout --bbox` → `cutout --bbox
--tolerance` の 3 手が要る。4.11（照明場）と 4.12（モデル）を足した後も、
「場を使うか」「許容量をどこに置くか」の選択は残ったままである。

kiri は決定的で 1 回が数秒なので、**候補集合を kiri が総当たりして指標で選ぶ**
ほうが、エージェントが JSON を読んで手を打つループより速く、確実で、記録が残る。
`--optimize` はその 3 手を kiri の中へ畳む。AI には決定の記録（`optimize`
ブロック）だけを渡す。

### 候補集合

固定の格子で、順序も固定である。

| 軸 | 候補 | 1 通りに畳む条件 |
|---|---|---|
| `bbox` | 無し / `subject.normalized_bbox` | `--bbox` を明示した／主体の信頼度が `low` |
| `tolerance` | 12 / 20 / 30 / 45 / 60 | `--tolerance` を明示した |
| `background_model` | `auto` / `flat` | `--background-model` を明示した／`auto` が `flat` を選んだ |

最大 2 × 5 × 2 = 20 通り。許容量の 12 は既定値、60 は実写（不織布の上の
リモコン）で `HALO_REMAINS` の hint に従って到達した値で、そこが最良だった。
あいだを 20 / 30 / 45 で埋める。等間隔にしないのは、飲み込む量が許容量に対して
線形ではないからで、低い側ほど 1 刻みの効きが大きい。

`auto` が 1 色を選んだ画像で `flat` を別候補にしないのは、その 2 つが
まったく同じ計算になるためである。`low` の主体から矩形を作らないのは
4.9 と同じ規約で、商品ですらない領域へ切り抜きを誘導しないためである。

**明示は探索より強い。** `--tolerance 30 --optimize` は「30 に固定して残りの軸を
探す」の意味になる。`--tolerance` は `default_value_t` を持つので値だけでは
明示を検出できないが、既定値を `Option` にすると `kiri schema` の `default` から
12 が消え、**指定しなくても何が効くのかが読めなくなる**。表示は変えずに、
clap の `ValueSource` を見た結果を `CutoutArgs::fixed` へ畳んで下流へ運ぶ。
`batch` の spec では `Some` がそのまま明示なので、この迂回は要らない。

### 2 段の探索

1. **探索段** — 長辺 `SEARCH_LONG_EDGE`（1500）px へ縮めた画像で、全候補を
   `refine` 抜き（フィル + フェザー + despill）で回す。指標と警告 code だけを
   残して**画像はその場で捨てる**。20 候補ぶんの 1500x1500 RGBA は 180MB ある
2. **最終段** — 探索段の上位 `FINALISTS`（2）を、原寸・利用者の設定そのままで
   順に回す。致命的な警告も品質の警告も出ない候補に当たったらそこで打ち切る

保持するのは「今までの最良の `CutoutResult`」1 つだけで、負けた候補の画像は
即捨てる。選ばれた結果はそのままキャンバス配置・書き出し・preview へ流れる
（**もう 1 回走らせない**）。

空間的な指示（4.9）は `Constraints::resampled` で縮小版へ最近傍で写す。
寸法の合わない指示は丸ごと無かったことにされる規約なので、写さなければ
**探索だけが指示の無い世界で行われる**ことになる。最終段は原寸の指示そのままで
回るので、書き出される画素は影響を受けない。

### スコア（辞書式）。**2 つの段は別の物差しで並べる**

最終段（原寸・利用者の設定そのまま）:

1. 致命的な警告の数 + 前景比率の崩れ（少ないほど良い）
2. **測れなかった診断値の数**（halo / 粗さ / 縁の汚染のうち `null` の個数。少ないほど良い）
3. 品質の重み和 `rim_contamination / RIM_CONTAMINATION_WARN + contour_roughness
   / CONTOUR_ROUGH_WARN + halo_ratio / HALO_WARN`（小さいほど良い）
4. `separability`（大きいほど良い。測れなければ 0）
5. 同点なら小さい `tolerance`、次に bbox 無し、次に `auto`

探索段（縮小・`refine` 抜き）:

1. `NOT_SEPARABLE` / `FOREGROUND_TOO_SMALL` / `FOREGROUND_TOO_LARGE` の数 + 崩れ
2. `separability`（大きいほど良い。**測れなければ最下位**）
3. 同点の決め方は最終段と同じ

しきい値は `cutout::diagnostics` の定数をそのまま引く。複製すると較正で定数を
動かしたときに、警告とスコアが別の世界で判断することになる。`null` の項は
1.0（ちょうどしきい値の上）として数える——0 と扱うと「測れなかった候補」が
最良として勝ってしまい、大きな値を入れると測れないだけで失格になる。
比較は `total_cmp` なので、同じ入力からは必ず同じ並びが出る。

#### なぜ段ごとに物差しを変えるのか

**最初の実装は 1 つの物差しを両方の段で使い、探索段が最終段と別の目的関数を
最適化していた。** `refine`（境界の再分類と平滑化）を抜くと、次の 2 つが
壊れる。

| 量 | 探索段で何が起きるか | 実測 |
|---|---|---|
| 外周接触（`SUBJECT_TOUCHES_EDGE` / `BBOX_RECOMMENDED`） | 縁に背景が残って前景が外周へ届く。**原寸では 1 つも出ない警告が探索段では全部に出る** | 実写で矩形つきの候補 6 つすべてが探索段でだけ出した |
| halo / 輪郭の粗さ / 縁の汚染 | 桁が変わる。しかも**倍率が候補ごとに違う**ので、寸法の換算では戻せない | 縁の汚染が 4〜6 倍、粗さが 3〜5 倍 |
| `separability` | ほとんど動かない。**境界の内側と外側を元画像の色で測る**量だから | 55.97 対 56.57、52.64 対 53.16、47.42 対 47.54（1% 以内） |

症状は具体的だった。`remote.jpg --bbox ... --background-model flat --optimize`
で、原寸の 1 位（tol 60、致命 0 / 品質 4.88）が探索段の 4 位へ落ち、原寸で
致命 1 の tol 12 が選ばれていた。探索段の第 1 項（致命の数）が信用できない量で
決まり切っていたためである。段を分けた後は tol 60 が選ばれる。

前景比率から出る致命（`FOREGROUND_TOO_SMALL` / `_TOO_LARGE`）と
`NOT_SEPARABLE` は `refine` の前に決まるので、探索段でも数えてよい。
前景比率そのものも寸法にも `refine` にも依らない。

#### 「測れなかった数」を品質より先に置く

`null` を 1.0 として数えるだけでは足りなかった。診断が 3 つとも測れない候補の
重み和は 3.0 になるが、境界がまともに引けている候補の重み和も 1〜3 に収まる
ので、**「何も測れなかった」が中位の成績として通る**。実測では、商品の無い
背景プレート（`desk_a.jpg`）で前景比率 0.0001 のほぼ空のマスクが重み和 2.0 で
探索段の 1 位に来ていた。診断が 3 つとも `null` になるのは、たいてい**測る
対象の境界が無い**からである。重み和より先に `null` の数を見れば、境界を
測れる候補が測れない候補に勝つ。

#### 致命の数え方を 2 つ直した

設計では致命的な警告を `NOT_SEPARABLE` / `FOREGROUND_TOO_SMALL` /
`FOREGROUND_TOO_LARGE` / `SUBJECT_TOUCHES_EDGE` の 4 つとしていた。R1〜R7 で
測ったところ 2 つ落ちたので、それぞれに 1 手入れた。

| 直し | 何が起きていたか | 入れた後 |
|---|---|---|
| `BBOX_RECOMMENDED` も致命に数える（最終段） | R6 で矩形を使わない tolerance 60 が選ばれ、輪郭誤差 5.91 → **84.00** | 3.35（`assisted` の 5.91 より良い） |
| 前景比率の崩れを致命 +1 | R3 で tolerance 60 が選ばれ、商品が 100% 飲まれて輪郭誤差 24.25 → **119.10** | tolerance 12 が選ばれる（それでも届かない。下記） |

**`BBOX_RECOMMENDED` と `SUBJECT_TOUCHES_EDGE` は同じ事実の別の読み方である**
（4.5 の「見切れと読むか前景の失敗と読むか」）。`collect_warnings` はどちらか
一方しか出さないので、片方だけを数えると**bbox 無しの候補だけが外周接触を
無料で通過する**——bbox がまさに直す失敗なのに、である。

ただし**順位の上で同じ重さで扱うことと、利用者に手詰まりを告げることは別の
判断である。** `OPTIMIZE_NO_CLEAN_CANDIDATE` は残り 4 つだけを数える。
`BBOX_RECOMMENDED` は「この矩形を渡せ」と矩形つきで次の一手を言っている警告で、
そこへ「候補をすべて試したが駄目でした、撮り直すか `--segment isnet` を」を
重ねると、**同じ結果に対して 2 つの矛盾した指示が並ぶ**。

もう 1 つは淡色商品の問題で、**スコアは `eaten`（商品をどれだけ削ったか）を
見られない**。許容量を上げて商品ごと飲まれた結果は、halo と縁の汚染が減った
**良い数値**として現れ、残った断片が外周に触れていなければ警告も 1 つも出ない。

崩れは 2 通りに測る。

| 段 | 何と比べるか | なぜ |
|---|---|---|
| 探索段 | 同じ bbox・同じモデルの**列**を許容量の昇順に見て、1 段前と比べる | 5 点そろうのは探索段だけ。落ち込みは以降へ伝播させる |
| 最終段 | **同じ候補の探索段の前景比率**と比べる | 前景比率は寸法に依らない量なので 1500px と原寸を直接比べられる。列の相方が要らない |

**最初の実装は最終段でも列の比較を使っていて、そこが穴だった。** 原寸まで
回るのは `FINALISTS`（2）だけで、その 2 つが同じ列にいるとも隣接しているとも
限らない。実測でも **R3 では順位を変えていない**（列の関門を入れる前 119.10、
入れた後 119.70。この素材は矩形が作れない時点で詰んでいる）。実際に効いて
いるのは最終段の自己比較のほうで、実写の 60 / bbox / auto がまさにそれである
（探索段 0.2049 → 原寸 0.0664、67.6% の落ち込み）。

`FOREGROUND_COLLAPSE`（0.30）はその下に、`refine` による正常な揺れの上に取る。
崩れていない候補の search → final の落ち込みは実測で最大 19.5%（R3）、実写の
tol 45 では 0.9% だった（表は下の一致率の節）。

`score.fatal` には崩れを足さない。あちらは**出た警告の数**で、
`OPTIMIZE_NO_CLEAN_CANDIDATE` が数える対象と重なっていなければならない
——足すと「`fatal` が 0 でないのに警告が出ない」状態が生まれ、`kiri schema` の
notes がそのまま嘘になる。順位の第 1 項は `fatal + collapsed` で、
`collapsed` は候補ごとに真偽で JSON に出す。

### R1〜R7（`--optimize` は bbox 無し・既定値から出発）

`assisted` は「エージェントが kiri 自身の hint に従って 3 手で到達する設定」で、
**矩形は正解由来**（真の輪郭 + 余白 5%）である。`--optimize` が使えるのは色から
測った `subject.normalized_bbox` だけなので、同じ矩形は使えない。

| シーン | `assisted` の tol | 輪郭誤差 | rim 正解 | `optimize` の tol / モデル | 輪郭誤差 | rim 正解 | eaten |
|---|---|---|---|---|---|---|---|
| R1 不織布 + 黒商品 | 60 | 4.23 | 0.176 | 60 / flat | **2.54** | **0.156** | 0.0000 |
| R2 照明勾配の不織布 | 60 | 1.11 | 0.065 | 45 / field | 1.11 | 0.065 | 0.0000 |
| R3 不織布 + 淡色商品 | 12 | 24.25 | 0.754 | 12 / flat（矩形なし） | **119.70** | **0.999** | 1.0000 |
| R4 暗い机 + 白商品 | 60 | 0.41 | 0.000 | 45 / flat | 0.41 | 0.000 | 0.0000 |
| R5 不織布 + 3px ストラップ | 60 | 9.52 | 0.205 | 60 / flat | **2.24** | **0.152** | 0.0034 |
| R6 柔らかい輪郭 8px | 60 | 5.91 | 0.134 | 45 / flat | **3.35** | **0.127** | 0.0000 |
| R7 照明勾配のある紙 | 60 | 0.41 | 0.000 | 30 / field | 0.41 | 0.000 | 0.0000 |

7 点中 6 点で `assisted` と同等以上、うち 3 点は輪郭誤差が半分以下になった。
**R1 / R5 / R6 で探索が 3 手ループに勝つのは、矩形が粗いほうが良いから**である
——`assisted` の矩形は正解に張り付いているので、フィルが矩形の辺で止まった
境界が輪郭として数えられてしまう（4.9 の「矩形の辺は輪郭として数えない」規約は
診断側の話で、正解側の `contour_error` には矩形そのものの近さが効く）。

#### R3 だけ届かない。そしてそれは素材の限界である

R3 の主体は**信頼度 `low`** と判定される（布との ΔE が 12 前後しかなく、塊として
まとまらない）。`low` の矩形を根拠に動かないという規約から、R3 の候補集合には
**矩形を使う候補が 1 つも無い**。矩形が無ければこの素材で商品と背景を分ける
許容量は存在せず、10 候補すべてで `SUBJECT_TOUCHES_EDGE` が出る。

しきい値をベンチに合わせて緩めることはしない。テストは R3 だけ期待値を
**現状の値で固定**し（`tests/real_backgrounds.rs` の定数）、悪化は検出できる状態にしてある。
利用者には `OPTIMIZE_NO_CLEAN_CANDIDATE` が「候補をすべて試したが致命的な
警告が残った」と報せ、hint が撮り直しか `--segment isnet` を案内する。
**20 通り試して駄目だったという事実そのものが情報である。**

### 縮小探索の順位はどれだけ当たるか

**比較子は本番のものをそのまま呼ぶ**（探索段は `better_search`、原寸は
`better_final`）。崩れの印も本番と同じ手順で付ける。ここで物差しを書き写すと、
表は「書き写した物差しの一致率」を語ることになる。

右端の列は `FOREGROUND_COLLAPSE`（0.30）の余裕を確かめるための数で、
**崩れていない候補**が縮小・`refine` 抜きから原寸へ移ったときの前景比率の
落ち込みの最大値である。

| 素材 | 候補 | 探索段の 1 位 | 原寸の 1 位 | 原寸 1 位の探索順位 | search→final の落ち込み |
|---|---|---|---|---|---|
| R1 不織布 + 黒商品 | 20 | 45 / box / flat | 60 / box / auto | 3 | 10.9% |
| R2 照明勾配の不織布 | 20 | 60 / box / auto | 45 / box / auto | 2 | 6.2% |
| R3 不織布 + 淡色商品 | 10 | 12 / none / flat | 12 / none / flat | 1 | 19.5% |
| R4 暗い机 + 白商品 | 20 | 45 / box / flat | 12 / none / flat | 20 | 2.4% |
| R5 不織布 + 3px ストラップ | 20 | 45 / box / flat | 60 / box / auto | 3 | 10.8% |
| R6 柔らかい輪郭 8px | 20 | 60 / box / flat | 12 / box / flat | 18 | 10.2% |
| R7 照明勾配のある紙 | 20 | 30 / box / auto | 30 / box / auto | 1 | 0.7% |
| 実写リモコン tol 45（4284x5712 → 1500px） | — | — | — | — | 0.9% |
| 実写リモコン tol 60（同上、**崩れた側**） | — | — | — | — | **67.6%** |

落ち込みの最大は 19.5%（R3）で、実際に崩れた候補の 67.6% との間に 0.30 が
入っている。

**順位の一致率は低い。7 点中 3 点しか上位 2 つに入らない。** それでも 7 点中
6 点で `assisted` と同等以上に届いている（上の表）のは、**この列が測って
いるのが「2 つの代理指標どうしの一致」であって「出てくる絵の良さ」では
ない**からである。R4 がその例で、全 20 候補を原寸で回したときの `better_final`
の 1 位は 12 / none / flat（探索段 20 位）だが、探索が実際に選んだ
45 / box / flat の輪郭誤差は 0.41 で `assisted` と同じ、削った量は 0 である。
つまり原寸の 1 位を外したこと自体は品質の悪化を意味しない。

段を分ける前（1 つの物差しを両方に使っていた頃）は R1 が 1 位、R2 が 2 位、
R7 が 1 位だった。**一致率は下がったが、品質は上がっている**——揃っていたのは
探索段が原寸と同じ「信用できない量」を見ていたからで、揃っていること自体には
値打ちが無かった。順位の一致を目的にするとその誤りへ戻る。

`FINALISTS` を 2 に保っているのは、1 位が原寸で崩れたときに 2 位が受けるため
であって、原寸の 1 位を毎回拾うためではない（次節）。

### 原寸で何個回すか（15 秒の目標）

原寸 1 回が 24.5MP で約 4.4 秒、1500px の探索 1 回が約 0.2 秒である。

| `FINALISTS` | 実写リモコンの総時間 | 選ばれた設定 | 4 指標 |
|---|---|---|---|
| 3 | 18.7 秒（目標超過） | tol 45 / bbox あり / field | fg 0.2037 / halo 0.0295 / sep 53.8 / 粗さ 0.254 |
| **2** | **13.7 秒** | tol 45 / bbox あり / field | 同じ |

選ばれる候補は測った 8 点（R1〜R7 と実写リモコン）すべてで同じだった。
**負けた候補を回すのは順位を確かめるためであって、最良を拾うためではない**
——探索段の 1 位が原寸で崩れたときに 2 位が受ければ足りる。実写ではまさに
それが起き、1 位（tol 60 / box）が原寸で商品を 3 分の 2 まで飲み
（前景比率 0.2037 → 0.0664）、2 位が救っている。

**早期打ち切りはこの素材では効かない。** 不織布の織り目は全候補で
`CONTOUR_ROUGH` を出すので、「品質の警告が 0」に到達する候補が存在しない。
きれいな素材では 1 位で止まるので、原寸は 1 回で済む。

#### 崩れは原寸でも測り直す

実写の 1 位（tol 60 / bbox）は 1500px では崩れず、**原寸でだけ**前景比率が
0.2049 → 0.0664 になる。原寸で回した候補は必ずその場でこれを測ってから
早期打ち切りを判断する（自己比較なので相方が要らない。上の表を参照）。
崩れた候補は「綺麗」ではないので打ち切りは起きず、2 位が回って救う。

抱えるのは**勝っている 1 つだけ**である。負けた候補の結果はその場で落ちる
（24.5MP の切り抜き 1 つが約 120MB あるので、2 つを同時に持たないことに意味が
ある）。実測のピークは下の表のとおりで、**`--optimize` は既定の実行より低い**
——原寸を回す回数が同じで、探索段が扱うのは 1500px だけだからである。

`score.fatal` には崩れを足さない。あちらは**出た警告の数**で、
`OPTIMIZE_NO_CLEAN_CANDIDATE` が数える対象と同じものでなければならない
——足すと「`fatal` が 0 でないのに警告が出ない」状態が生まれ、`kiri schema` の
notes がそのまま嘘になる。順位の第 1 項は `fatal + collapsed` で、
`collapsed` は候補ごとに真偽で JSON に出す。

### 実写（4284x5712、24.5MP、白い不織布の上の黒いリモコン）

| 設定 | fg | halo | sep | 粗さ | 縁の汚染 | 時間 | ピーク RSS |
|---|---|---|---|---|---|---|---|
| 既定値（bbox 無し） | 0.2492 | 0.1264 | 19.6 | 1.239 | null | 7.9 秒 | 892MB |
| 旧「手動の最良」（`--bbox ... --tolerance 60`、`auto` → field） | 0.0664 | 0.0581 | 48.8 | 0.812 | null | 5.0 秒 | — |
| 手動の最良（`--bbox ... --tolerance 60 --background-model flat`） | 0.2037 | 0.0296 | **56.6** | **0.2445** | 0.0611 | **3.0 秒** | — |
| 探索が選んだ設定を明示（`--bbox ... --tolerance 45`） | 0.2037 | 0.0295 | 53.8 | 0.254 | 0.0613 | 4.6 秒 | 809MB |
| **`--optimize`（bbox 無しから出発）** | **0.2037** | **0.0295** | **53.8** | **0.254** | 0.0613 | 13.7 秒 | **873MB** |

**探索は手動の最良と同等の絵に、5 倍の時間を払って到達する。** 選んだのは
tol 45 / bbox あり / `auto`（→ field）で、手で当てた tol 60 + `flat` とは
`separability` で 53.8 対 56.6、粗さで 0.254 対 0.2445 の差がある——どちらも
**目で見て区別が付く差ではない**。払っているのは 3.0 秒に対する 13.7 秒である。

値打ちは速さではなく、**その 3 手を人が打たなくてよいことと、決定の記録が
残ること**にある。加えて、手で決めた設定はアルゴリズムが変わった瞬間に
古くなる——Phase 14 までの変更（照明場・matting）で `auto` の上での最良の
許容量は 60 から 45 へ動いており、古い「最良」の 60 は今では商品を 3 分の 2
まで飲む（前景比率 0.0664。表の 2 行目）。探索は毎回引き直す。

**メモリは増えない。** `--optimize` のピーク（873MB）は既定の実行（892MB）
より低い。原寸を回す回数は同じで、探索段が抱えるのは 1500px の画像 1 枚と
候補 20 件ぶんの指標だけだからである（画像はその場で捨てる）。

暗い机の上の黒いキーボード（12MP、色では分離できない既知の限界、4.5）では
全候補に致命的な警告が残り、`OPTIMIZE_NO_CLEAN_CANDIDATE` が
`SUBJECT_TOUCHES_EDGE` を載せて出る（9.2 秒、479MB）。
**探索が何も改善できなかったことを明示する。**

#### 全候補が致命なら、順位そのものに意味は無い

商品の写っていない背景プレート（`tests/fixtures/backgrounds/desk_a.jpg`）では、
10 候補すべてが `FOREGROUND_TOO_SMALL` を出す（前景比率は最大でも 0.0091）。
**そういう画像で「どれが選ばれたか」を問うても意味が無い**——切り出す対象が
無いのだから、どの候補も等しく成立していない。答えは順位ではなく
`OPTIMIZE_NO_CLEAN_CANDIDATE` のほうで、`data.remaining` が
`FOREGROUND_TOO_SMALL` を載せて「20 通り試したが前景が無い」と言う。

「測れなかった数」を品質より先に置いた（上記）のはこの画像で見つけた穴だが、
直したのは**まともな候補が混じっているときに空マスクが勝つこと**であって、
全候補が空のときの順位ではない。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| 許容量を二分探索する | 順位を決める第 1 項（致命の数）が連続でない。前景比率の崩れは許容量のどこか 1 点で立ち、そこを跨ぐと品質の重み和の比較そのものが意味を失う。他の 2 軸も範疇で、二分できるのは 1 軸だけである。格子なら順位が固定で、記録もそのまま読める |
| 全候補を原寸で回す | フィルだけでも 24.5MP で約 1.9 秒、20 候補で 40 秒。縮小探索の上位 2 つで、測った 8 点すべてで `assisted` と同等以上に届いている |
| `--optimize` の中で `--cleanup` や `--feather` も振る | 軸が増えると候補が掛け算で増える。この 2 つは素材ではなく納品先の都合で決まる値で、探索して選ぶ性質のものではない |
| 探索段でも `refine` を走らせる | 境界処理は 4.10 の実測でフィルと同じ桁の費用を持ち、20 候補ぶん払う理由が無い。**`refine` に依らない量だけを見る**ことでこの費用を避けている（上のスコアの節）。上位 4 つを 1500px で `refine` つきに回し直す中間段は、R1〜R7 が `assisted` に届いているあいだは要らない |
| `eaten` をスコアに入れる | 正解を持たない実行では測れない。前景比率の崩れで代用する（上記） |
### 許容量の格子を細かくする / 伸ばす（不採用）

格子は 12 / 20 / 30 / 45 / 60 の 5 点で固定である。「選ばれた値の両隣をもう 1 度
細かく刻む」道を測った。

まず**天井**を測る。R1〜R7 のそれぞれについて、粗い格子（5 点）と細かい格子
（12 / 16 / 20 / 25 / 30 / 37 / 45 / 52 / 60 / 70 / 80 の 11 点）を、矩形の有無
（なし / 主体の矩形）とモデル（auto / flat）の全組み合わせで原寸まで回し、
**正解に対する輪郭誤差の最小値**を比べた。順位付けを介さない、格子だけの上限である。

| シーン | 粗い格子の最良 | 細かい格子の最良 | 差 |
|---|---|---|---|
| R1 不織布 + 黒商品 | 1.85（tol 60） | 1.49（tol 80） | 0.37 |
| R2 照明勾配の不織布 | 1.09（tol 60） | 0.78（tol 70） | 0.31 |
| R3 不織布 + 淡色商品 | 110.75（tol 20） | 108.68（tol 16） | 2.07 |
| R4 暗い机 + 白商品 | 0.41（tol 12） | 0.41（tol 12） | 0.00 |
| R5 不織布 + ストラップ | 1.51（tol 60） | 1.43（tol 80） | 0.09 |
| R6 柔らかい輪郭 8px | 2.22（tol 60） | 1.82（tol 80） | 0.40 |
| R7 照明勾配のある紙 | 0.41（tol 12） | 0.41（tol 12） | 0.00 |

**刻みを細かくして得るものは無い。** 最良を更新した点は 1 つ残らず**上端の外側**
（70 / 80）にあり、既存の 5 点のあいだから出たものは 1 つも無い。R3 の 2.07 は
壊滅ケースの中での上下で、意味を持たない。残る 4 点の利得は 0.09〜0.40px——
1200px の素材での話である。

上端を 80 まで伸ばす道だけは合成では効く。`SEARCH_TOLERANCES` に 80 を足すと
R2 が輪郭誤差 1.11 → 0.78（rim 正解 0.065 → 0.050）、R6 が 3.35 → 1.82
（0.127 → 0.050）へ改善し、他の 5 点は 1 ビットも動かない。

**それでも採らない。実写が壊れる。** 24.5MP のリモコンでは探索段の 1 位と 2 位が
**どちらも tolerance 80**（モデル違い）になり、原寸で両方が商品を飲む
（前景比率 0.2037 → 0.0386）。`FINALISTS` は 2 なので逃げ場が無く、崩れた候補が
そのまま選ばれる。所要時間も 12.9 秒 → 15.1 秒で目標（15 秒）に並ぶ。

逃げ場を作る道も測ったが、どれも通らない。「最終段の 2 つは許容量を違えねば
ならない」という規則を足しても、この素材では tolerance 60 も原寸で飲む
（0.0664）ので助からない。崩れたら次を回す形にすると、この素材では
80 / 80 / 60 と 3 つ落としてから 45 に当たるので原寸が 4 回になり、
12.9 秒が 26 秒級になる。

**格子の刻みは順位の精度より細かい。** 粗い格子の天井（R1 1.85 / R5 1.51 /
R6 2.22）に対して `--optimize` が実際に届くのは 2.54 / 2.24 / 3.35 である。
失っている 0.7〜1.1px は**縮小探索の順位の側**にあり、格子を細かくしても
拾えない量である（順位の一致率は 4.13 の表）。
