## 4.9 空間的な指示（トライマップ / マスク / 多角形）

**数値ノブにはもう余地が無い。** 最良設定の周りで 4 つのノブ（`--tolerance` /
`--step-tolerance` / `--shadow-tolerance` / `--edge-threshold`）を振っても、
指標は 1 桁目まで動かなかった。パラメータ空間を探しても、輪郭のコントラストが
足りない素材や、商品と同じ色の小道具は解けない——**そこには色の手がかりが
無い**のだから、しきい値をどう選んでも同じである。

一方で、kiri を使うのは AI エージェントである。**エージェントが得意なのは
「どこが商品か」という意味の判断であって、しきい値の試行錯誤ではない。**
難しくするなら数値ではなく空間の指示を増やすのが正しい形になる。

既存の空間的な指示は `--bbox`（矩形の外は背景）と `--fg-seed`（半径 5px の点）
だけで、次ができなかった。

- 商品と同じ色の小道具が bbox の内側にあるとき、それを背景と教える
- 商品の内側で背景色と同じ部分（白い商品の白いラベル）を面で守る
- ビジョンモデルが返す粗いマスクをそのまま渡す
- 「ここは確定背景、ここは確定前景、境界はこの帯」をトライマップとして渡す

### 入口は増やすが、内部の表現は 1 つにする

| 入口 | 確定前景 | 確定背景 |
|---|---|---|
| `--trimap` | 輝度 192 以上 | 輝度 63 以下 |
| `--fg-mask` / `--bg-mask` | 輝度 128 以上 | 同左 |
| `--fg-polygon` / `--bg-polygon` | 内部（偶奇規則） | 内部 |
| `--fg-seed` | 半径 5px の円 | — |
| `--bbox` | — | 矩形の外 |

内部は画素ごとの `Constraint`（`Free` / `ForcedFg` / `ForcedBg`）1 つに畳む。
入口ごとに経路を作ると、フィル・診断・プレビューの 3 箇所で同じ判断を書き直す
ことになり、片方だけ直したときに「指定したのに効かない」が生まれる。

1 画素 1 バイトのフラグで持つ（12MP で 12MB）。**前景と背景を別のビットにする**
のは、衝突をそのまま表現するためである。衝突は黙って解決せずエラーへ回すので、
「選べない状態」を持てること自体が要る。

パスの解決とマスク画像の読み込みは `commands/cutout.rs` が行い、`cutout/` は
ファイルを知らない（`--bbox` の `resolve_bbox` と同じ分担）。

### フィルへの効き方

- **確定背景は種になる。** `fill_from_border` の起点に、画像外周・bbox の縁に
  加えて確定背景の画素を足す。**種そのものは色によらず背景**で、候補の規則を
  通さない。そこからの拡張は既存の規則（芯 / 拡張 / 影、堤防、段差）に従うので、
  商品と違う色の小道具を指しても商品へは侵入しない。**商品に囲まれて外周から
  届かない背景も、これで消せる**
- **確定背景は最後にも強制する。** bbox の外側と同じ扱いで、測地的オープニングの
  前に背景として確定させる。オープニングでは確定背景それ自身を起点にする——
  利用者が背景だと言い切った領域は、定義上「隙間を通って入ってきた浸水」では
  ありえない
- **確定前景は保護する。** `--fg-seed` と同じ経路（候補から外し、最後に前景へ
  戻す）で、bbox の外側より優先する。面積フィルタの後にも塗り戻す——下限は
  解像度に比例するので、5712x4284 では 20x20 の指示が丸ごと消え、しかも
  `constraints.sources` には名前が出たままだった。**確定前景は不透明で残る**
  （指した面が商品の輪郭に重なれば、そこは階調の無い硬い縁になる）

**芯が取れたかどうかは色で問う。** 2 段フィルは「厳しい許容量で芯が取れたか」を
見て、取れなければ 1 段フィルへ落とす。確定背景は候補判定を通さずに塗られるので、
その画素まで数えると指示が 1 画素あるだけで芯が取れたことになり、救済が到達不能に
なる。外周が推定背景色から離れた素材では、段差判定を越えられない背景がまるごと
前景に残った——**指示を足したせいで結果が悪くなる**、いちばん筋の悪い壊れ方である。

種を全部キューへ積んではいけない。トライマップのように画像の 7 割を背景だと
言い切った指示では数百万要素になり、12MP の実測でピーク RSS が 160MB 増えた。
縁の画素だけを積む（`expand` が同じ理由で同じことをしている）。

### 重なりはエラーにする

同じ画素が確定前景と確定背景の両方になったら `CONSTRAINT_CONFLICT`（exit 2）で
断る。**黙ってどちらかを選ぶと「指定が効いていない」という最も追いにくい失敗に
なる。** message に重なった画素数と外接矩形を載せ、どちらを削ればよいかを示す。

寸法が入力画像（EXIF 適用後）と違うマスクは `MASK_SIZE_MISMATCH` で断る。
**黙って拡縮しない**——伸ばして合わせると、指示した境界が商品の輪郭から半画素
ずつずれたまま、結果だけがそれらしく返る。マスクは 1 チャンネルのグレーとして
読み、**アルファは見ない**。ICC も EXIF も適用しない（画素そのものが指示である）。

ただし EXIF Orientation を持つ指示画像は `MASK_ORIENTATION_IGNORED` で報せる。
**180 度（3）や鏡像（2/4）は寸法が変わらない**ので寸法の検査を素通りし、
上下逆さまの指示がそのまま効く。結果の数値からは「切り抜きが下手」としか
読めない失敗なので、黙って進めない。

マスクのしきい値は輝度 128 にそろえる。「0 でない」では JPEG のリンギングを
拾い、白く塗った矩形を q85 で保存しただけで指示面積が膨らんだ。**可逆形式
（PNG）で渡すこと**を `--help` と README に書いたうえで、経由してしまった
場合も中点で切れば指示は動かない。

渡した入口が 1 画素も塗らなければ `CONSTRAINT_EMPTY` で報せる（`data.source`
に入口の名前）。`constraints` ブロックそのものは比率 0・`sources` 空配列で
出す。**「渡していない」と「渡したが空だった」は打つ手が違う**ので、
`sources` の不在で読ませない。

多角形の座標は範囲外を許す。`--bbox` の外側を帯で囲むという最も素直な指示は、
帯の外周が必ず画像の縁に接するかその外へ出るためである（`-0.05` / `1.05`）。
充填の側が走査線ごとに画像の中へ切り詰める。`--normalized` のときだけ、
絶対値 2.0 を超える値を「画素座標を渡した取り違え」として `INVALID_POLYGON`
で断る。

### 診断値との関係

`separability` は bbox の辺を境界から除いている。同じ理由で、**指示が決めた
境界画素**も除く。前景側が確定前景であるか、背景側が確定背景であるかの
**どちらか**で除く——利用者が引いた線そのものと、フィルが指示にぶつかって
止まった線は、どちらも色の判断ではないからである。全境界が除外なら `null`
（「測れる境界が無かった。0 ではない」）を返す。

両側の厳密一致で問うていた頃は、境界が 1px ずれた瞬間に除外が素通りし、
契約が禁じた 0.0 を返していた。refine と feather が動かす場合もあれば、
不明の帯を 2px 挟んだだけでもそうなる。

`halo_ratio` / `contour_roughness` / `rim_contamination` / `edge_width` は
除外しない。渡されたマスクが背景を含んでいれば halo が上がり、ギザギザなら
roughness が上がる。**それはエージェントが自分の指示の粗さを知る唯一の手段**
なので隠さない。

### 実測（R1: 不織布の上の黒い商品、1200x1200 の合成）

指示の効きは `assisted`（正解の bbox + 余白 5%、`--tolerance 60`）と比べる。
tolerance は同じにして、**変えるのは「どう指すか」だけ**にしてある。

| 設定 | 輪郭誤差 | rim 正解 | 粗さ | 縁の汚染 | alphaMAE | 境界ずれ |
|---|---|---|---|---|---|---|
| defaults | 126.10 | 0.950 | 1.439 | 0.353 | 0.212 | +250.0 |
| assisted（bbox + tol 60） | 18.42 | 0.512 | 0.851 | 0.251 | 0.082 | +20.9 |
| trimap（正解を 2% 収縮／膨張） | **3.76** | **0.255** | 0.734 | 0.178 | 0.081 | **+4.7** |
| polygon（内側の矩形 + 外側の帯 4 枚） | 19.76 | 0.515 | 0.850 | 0.256 | 0.082 | +20.6 |

トライマップは不明の帯を長辺の 4% も残した粗い指示だが、輪郭の位置を絞り込む
だけで輪郭誤差が 5 分の 1 になる。多角形のほうは輪郭について何も言っていない
ので assisted と並ぶ——**矩形 4 枚で bbox と同じ品質に届く**のであって、
それ以上にはならない。

ベンチは `forced_kept`（確定前景のうち最終マスクで前景として残った割合）を
trimap / polygon で 1.0 に固定する。**「assisted より悪くなっていない」だけを
見る判定は空振りする**——`eaten` は 4 設定すべてで 0 なので、`0 <= 0` しか
検査しておらず、指示が届いたかどうかを何も言っていなかった。

| 設定 | 輪郭誤差 | rim 正解 | eaten | forced_kept |
|---|---|---|---|---|
| defaults | 126.10 | 0.950 | 0.0000 | — |
| assisted | 18.42 | 0.512 | 0.0000 | — |
| trimap | 3.76 | 0.255 | 0.0000 | 1.00 |
| polygon | 19.76 | 0.515 | 0.0000 | 1.00 |

追加コストは 12MP（3000x4000）の実写で測って、**指示が空のまま表だけを持つ
場合で +27ms / +11MB**（制約の表そのもの）。実際に効く指示を渡すとフィルが
早く終わるため、トライマップでも多角形でも **280ms ほど速く、RSS は 13MB
小さい**（1155ms / 326MB → 875ms / 313MB）。

## 4.12 意味の事前知識をモデルから借りる

3.6 が「何を採るか」を決めた。ここは「採ったものをどう流すか」である。

### 新しい切り抜き経路は作らない

モデルが出すのは 1024x1024 の確率マップである。原寸 24MP に対して 1 画素が
24 画素ぶんを代表する粗さで、**輪郭の位置はこれで決められない**。一方、原寸の
画素精度は Phase 2（`Constraints`）と Phase 3（matting）が既に持っている。

そこで**確率マップをトライマップに落として既存の入口へ流す**。モデルは
「ここは確実に商品」「ここは確実に背景」だけを言い、そのあいだの帯は今までどおり
色と連結性とマッティングが決める。切り抜きのコードは 1 行も分岐しない。

これは 4.9 が既に用意していた形そのものである——README が
「SAM のような分割モデルが返すマスクをそのまま渡す」例として書いていた経路に、
kiri 自身がモデルを差すようになっただけで、**新しい概念は 1 つも増えていない**。

### 確率マップ → トライマップ

**二値化も収縮も、原寸ではなく確率マップ自身の格子（ISNet なら 1024x1024）で
行う。** `r` もその格子を基準に測る。

| 段 | 内容 | どこで |
|---|---|---|
| 1 | 出力テンソルの先頭チャンネルを取り、**余白を切り落としてから** min-max で [0,1] へ | 格子 |
| 2 | `r = ceil(SEG_MARGIN * 格子の長辺/1000)`、`SEG_MARGIN` は 8（1024 なら `r` = 9） | 格子 |
| 3 | `p >= SEG_FG`（0.9）を `erode(r)` して確定前景 | 格子 |
| 4 | `p <= SEG_BG`（0.1）のうち**外周から届くもの**を `erode(r)` して確定背景 | 格子 |
| 5 | 二値のまま原寸へ最近傍で配る | 原寸 |

設計では 2 段目で原寸へ双線形で拡大し、そこで `erode` するつもりだった。
**実測でそこが処理時間の大半を占めた**——`erode` は窓を素直に舐めるので
`O(n * r)` になり、24.5MP・半径 33px では 1 枚 9.7 秒かかった（推論は 2.4 秒）。
格子で畳めば `1024² * 9` で済み、0.16 秒になる。

**同じことを言っている。** `SEG_MARGIN` は長辺 1000px 換算の値で、確率マップの
長辺はちょうどその程度（1024）だからである。原寸へは最近傍で配るので格子 1 つが
原寸の数 px に広がるが、その数 px は既に `r` の収縮で不明の帯に含まれている。
副次的に、原寸の `Mask` を 2 枚（24MP で 48MB）持たずに済む。

**しきい値を 0.5 に置かない。** 0.5 は「どちらかといえば前景」でしかなく、輪郭の
すぐ内側まで確定前景になる。確定前景は色によらず不透明で残る規約（4.9）なので、
そこが 1px でも外れると硬い縁が商品の外へ張り付く。0.9 / 0.1 はモデルが
言い切っている芯だけを採る線である。

**そのうえで両側を `r` 削る。** 1024² の 1 画素は 24MP では 4.8 画素ぶんあり、
双線形で伸ばした時点で等高線は真の輪郭から数 px ずれうる。削るのは
**不明の帯を両側へ広げる**ことと同じで、ずれはその帯の中へ収まる。

`SEG_MARGIN` を 8 に置いたのは、正解から作った粗いトライマップ（長辺の 2%、
1200px で 24px）より狭い線だからである。**モデルの輪郭は手描きより信用できる**
ので、そこまで広げると指示の価値を捨てることになる。

### 利用者の指示はモデルに勝つ

同じ画素で衝突したら、利用者の側を採る（`Constraints::overlay`）。
`CONSTRAINT_CONFLICT` にはしない。

**4.9 が「重なりはエラーにする」と決めたのと矛盾しない。** あちらが対等な指示
どうしの話なのに対し、こちらは片方がモデルの**提案**で、もう片方が利用者の
**決定**である。「モデルが背景だと言った画素を利用者が前景だと指した」のは
矛盾ではなく訂正で、そこでエラーを返すと「モデルを使うと指示が出せなくなる」
という筋の悪い規約になる。

上書きは画素ごとに全部である。ビットを OR すると衝突として残り、後段の
`conflict()` が拾ってしまう。

### 前処理は rembg と同じく 1024x1024 へ歪める

設計では「アスペクト比を保って縮小し、余白を平均色で埋める」（`SegmentFit::Letterbox`）
つもりだった。**実写 2 枚で比べて、rembg と同じ歪め（`SegmentFit::Stretch`）を
既定にした。**

| 画像 | 前処理 | 確定前景 | 確定背景 | 不明 | 前景比率 | 目視 |
|---|---|---|---|---|---|---|
| キーボード 3024x4032 | letterbox | 0.89% | 51.88% | 47.23% | 42.72% | **右列が欠ける** |
| キーボード | **stretch** | 0.80% | 51.52% | 47.68% | 45.00% | 欠けない |
| リモコン 4284x5712 | letterbox | 17.42% | 77.19% | 5.39% | 20.51% | 差なし |
| リモコン | **stretch** | 17.53% | 77.32% | 5.16% | 20.51% | 差なし |

**実測は設計の見込みと逆だった。** アスペクト比を保ったほうが形は崩れないはず
だったが、キーボードでは余白つきのほうが右列を丸ごと落とした。理由は学習時の
前処理だと考えている——ISNet は歪めて 1024² にした画像で学習されており、
余白は学習時に存在しなかった構造である。リモコンでは差が出ない。

**根拠は目視と前景比率だけである。** 同じ実行で `separability` 21.02 / 16.63、
`contour_roughness` 0.648 / 0.388 も出ているが、**どちらも前処理の良し悪しを
測っていない**。

- `separability` は**商品を削った側ほど高く出る**。letterbox が 21.0 なのは、
  右列を落とした結果、境界が銀色の枠と暗い机のあいだに来るからである
- `contour_roughness` は素材の符号化で動く。同じ写真を `sips` の品質だけ変えて
  JPEG にすると、`--segment isnet` の粗さが 0.388 と 0.550 のあいだで動いた
  （下の「素材を固定する」を参照）。**符号化のノイズが輪郭に乗るぶんを、
  この指標は前処理の差と区別しない**

右列が欠けているかどうかは 42.72% と 45.00% の差にそのまま出ており、拡大して
見れば誰でも同じ結論に達する。**指標を 4 つ並べるより、効いた 1 つだけを
根拠として名指すほうが後から検算できる。**

### 素材を固定する

実写の数値は**素材のバイト列に紐づく**。HEIC からの JPEG 変換は品質の指定で
別のファイルになり、上に書いたとおり `contour_roughness` はその差で動く。
以下のとおりに作ったファイルが、この節と 4.12 の実測・README・
`implementation-plan.md` の数値すべての出どころである。

```
sips -s format jpeg -s formatOptions 95 IMG_0238.HEIC --out keyboard.jpg
sips -s format jpeg -s formatOptions 95 IMG_0251.HEIC --out remote.jpg
```

| ファイル | バイト | SHA-256 | 寸法（EXIF 適用後） |
|---|---|---|---|
| `keyboard.jpg` | 3,808,626 | `f6dd587331f00376d08da4d4997146ba518d2eaac062e3421e6252bc5fec4619` | 3024x4032 |
| `remote.jpg` | 7,410,773 | `5b9b072cec9264c964a8cdfc16eda9cb7c557d1b4250513a31f7f270194b4ab2` | 4284x5712 |

`sips` の出力はこの引数なら決定的で、同じ HEIC から同じバイト列が出る。
**`formatOptions` を `high` にすると別のファイル**（2,726,565 / 5,349,025 バイト）
になり、キーボードの `--segment isnet` の粗さは 0.3883 ではなく 0.5499 と出る
（`off` の側も 0.8132 から 0.7675 へ動く）。写真そのものはリポジトリに置かない
（実写素材は入れない規約）ので、**digest を書いておくことが唯一の突き合わせ
手段**である。

細長い商品（1:3 以上）は測れていない（手元の実写 2 枚は両方 3:4）。
`SegmentFit::Letterbox` はライブラリに残してある。

余白を 0（黒）で埋めないのは、白い商品の周りに本物ではない段差ができ、モデルが
それを輪郭として拾うためである。平均色なら、少なくとも「その画像にありそうな色」
になる。

### R1〜R7: 正解から作ったトライマップに負けない

`trimap` 設定は**正解の二値**を長辺の 2% で収縮・膨張して作ったもので、画像を
見ずには作れない。`segment` はモデルの出力だけで作る。同じ土俵で並べる。

| シーン | 設定 | 輪郭誤差 | rim 正解 | eaten | alphaMAE | 前景比率 |
|---|---|---|---|---|---|---|

### `--segment-size` は置かなかった

設計では `512 | 1024` を選べるようにするつもりだったが、**ISNet の ONNX は
1024 を graph に焼き込んでいる**。入力 fact を 512 にすると復号側の Concat が

```
Failed analyse for node #272 "/stage1/Concat_2" InferenceConcat
  Applying rule inputs[0].shape[2] == inputs[1].shape[2]
  Impossible to unify Val(32) with Val(16)
```

で落ちる（`Resize` の出力寸法が定数として埋まっているため）。**常に失敗する値を
契約に載せるのは、誤った助言と同じ害を持つ。** 代わりに、モデルが決めた値を
`segment.input_size` と `kiri model list` の `input_size` で名乗る。
可変にできるモデルを足すときに、そのときの入口を作ればよい。

### 推論は f16 で走らせる

ISNet は 1024² の入力に 64 チャンネルの特徴マップを重ねるので、**中間テンソル
1 枚が f32 では 256MB** ある。ピーク RSS を作っているのは重み（176MB）ではなく
こちらで、f16 へ畳むと 24.5MP の `cutout --segment isnet` が 6.20 秒 / 1642MB
から **5.61 秒 / 1300MB** になる（`info --segment isnet` は 1.88 秒 / 1456MB →
1.97 秒 / 938MB）。

**精度は使い道が吸収する。** kiri が確率マップから読むのは「0.9 以上か」
「0.1 以下か」の 2 つだけで、そのあいだの帯は色と連結性とマッティングが決める
（`to_constraints`）。実写 2 枚での差は下のとおりで、**動くのは小数第 3 位**
である。

| 画像 | 指標 | f32 | f16 |
|---|---|---|---|
| リモコン 5712x4284 | 確定前景の割合 | 0.1745 | 0.1746 |
| リモコン（`--tolerance 20`） | 前景比率 / halo / 粗さ | 0.2050 / 0.0788 / 0.2716 | **4 桁まで同じ** |
| キーボード 4032x3024 | 確定前景の割合 | 0.0080 | 0.0080 |
| キーボード | halo / 粗さ / 境界色差 | 0.0992 / 0.3883 / 16.63 | 0.0984 / 0.3942 / 16.61 |

警告の並びはどちらの画像でも変わらない。

畳むのは `tract_core::floats::FloatPrecisionTranslator` で、最適化の前に掛ける。
**通らない環境では f32 のまま走る**——f16 の核を持たない CPU や、変換が通らない
別の重み（`--model-path`）を断る理由は無い。遅くて重いだけで、答えは出る。

### 読み込みと検証はプロセスで 1 度だけ

`batch` が `--segment` を受けられなかったのは、**件ごとに 176MB を読み直し、
ピーク RSS を並列度ぶん積む**形だったためである。2 つを変えた。

- **実行計画をプロセスで持ち回す**（鍵はパス・素性・入力の一辺・`--model-path`
  かどうか）。素性（大きさと更新時刻）を鍵に入れるのは、同じパスの中身が
  置き換わったときに古い計画を返さないためである
- **推論そのものは 1 本ずつ通す。** 中間テンソルの山が並列度ぶん積み上がるのを
  防ぐ。止まるのは推論だけで、復号・フィル・書き出しは並列に走る

実測（1000x1000 を 4 件）はモデルのぶんの増分が `--jobs 1` で 881MB、
`--jobs 4` で 874MB と**変わらない**。時間は並べられないので、1 件 1.3 秒が
そのまま積む。

読み込みの前に **SHA-256 を突き合わせる**。想定と同じ長さの壊れたファイルは
大きさでは捕まらず、tract の解析失敗まで落ちないためである。176MB の走査は
0.4 秒かかるので、確かめた結果をモデルの傍らの `<ファイル名>.verified` に
残す（版・ダイジェスト・大きさ・更新時刻）。**印は「正しい」ではなく
「何であるか」を記録する**——想定と違うファイルでも、2 回目からは計り直さずに
同じ警告を出せる。印が書けない場所では毎回計る（答えは変わらない）。

### `auto` の門

`info` が「色では解けない」と言う画像でだけ走らせる——`background.uniformity` が
下限を切っていて、かつ `NOT_SEPARABLE` になるか `subject.confidence` が `low` に
なるとき。`info` の `low_uniformity_warnings` と同じ形にしてある。

**均一度の門を外さない。** 白背景に小さな商品が載っているだけの画像でも
`subject.confidence` は面積不足で `low` になるが、そこは色が解いている。外すと、
解けている画像すべてで 1.2 秒を払うことになる。

門は外周の 1 色分布と主体だけを見る（照明場は作らない）。場の推定は 24MP で
数百 ms かかるうえ、門はそれを使わない。

**門が測ったものは切り抜きへ持ち回す**（`BackgroundSeen`）。同じ画像・同じ
`--border` なら答えは同じなので、`cutout` が測り直すのは二度手間である
（`info` は逆向きで、自分が測ったものを門へ渡す）。持ち回せるのは外周の
1 色分布と主体までで、**照明場は入れない**——`--tolerance` にも矩形にも
`--background-model` にも依るからである。同じ仕組みで `--optimize` の探索段も
21 回から 1 回になった。

### モデルの「確率が低い」は「背景」ではない

**実写キーボードでこれが要ることが分かった。** ISNet は黒いキーキャップを
ほぼ確率 0 で返す——顕著性のモデルにとって、平坦で暗い内部は「目立たない」
のであって「背景」ではない。そのまま確定背景にすると、**キーが 1 つ残らず
穴として抜けた**（確定背景は色によらず背景なので、フィルが届く必要すら無い）。

kiri は最初から背景を「外周から到達できる領域」として定義している（4.1）。
モデルの提案もその定義を通して読む——**低確率の領域のうち、格子の外周から
4 近傍でたどり着けるものだけ**を確定背景にする。囲まれた島は不明のまま残り、
そこは色と連結性が決める（キーキャップは商品の枠に囲まれているので前景に残る）。

**払うものがある。** 取っ手の内側のような「商品に囲まれた本物の背景」を
モデルから受け取れなくなる。ただしそれは `--segment off` の経路でも同じ制約で、
`--bg-polygon` という逃げ道も既にある。**モデルが見つけたものを 1 つ失うより、
モデルが見つけていないものを確定させるほうが害が大きい。**

### 実測（Apple M4 Pro）

| 項目 | 値 |
|---|---|
| 推論（1024x1024、モデルの読み込み込み） | 1.3 秒前後 |
| そのうちモデルの読み込み + 最適化 | 0.10 秒 |
| トライマップ化（確率マップ → `Constraints`） | 0.10 秒（12MP） / 0.16 秒（24MP） |
| ピーク RSS の増分 | +0.7〜1.2 GB |
| clean build | 50 秒 → 200 秒 |
| バイナリ | 3.26MB → 19.26MB（Phase 4 は 3.21MB） |
| 依存クレート | 97 → 175（`*-sys` は 0） |

**トライマップ化を格子の側でやる前は 3.5 秒 / 9.7 秒かかっていた。** 原寸で
`erode` すると `O(n * r)` で、24.5MP・半径 33px では推論より重くなる。

### 決定性

同じバイナリ・同じ機械で CPU 推論は決定的である。加えて**確率を 0.9 / 0.1 で
量子化してから流す**ので、最下位ビットの揺れは結果に出にくい。ICC の `powf` と
同じ注意（別の機械・別の版では最下位ビットが動きうる）はここにも当てはまる。
