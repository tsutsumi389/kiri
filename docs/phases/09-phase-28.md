# 9. Phase 28: 帯を遷移と厚みから引き直す

節番号は分割前のまま変えていない。`計画 §8.6` のような参照が他の節・src / tests から
150 箇所以上張られていて、**番号が識別子として働いている**からである。どの節がどの
ファイルにあるかは [実装計画](../implementation-plan.md) の索引で引く。

§8 は「狙った的には当たらず、別の場所に当たった」で終わった。当たらなかった側の
原因として §8.10 が名指ししたのは**帯幅**で、§8.6 はそれを「`refine` の (b)(c) と
較正表 29 点へ波及する別の工事」として段の外へ出した。**この段はその 1 件を回収する。**

## 9.1 なぜここか

順序は好みではなく、次の 5 つから決まっている（§7.1 と同じ立て方）。

1. **前の段が名指しで送った 2 件のうち、下流でないのはこちらだけである。** §8 が
   送ったのは「帯幅」（§8.6）と「`--optimize` の探索段に解き方を載せる」（§8.10 の
   末尾）で、後者は「どの素材でどの解き方が勝つか」を探索段（1500px・`refine` 無し）
   から予測できることが前提である。その予測則は **closed-form が負ける原因が
   分かってからしか書けない**
2. **既定を動かせる状態を作る唯一の工事である。** いまの 3 択はどれを既定にしても
   大きく負ける側がある——closed-form なら S4 +0.0460 / R6 +0.0538 / S12 +0.0640 と
   3px ストラップの粗さ 0.082 → 0.272、`projection` なら R1 assisted の粗さ
   0.331 → 0.670 と縁の汚染 0.138 → 0.188（§5 Phase 12 の段の表）。closed-form が
   負ける 3 群のうち **2 群（柔らかい輪郭・細いストラップ）を §8.10 自身が帯幅へ
   帰着させている**
3. **的が 21 点の中で最大かつ唯一「直せる」場所である。** §8.8 の読み取り 4 の
   とおり S9 0.3345 と R3 0.4651 は切り抜きそのものが壊れている点で的ではなく、
   それを除いた最大は **S4 0.1389 / R6 0.1195** で、3 番目（S5 0.0937 / R1 0.0901）
   に対して桁が 1 つ近い差がある。残る 19 点は `projection` で 0.0053〜0.0457 に
   収まっている
4. **代替の道は全部測って潰れている。** 窓を広げる道は S4 0.1436 / R6 0.1452 で
   頭打ちになり、しかも R1 を 0.0658 → 0.0865 と悪化させる（§8.10 の掃引表）。
   帯を一律に広げる道は `rim_contamination` 0.061 → 0.133 と単調に悪い
   （design.md 4.7 の `max_radius` の表）。帯を粗くして解く・未知を帯の全画素に
   する・Σ の窓を帯幅にそろえる、はいずれも §8.9.11 で却下済みである。
   **残っている手は「帯を画素ごとに遷移へ追従させる」だけである**
5. **契約の面積がほぼゼロで、いま以外のどの段でもやりにくい。** 帯幅は `cli.rs` に
   入口が 1 つも無い純内部の値で、新しいフラグも warning code も
   `schema_version` の変更も要らない。一方で**既定の出力バイト列は動く**。
   §7.1 は「バイト列を動かす変更はバイト列に依存する機能より前に置く」と言って
   いて、**§7 が Phase 26 で閉じ、バイト列に依存する未着手の機能が 1 つも無い
   いまが、その条件を満たす唯一のタイミングである**

## 9.2 着手の第一歩は、§8 の診断そのものを疑うことである

**これは §8.5 の 1（着手前の測り直し）と同じ位置にある作業で、前より重い。**
§8.6 / §8.10 と `closed_form_loses_on_soft_edges_and_thin_straps` の doc は
いずれも「帯の半径は S4 で 2px / R6 で 3px しかない」と書き、根拠に
`settings.band_min_radius` を挙げている。**しかしそれは帯幅の下限であって、
画素ごとの帯幅ではない。**

帯幅は輪郭画素ごとに `transition_width`（`cutout/refine.rs`）が決める。法線方向へ
進み、参照色へ `CONVERGED`(2.0) 以内で収束するまでの距離を返す関数で、値域は
1〜`max_r`、`max_r` は原寸の `DEFAULT_MAX_RADIUS`(10) である。**8px の遷移に
7〜8px の帯が張られていてもおかしくない。** 下限が 2〜3px であることは、
画素ごとの帯が 2〜3px であることを意味しない。

だから最初にやるのは実装ではなく、**S4 / R6 の輪郭画素で実際に張られた帯幅の
分布（中央値・p90・最大）を表にすること**である。`print_the_stage_table` と同じ
`#[ignore]` の計測用テストとして置き、判定はせず表を出す。

| 分布が示すもの | 読み | この段の行き先 |
|---|---|---|
| 中央値が **8px 以上** | 帯は既に真の遷移を覆っている。**§8 の診断は誤り** | 帯に手を付けず、誤った診断を訂正する記録だけを残して的を選び直す（中止条件 1） |
| 中央値が **3px 前後** | 診断は当たっている | 9.3 へ進む |

**§8.10 の窓半径の掃引だけではこれは決まらない。** 1 → 4 で単調に改善した
（S4 0.1849 → 0.1436、R6 0.1733 → 0.1452）という事実は**どちらの読みとも整合する**
——帯が狭いなら窓が帯の外の確定画素を拾うから効くし、帯が広いなら律速は局所の
色モデルの側だから窓で効く。**決まるのは分布を見たときである。**

- ※ **1 表で中止できることが、この的を選ぶ理由の 1 つである。** §6 が P2 へ課した
  「着手前に必ずベンチで見積もる」を、最も安い形で満たす
- ※ **測った。§9.9 にある。中止条件 1 が発火し、この段は帯に手を付けない。**
  §8 の診断は誤りで、帯は S4 で半径 6px（総幅 12px）、R6 で半径 8px（総幅 16px）
  あり、真の遷移 8px を既に覆っていた。**下の表の「3px 前後」の側は起きなかった**

## 9.3 作るもの

帯の決め方を 2 点だけ直す。**どちらも `transition_width` と `band_map_into`
（`cutout/refine.rs`）の中で閉じる。**

1. **外側の参照色を帯の中から採らない。** いまは「法線方向 `max_r` 以内で最も
   外側にある非前景画素」を背景の参照にし、そこへ収束する距離を測っている。
   8px で溶ける輪郭では二値の輪郭が**混色のかなり背景寄り**に立つ（design.md 4.5。
   境界位置が +5px 外側）ので、**この参照そのものが遷移の中から採られうる。**
   参照が汚染されれば収束が早く宣言され、帯は遷移に届かない。受け皿として
   `field.rgb_at(x, y)`（照明場）が既に実装されているので、**参照を場から採る／
   遷移より外から採る**へ替える
2. **帯を局所の前景の厚みで打ち止める。** `paint_disc` は輪郭画素ごとに半径
   `width` の円を塗るので、幅 3px のストラップでは芯まで埋まり、closed-form の
   境界条件（帯の外の確定画素）の支えがほとんど消える（§8.10 の ※、粗さ
   0.082 → 0.272）。距離変換は `rim_contamination` 側と `CORE_RATIO` で既に
   持っているので、**厚みの半分で帯を打ち止める**規則を足す

**新しい入口は作らない。** `--band-*` のようなフラグは `cli.rs` に 1 つも無く、
外へ出ているのは `settings.band_min_radius` だけである。**数値ノブを 1 つ増やして
較正を利用者へ押し付けるのは、§7.2 が Phase 11 で「数値ノブにはもう余地が無い」
と書いた判断に反する。**

## 9.4 契約への影響

| 場所 | 変更 |
|---|---|
| `cli.rs` / `kiri schema` / `batch` の spec | **無い。** 帯幅は内部の値で、入口が 1 つも無い |
| `schema_version` | **2 のまま。** キーも型も意味も変わらない |
| `warning.rs` | **足さない。** 帯が遷移に届かないことを名乗る code は作らない——`contour_roughness` と `rim_contamination` が既にその結果を数値で言っている |
| `settings.band_min_radius` | **意味と型は変わらない**（実際に効いた帯幅の下限）。値は動く |
| 既定 `guided` の出力バイト列 | **動く。** 帯幅は (b) 再分類・(c) 色の門つきメディアン・(e) の窓（`GUIDED_MARGIN` = 帯幅の下限 +1）すべての入力である |
| md5 のゴールデン | **一度取り直しになる。**（Phase 18 の派生系と Phase 24 / 25 / 27 の main 比較） |

**§8.6 の受け入れ条件 3「既定経路が 1 ビットも動かない」は、この段では成立しない。**
§8 はそれを中止条件の筆頭に置いていたが、あれは「素材で勝ち負けが分かれる機能を
足す段」の条件である。**この段は帯という共通の入力を直すので、既定が動くことが
目的の側にある。** 代わりに置くのは「**動いた点と向きを全部名指しする**」で、
9.7 の (f) がそれを引き受ける。

- ※ **計測の通り道が今は無い。** `cutout()` は `RefineOptions` の半径を
  `..Default::default()` で埋めていて（`cutout/mod.rs`）、`CutoutOptions` に半径の
  フィールドが無い。帯を掃引するには計測用の通り道が要る。**CLI へは出さない**

## 9.5 費用

規模は **L**。算術そのものは小さい（`transition_width` は 75 行、距離変換は既に
ある）が、**較正とベンチの往復が長い**——Phase 24 が「計算は M だが較正とベンチの
往復が長い」で L と見積もったのと同じ形である。

時間とメモリの増分はほぼ無いと見ている。帯が広がれば帯の面積は増えるが、
closed-form の実測は帯 25 万画素 / 31 反復 / 3.1 秒で `guided` の 3.3 秒と並んで
いて（§8.10）、帯が倍になっても桁は変わらない。**ただしメッシュ・レース・櫛の
ような素材だけは周長が桁で違う**（§3.2b）ので、そこは形状ごとに前後で測る。

## 9.6 テスト方針

1. **第一歩は 9.2 の分布の表である。** 判定はせず表を出す `#[ignore]` の計測用
   テスト。ここで的が消えることがある
2. 分布と同時に**帯幅を掃引した 21 点の `alpha_mae`** を出す。§8.10 が窓半径で
   やったことを帯幅の側でやる
3. 的（9.7 の (a)(b)(c)）を固定する。**先に落ちるテストを書く**
4. **くっきりした輪郭で帯が 1px も動かないことを固定する**（9.7 の (e)）。
   これが「一律に広げていない」ことの裏になる
5. 既定 `guided` の 21 点 + 較正表 29 点を前後で出し、**動いた点と向きを記録する**
6. 決定性（既定 / `projection` / `closed-form` の 3 通りで 2 回のバイト一致）
7. 時間とピーク RSS を形状ごとに前後で測る（`print_the_refine_cost_on_large_inputs`）
8. clippy / fmt / MSRV / `--features segment` の有無で 2 系統。**feature 違いの
   `cargo test` は直列で回す**——同時に走らせると `target/release/kiri` を
   取り違えて偽の失敗になる

## 9.7 受け入れ条件と中止条件

### 受け入れ条件

**§8.6 が「この段では満たせない」として送った条件をそのまま復活させる。緩めない。**

- **(a) 送られた条件を回収する。** R6 の `closed-form` の `alpha_mae` が
  **0.1195 を下回る**（現状 0.1733）。§8.6 の「着手前に立てた条件」と同一の的
- **(b) 柔らかい輪郭のもう 1 点も `guided` 以下。** S4 の `closed-form` が
  **0.1389 以下**（現状 0.1849）
- **(c) 細い構造の警告を消す。** S5（3px ストラップ）の `closed-form` の
  `contour_roughness` が **`CONTOUR_ROUGH_WARN`(0.16) 未満**（現状 0.272）。
  同時に S5 / S5b の `strap_kept` が **100%**、`forced_kept` / `forced_bg_kept` が
  **1.0** のまま
- **(d) §8 が当てた的を 1 つも落とさない。** R1 の `closed-form` が `alpha_mae`
  **≤ 0.0658**、`contour_roughness` **≤ 0.16**、`rim_contamination` **≤ 0.02** を
  保ち、`closed_form_halves_the_truth_side_error_on_a_woven_background` が無修正で
  通る。R2 / R5 / R7 の `alpha_mae` も現状比 **+0.005 以内**（0.0432 / 0.0738 / 0.0114）
- **(e) くっきりした輪郭では帯が 1px も動かない。** S1 / S2 / S13 / R4 / R7 で
  帯幅の分布が変更前と**完全一致**し、`guided` の出力が **md5 で一致**する。
  **これが「一律に広げていない」ことの裏である**——一律拡大は design.md 4.7 で
  既に潰れている案なので、区別できなければ再提案になる
- **(f) 既定経路の動きを全部名指しする。** 既定 `guided` の出力は動いてよいが、
  **動いた点と向きを 21 点 + 較正表 29 点の表で残す**。そのうえで `guided` の
  `alpha_mae` が現状比 **+0.005 を超えて悪化する点が 0 点**、`contour_roughness` /
  `rim_contamination` が**合格側から警告側へ移る点が 0 点**
- **(g) 較正の窓が閉じない。** `print_the_calibration_table` の群間比が現状より
  狭まらず、`CONTOUR_ROUGH_WARN` / `RIM_CONTAMINATION_WARN` が**正解だけで分けた
  2 群のあいだに入ったまま**（Phase 10 の規約。しきい値そのものは動かさない）
- **(h) 段の担当が生きている。** `each_stage_moves_the_metric_it_is_responsible_for`
  の 3 つの比が無修正で通る
- **(i) 費用が桁で変わらない。** 24.5MP の `cutout` の所要時間の増分が
  **+10% 以内**、ピーク RSS の増分が **+50MB 以内**。
  `refine_does_not_scale_with_the_area_of_the_window` が無修正で通る
- **(j) 決定性。** 同じ入力で 2 回のバイト一致（3 通りすべて）
- **(k) 契約が 1 つも増えない。** 新しいフラグ・warning code・`schema_version` の
  変更が **0 件**。増えたら設計を疑う合図として扱う
- **(l) 負けを assert しているテストを、通らなくなったことを理由に消さない。**
  `closed_form_loses_on_soft_edges_and_thin_straps` は**残る素材（S12 の
  淡色 × 織り目、0.0724 → 0.1364）へ書き換える**。§8.6 の条件 4「負けることの
  証拠を機械が持っている」を維持する

**(a)(b)(c) が的、(d)〜(i) が非悪化、(e)(k)(l) が「別のことをやっていない」ことの裏。**

### 中止条件

1. **9.2 の分布で的が帯幅に無いと出たら中止する。** 中央値が 8px 以上なら
   §8.6 / §8.10 / テスト doc の「帯幅の限界」という診断は誤りである。その場合は
   **帯に手を付けず**、誤った診断を訂正する記録だけを残して的を選び直す
   （次の疑いは Σ / ε の窓と `CONVERGED`(2.0) の側。窓半径の掃引が単調に効いた
   という事実がそちらを指している）
2. **(a)(b)(c) のどれかが満たせないと分かった時点で中止する。** 「近づいたので
   条件を下げる」はしない。ただし §8.6 と同じく、**測って的が別の場所にあったと
   分かった場合は条件を差し替えてよい。緩めてはいけない**
3. **(e) が落ちたら中止する。** くっきりした輪郭の帯が動くなら、それは遷移追従では
   なく一律拡大であり、**既に実測で潰された案の再実装**である
   （`rim_contamination` 0.061 → 0.133）。他が全部通っていても落とす
4. **(g) が落ちたら中止する。** 較正の窓が閉じる、あるいは正解由来の群分けと
   しきい値の順序が入れ替わるなら、Phase 10 が作った 2 つの指標の意味が壊れる。
   **指標が壊れれば以降のどのフェーズも「良くなったか」を言えなくなる**
5. **(f) で既定の悪化が出て、それを設計で受けられないなら中止する。** 帯の変更が
   柔らかい輪郭にだけ効く（＝素材で分岐しない）形に収まらないなら、この段では
   入れない。§8.6 の中止条件 3 が言う「勝ち負けの話より先に契約の話になる」は
   ここでも同じに効く
6. **(i) を割ったら中止する。** 帯の面積は周長 × 帯幅で決まり、メッシュ・レース・
   櫛のような素材だけで桁が変わる

## 9.8 却下した代替案

- ※ **`max_radius` を一律に上げる。** design.md 4.7 の表で既に潰れている
  （実写リモコンの `rim_contamination` 0.061 → 0.133、R1 assisted の輪郭誤差
  6.03 → 14.75）。**この段が (e) を条件に入れているのは、一律拡大と遷移追従を
  機械が区別できる状態にするためである**
- ※ **closed-form の窓半径を上げる。** §8.10 の掃引で頭打ち（S4 0.1436 /
  R6 0.1452）かつ織り目側を悪化させる（R1 0.0658 → 0.0865）
- ※ **帯幅にフラグを足して利用者に決めさせる。** 較正を押し付けることになる。
  §7.2 の Phase 11 が「数値ノブにはもう余地が無い」と書いたのと同じ理由
- ※ **`--optimize` の探索段に解き方を載せる。** §8.10 が送ったもう 1 件だが、
  探索段は 1500px・`refine` 無しで matting の差が出ない。**「どの素材でどの
  解き方が勝つか」が縮小画像から予測できる量と結びつかないと原理的に載らない**
  ので、この段の答えの後になる
- ※ **既定の解き方をここで差し替える。** §8.8 が出した「既定 `guided` は 21 点中
  20 点で `projection` に負ける」は正面から扱う価値があるが、**門の材料は
  この段の答えに依る**。帯を直した後の 3 択で測り直すのが順序である
- ※ **`--segment` を `--optimize` の候補集合へ入れて R3 / S9 を救う。** 効果は
  大きい（R3 の輪郭誤差 115.15 → 6.51、design.md 4.11）が、**feature `segment` は
  既定で無効**なので既定の build で受け入れ条件が 1 つも検査できない。
  **既定の品質を上げる段にはならない**
- ※ **Phase 26 が送った「`set` があるときセット全体で段を 1 つ決める」。** `batch`
  の設計変更で、境界品質とは別系統である。§8.7 が「境界を解き直す段に混ぜない」と
  書いたのと同じ理由で、**帯を引き直す段にも混ぜない**
- ※ **README の `product.jpg` 実例 14 箇所の撮り直し**（Phase 26 が送った）。
  素材がリポジトリにも履歴にも無い。**単独の docs 段として切るのが正しい**

## 9.9 帯幅の分布（2026-10-01。§9.2 の第一歩）

**§8 の診断は誤りだった。中止条件 1 が発火する。** `print_the_band_width_distribution`

### 読み取り

1. **S4 は p50 6px / p90 8px、R6 は p50 8px / p90 10px である。** §8.10 と
   §8.6 と `closed_form_loses_on_soft_edges_and_thin_straps` の doc が書いた
   「帯の半径は S4 で 2px / R6 で 3px しかない」は、**下限を帯幅と読み違えている。**
   最頻値ですら S4 で 6px、R6 で 10px である
2. **さらに、帯幅は半径である。** `paint_disc` は輪郭画素を中心に半径 `width` の
   円を塗り、**中心画素も塗るので総幅は 2r+1** になる（`window_for` の doc が
   「帯の一番外側の画素から確定前景までは 2r+1」と書いている、その数え方と同じ）。
   R6 なら 17px、S4 なら 13px で、**真の遷移 8px は帯の中に完全に収まっている。**
   下限の 2px / 3px でも総幅は 5px / 7px であって、「帯の中で 0 → 1 を完結させる
   しかないから必ず急になる」という §8.10 の説明は**その下限の値でも成り立って
   いなかった**
3. **したがって closed-form が柔らかい輪郭で負ける原因は帯幅ではない。**
   §9.1 の 4 が「残っている手は帯を画素ごとに遷移へ追従させるだけ」と書いたのは、
   **追従が既に効いていることを見落とした上での結論だった**——`transition_width`
   は S4 で 2 → 6px、R6 で 3 → 8px、S9 で 6px、S10 で 4px と、素材ごとに実際に
   動いている
4. **塗り直しは帯を狭める。** `phase2`（(b)(c) 無し）と既定を並べると、S4 は
   p50 8 → 6px、R1 は 8 → 7px、R2 は 7 → 6px へ下がり、輪郭画素の数も R1 で
   4448 → 2934、R3 で 14675 → 5619、R5 で 4936 → 3203 と減る。**(b)(c) が輪郭を
   整えた結果、遷移の要求が小さくなっている。** 帯は静的な設定ではなく、
   塗り直しの出力でもある
5. **3px ストラップの帯も芯まで埋まっていない。** S5 は p50 2px で、**4px 以上を
   要求する輪郭画素は 1460 中 150 件、8px 以上は 9 件しかない。** §9.3 の (2) が
   前提にした「幅 3px のストラップでは芯まで埋まり Dirichlet の支えが消える」も、
   **少数の画素でしか起きていない。** 粗さが 0.082 → 0.272 へ出る原因は別にある

### 条件の文面と実測の食い違い

**§9.2 の表と中止条件 1 は「中央値が 8px 以上」と書いた。R6 は 8px でこれを
満たすが、S4 は 6px で満たさない。** それでも中止するのは、読み取り 2 のほうが
条件より強いからである——**条件を書いた時点で、帯幅が半径であることを
見落としていた。** 総幅（2r+1）で読めば S4 は 13px、R6 は 17px で、どちらも
真の遷移 8px を覆っている。

**しきい値を後から下げて「満たした」ことにするのではない。** 満たすべき量の
**定義が間違っていた**ので、条件の文面ではなく前提の側が崩れている。§9.2 が
「分布を見れば的が決まる」と書いた判断そのものは働いた——決まったのは
「的は帯幅ではない」という向きである。

### この段の行き先

**中止条件 1 のとおり、帯には手を付けない。** §9.3 の (1)(2) はどちらも
「帯が遷移に届いていない」という前提に立っていて、その前提が消えた。

**§9.7 の受け入れ条件は §9.3 を実装する前提のものなので、ここでは判定しない。**

形をここでも採るが、**動かす先はまだ測っていない。** 次の疑いは §9.2 と

- **Σ / ε の窓。** §8.10 の掃引で窓半径 1 → 4 が S4 0.1849 → 0.1436、
