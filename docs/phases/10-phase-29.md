# 10. Phase 29: 素材と文字を spec から組む

節番号は分割前のまま変えていない。`計画 §8.6` のような参照が他の節・src / tests から
張られていて、**番号が識別子として働いている**からである。どの節がどのファイルに
あるかは [実装計画](../implementation-plan.md) の索引で引く。

EC の商品ページに載るのは商品そのものの画像だけではない。寸法・素材・使い方を文字で
説明する画像が並び、note の見出し画像も同じ形をしている。**kiri は切り抜きの出口
までは持っているが、その先で素材と文字を組む口が無い。** この段はそこを作る。

**作るのは組版器ではなく合成器である。** どこに何を置くかは spec が決める。kiri は
置いて、**測って、言う**。この向きは design.md §5.6 の「処理結果には実際に何が
起きたかを含める。AI が結果を検証して次の手を打てるようにするため」をレイアウトへ
当てはめたもので、新しい思想ではない。

## 10.1 なぜここか

1. **切り抜きの下流にしか触れない。** 境界品質の的は §9.9 で選び直しになっている
   （帯は真の遷移を既に覆っていた）が、この段はその答えを待たない。入力は
   「切り抜き済みの素材」で、`cutout` のどの経路も読まない
2. **出口が既に揃っている。** キャンバス配置（`transform/canvas.rs`）、straight alpha
   の 1 画素合成、派生出力（`image_io/derive.rs`）、結果 JSON、`--fail-on`、
   `kiri schema` による契約の配布。**足りないのは「文字」と「役割を持った配置」の
   2 つだけ**で、それ以外は既にあるものの上に載る
3. **既定の出力バイト列を 1 ビットも動かさない。** §7.1 の「バイト列を動かす変更は
   バイト列に依存する機能より前に置く」という順序規則に対して、この段は新しい
   コマンドの中で閉じるので順序の制約を受けない。§9 がタイミングを選ばざるを
   えなかったのと逆の位置にある
4. **利用者が名指しで求めた的である。** 「商品画像のほかに説明文などの画像がある」
   「画像と文字を組み合わせたい」「あくまで素材を組み合わせるだけ」。最後の 1 句が
   この段の範囲を決めている（§10.3.2）

## 10.2 着手の第一歩は、検証できる形になるかを確かめることである

**§9.2 と同じ位置にある作業で、問いが違う。** §9 は「診断が正しいか」を疑った。
ここで疑うのは**実現性**で、具体的には 1 つである。

> 組版を外の crate に任せたとき、**組んだ結果の幾何をレイヤ単位で取り出せるか。**

取り出せなければ、kiri が測れるのは画素だけになる。「見出しが枠から 144px はみ出して
いる」「この文字は背後とのコントラスト比が 2.1 で読めない」が言えず、**エージェントが
検証して次の手を打つ**という目的そのものが立たない。その場合この段は中止になる
（中止条件 1）。

### 測った（2026-10-03）

`resvg` 0.48.1 / `usvg` 0.48.1 に、1280x670 のキャンバスと 4 要素を渡した。
見出しはわざと枠に収まらない長さにし、1 行だけ存在しないフォント名を指定した。

| id | spec が書いた位置 | 組んだ後の実測 bbox | 読み |
|---|---|---|---|
| `bg` | 0,0 1280x670 | (0.0, 0.0) 1280.0x670.0 | 一致 |
| `subject` | 700,85 500x500 | (825.0, 85.0) **250.0x500.0** | **書いた枠と実際が違う。** 縦長の素材が枠へ内接し、横 250px に収まって中央へ寄った |
| `heading` | 80,150 から 64px | (80.0, 173.7) **1344.0**x64.0 | **右端 1424 > 1280。144px はみ出している** |
| `lead` | 80,290 から 36px | (80.0, 288.3) 614.7x36.0 | 収まっている（右端 694.7） |
| `ghost` | 存在しないフォント | (80.0, 391.5) 540.0x48.2 | **描けている。黙って別のフォントへ落ちた** |

読み取りは 4 つある。

1. **幾何はレイヤ単位で取れる。** spec に書いた `id` が木に残り、
   `Node::abs_bounding_box()` が組版後の絶対座標を返す。中止条件 1 は発火しない
2. **はみ出しは数で言える。** `heading` の右端 1424 とキャンバス 1280 の差 144px が
   そのまま `TEXT_OVERFLOW` の `data` になる。目で見る必要が無い
3. **「書いた枠」と「実際に置かれた矩形」は違う。** `subject` は 500x500 の枠に
   250x500 で入った。**この差こそエージェントが知りたい値である**——枠を書いた側は
   素材の縦横比を知らないので、返ってこなければ余白の計算ができない
4. **フォントは黙って代替される。** 存在しない `NoSuchFontXYZ` が指定どおりの行高で
   描けてしまった。**これは kiri の側で断らなければ止まらない**（§10.3.4）

同じ入力で日本語と `font-weight` の解決も通っている（システムフォント 913 面を
読み込んだ状態で、見出しが太字で組まれた）。

## 10.3 作るもの

### 10.3.1 `kiri compose`

新しいサブコマンド 1 つ。入力は spec（JSON）、出力は画像 1 枚と結果 JSON。

```
kiri compose layout.json -o thumb.jpg --json
kiri compose layout.json --dry-run --json   # 画素を書かずに幾何だけ返す
```

**`cutout` へフラグとして足さない。** `cutout` は 1 枚を切り抜くコマンドで、組む
相手がその中に無い。`--text` のようなフラグを生やすと、1 つのコマンドが
「切り抜き」と「組版」の 2 つの契約を持つことになる。`batch` の `set` を
`cutout` の CLI から入れなかったのと同じ判断である。

**`batch` の spec とも別にする。** `batch` の spec は「同じ処理を N 枚へ配る」形で、
compose の spec は「N 個の素材を 1 枚へ集める」形である。向きが逆のものを 1 つの
スキーマに同居させると、どちらのキーがどちらで効くのかが読む側から見えなくなる。

### 10.3.2 spec の形

```json
{
  "canvas": { "width": 1280, "height": 670, "background": "#f5f2ec" },
  "font": { "family": "Noto Sans JP", "path": "fonts/NotoSansJP-VF.ttf" },
  "safe_area": [0, 108, 1280, 454],
  "layers": [
    { "id": "subject", "role": "subject", "image": "out/product.png",
      "rect": [700, 85, 500, 500], "fit": "contain" },
    { "id": "heading", "role": "heading",
      "lines": ["素材を組み合わせる", "それだけをやる"],
      "rect": [80, 150, 560, 200],
      "size": 64, "weight": 700, "color": "#1f2328", "line_height": 1.3 }
  ]
}
```

**`role` が検査を決める。** `subject` / `heading` / `body` / `caption` / `decoration`
の 5 つ。文字の役割にはコントラスト比を測り、`decoration` には測らない。
**役割が無ければ何も測れない**——これが生の SVG を受けない理由である（§10.9）。

**文字は行の配列で受け取る。自動で折り返さない。** これが「あくまで素材を
組み合わせるだけ」の線引きである。

- 自動折り返しは**禁則処理**（行頭に句読点・閉じ括弧を置かない、行末に開き括弧を
  置かない）と**字詰め**を伴う。日本語でこれを持つと、この段は合成器ではなく
  組版器になる
- 行をどこで割るかは**文意の問題**で、エージェントが決めるべき側にある。
  kiri が勝手に割ると、割った位置が結果 JSON に出たところで直す口が無い
- 行ごとの実測幅は返す（§10.3.5）。**割る材料は渡すが、割らない**

`rect` は `[x, y, 幅, 高さ]`。文字の `rect` は**枠であって縮小の指示ではない**
——収まらなければ縮めずに `TEXT_OVERFLOW` で言う。`--fill-ratio` が商品を枠へ
合わせるのとは逆の約束で、**文字サイズを黙って変えると、揃えたくて spec を書いた
側の指定が消える**。

### 10.3.3 組版は借りる、契約は自分で配る

内部で spec を SVG へ落とし、`resvg` でラスタライズする。**外から SVG は見えない。**

| | 利用者が書くもの | kiri が約束できること |
|---|---|---|
| 生の SVG を受ける | SVG | **ほぼ無い。** `kiri schema` が配れず、どの要素が何かを kiri が知らない |
| 自前で組版する | spec | 全部。ただし禁則・字詰め・グリフ配置を自分で持つ |
| **spec を受けて内部で SVG へ落とす** | spec | **全部。** 組版だけを外へ出す |

3 つ目を採る。`kiri schema` が `compose` の spec を配れ、未知のキーは
`SPEC_UNKNOWN_FIELD` で断れ、結果 JSON に実際に効いた値を書ける——`batch` の spec で
既に成立している契約が、そのままこちらでも成立する。

### 10.3.4 フォントは明示を要求する。黙って代替しない

§10.2 の読み取り 4 のとおり、指定が外れてもフォントは描けてしまう。これを通すと
**同じ spec が機械ごとに違う絵になる**——kiri の中核の約束（同じ版が同じ入力から
同じ結果を出す）に正面から触る。

- `font.path` が与えられたら**そのファイルだけを読む**。システムのフォント群は
  見に行かない
- `font.family` だけのときはシステムから探し、**見つからなければ
  `FONT_NOT_FOUND` で断る**。代替へ落ちない
- 使ったフォントのパスと SHA-256 を結果 JSON に載せる。`MODEL_NOT_FOUND` と
  `settings` のモデル素性が既にこの形である（`segment/model.rs`）

**`SEGMENT_UNAVAILABLE` と同じ向きである。** feature が無いときに黙って off へ
落とさず断る、という既存の判断をフォントへ写しただけで、新しい作法ではない。

### 10.3.5 測って返す

`--fail-on` の語彙を増やす。**新しい仕組みは作らない**——`Metric::ALL` と
`WarningCode` と exit 5 が既にあるので、そこへ合流させる。

| 指標 | warning code | 何を見るか |
|---|---|---|
| `text_overflow` | `TEXT_OVERFLOW` | 文字の bbox が `rect` を超えた量（px）。超えた向きも返す |
| `text_contrast` | `TEXT_CONTRAST_LOW` | 文字色と、その文字が載る背後の実測輝度のコントラスト比 |
| `layer_overlap` | `LAYERS_OVERLAP` | 文字の bbox と `subject` の不透明部分が重なった面積の比 |
| `safe_area` | `OUTSIDE_SAFE_AREA` | `safe_area` の外へ出た要素がある |

コントラスト比は**背後を実測する**。文字のレイヤを抜いた状態で 1 回描き、文字の
bbox の中の輝度の中央値を採って、文字色との比を出す。背景色の指定から計算すると、
**下に画像が敷いてある場合に必ず外れる**——ちょうどそこが読めなくなる場所である。

`safe_area` には出典がある。note のヘッダー画像は一覧ページで **1280x454 の範囲
だけ**が表示されると公式が書いている
（<https://www.help-note.com/hc/ja/articles/360000231642>）。`Rules` と同じく、
**辿れない数は置かない**。

結果 JSON は**書いた値ではなく効いた値**を返す（canvas ブロックの規約と同じ）。

```json
{ "schema_version": 2, "compose": {
    "font": { "family": "Noto Sans JP", "path": "...", "sha256": "..." },
    "layers": [
      { "id": "subject", "role": "subject", "rect": [825.0, 85.0, 250.0, 500.0] },
      { "id": "heading", "role": "heading", "rect": [80.0, 173.7, 1344.0, 64.0],
        "lines": [{ "width": 1344.0 }, { "width": 512.0 }],
        "overflow": [144.0, 0.0], "contrast": 12.6 }
    ] } }
```

**`--dry-run` で画素を書かずにここまで返す。** エージェントが座標を直す往復は
これで閉じる。画像を見る必要があるときは書かせればよい。

## 10.4 依存の費用（測った。2026-10-03）

| 候補 | MSRV | `-sys` 依存 | crate 数 | 判定 |
|---|---|---|---|---|
| **`resvg` 0.48.1** | **1.85.0** | **0** | 94 | 採る。kiri の MSRV とちょうど同じ |
| `cosmic-text` 0.19.0 | 1.89 | 0 | 46 | **MSRV が 1.85 を超える**（`tract-onnx` と同じ問題） |
| `ghe2d` 0.2.0 | 1.80 | 4（`libwebp-sys` ほか） | 435 | C 依存。`cargo tree -e normal` の約束が壊れる |
| `banner-builder` 0.2.6 | 未宣言 | 0 | 351 | 薄い。自分で書くのと変わらない |

clean release build は **9.7 秒**（CPU 70.6 秒）。`tract-onnx` を足したときの 200 秒
とは桁が違う。

**feature で囲わない。** `segment` を既定で無効にしたのは 2 つの理由からで
（MSRV 1.91、build 50 秒 → 200 秒）、`resvg` は**どちらにも当たらない**。
囲うと `compose` が既定の build で動かず、受け入れ条件が既定で検査できなくなる
（§10.9 で `--segment` を `--optimize` に入れない理由として挙げたのと同じ形）。

バイナリの増分は**まだ測っていない**。上の 9.7 秒は strip も LTO も無い probe での
値で、kiri の 3.26MB とは比べられない。受け入れ条件 (h) で測る。

## 10.5 契約への影響

| 場所 | 変更 |
|---|---|
| `cli.rs` | **`compose` を 1 つ足す。** 既存コマンドの引数は 1 つも触らない |
| `kiri schema` | `commands[]` に `compose`、spec の形、`layers[].role` の候補、新しい指標 4 つ。**キーが増えるだけである** |
| `schema_version` | **2 のまま。** 既存のキーの意味も型も変わらない（design.md §5.6 の規約） |
| `error.rs` | `FONT_NOT_FOUND` を 1 つ。spec 側は `SPEC_INVALID` / `SPEC_UNKNOWN_FIELD` / `SPEC_UNREADABLE` を**再利用する** |
| `warning.rs` | `TEXT_OVERFLOW` / `TEXT_CONTRAST_LOW` / `LAYERS_OVERLAP` / `OUTSIDE_SAFE_AREA` の 4 つ |
| `compliance.rs` | `Metric::ALL` に 4 つ。`--fail-on` の語彙が増える |
| 既存の出力バイト列 | **1 ビットも動かない。** `cutout` / `batch` / `lint` のどの経路も読まない |
| `Cargo.toml` | `resvg` を既定の依存として足す（feature で囲わない。§10.4） |
| `profile.rs` | **この段では触らない。** note のプリセットは §10.9 で送る |

## 10.6 費用

規模は **L**。算術は小さい（幾何の比較と輝度の比だけ）が、**契約の面積が
これまでで最大である**——新しいコマンド 1 つ、spec スキーマ 1 つ、error 1 つ、
warning 4 つ、指標 4 つ。§9 が「契約の面積がほぼゼロ」で L だったのと逆の理由で L になる。

時間とメモリは、ラスタライズ 2 回ぶん（文字あり / 文字なし）が上限である。
1280x670 は切り抜きが扱う 24.5MP に対して 0.86MP で、桁として問題にならない。

## 10.7 テスト方針

1. **幾何の表明を先に書く。** §10.2 で測った 5 要素をそのまま固定する。
   はみ出し 144px、`subject` の 250x500 への内接、どちらも数で合わせる
2. **フォントを断ることを固定する。** 存在しないフォント名で `FONT_NOT_FOUND`、
   exit code、`--json` の `errors[]` まで。**「描けてしまう」ことの裏を取る**ので、
   この表明が落ちたら §10.3.4 が効いていない
3. **決定性。** 同じ spec で 2 回のバイト一致。フォントを `path` で固定した spec と、
   `family` で引いた spec の両方
4. **テスト用のフォントをリポジトリに置く。** システムフォントに依存した表明は
   CI と手元で別の絵になる。ライセンスが明快で小さいものを 1 つ
   （`tests/fixtures/` に、出典と版を添えて）
5. **コントラスト比は合成画像で較正する。** 白地に黒（21:1）、白地に薄灰（既知の値）、
   **下に画像を敷いた場合**の 3 つ。3 つ目が背景色からの計算で外れることを
   同じテストで示す
6. **`kiri schema` が spec を配れていること。** `compose` の spec の全キーが
   `schema` に現れ、未知のキーが `SPEC_UNKNOWN_FIELD` で断られる

## 10.8 受け入れ条件と中止条件

### 受け入れ条件

- **(a) 幾何が返る。** `--dry-run --json` が全レイヤの実測 `rect` を返し、
  §10.2 の 5 要素と一致する。**`subject` の「書いた枠と実際の矩形の差」が
  返ること**——これが返らなければエージェントは余白を計算できない
- **(b) はみ出しが数で返る。** `heading` の `overflow` が `[144.0, 0.0]`、
  `TEXT_OVERFLOW` が 1 本、`--fail-on text_overflow` が exit 5
- **(c) フォントを黙って代替しない。** 存在しないフォント名が `FONT_NOT_FOUND` で
  断られ、**画像が 1 枚も書かれない**
- **(d) コントラストが背後の実測である。** 下に画像を敷いた文字で、背景色からの
  計算と実測が**異なる値になることを表明が示している**
- **(e) 決定性。** 同じ spec で 2 回のバイト一致。フォントは `path` 指定と
  `family` 指定の両方で
- **(f) 既存が 1 ビットも動かない。** `cutout` / `batch` / `lint` / `info` /
  `convert` の md5 ゴールデンが全部無修正で通る。**この段が下流にしか触れない
  ことの裏である**
- **(g) 契約が全部配られている。** `kiri schema` に `compose` と spec の全キーと
  指標 4 つが出る。`every_code_named_in_the_docs_exists` が通る
- **(h) 費用が桁で変わらない。** release バイナリの増分が **+3MB 以内**、
  clean build の増分が **+60 秒以内**。`segment` を既定で無効にした 2 つの理由
  （`Cargo.toml` の `[features]` の doc）のどちらにも当たらないことを数で示す
- **(i) 自動で何もしない。** 文字サイズの自動縮小・自動折り返し・自動配色が
  **0 件**。spec に書いた値が結果 JSON にそのまま効いた値として返る
- **(j) MSRV が 1.85 のまま。** `cargo +1.85 check` が通る

**(a)(b)(d) が的、(c)(e)(i)(j) が「黙って何かを変えていない」ことの裏、
(f)(g)(h) が非悪化。**

### 中止条件

1. **組んだ結果の幾何がレイヤ単位で取れないと分かったら中止する。** →
   **測った。取れる（§10.2）。この条件は発火しない**
2. **(c) が満たせないなら中止する。** フォントの代替を kiri の側で止められない
   なら、同じ spec が機械ごとに違う絵になる。**決定性を失ってまで入れる機能では
   ない**
3. **(f) が落ちたら中止する。** 既存の出力が動くなら、この段は「下流にしか
   触れない」という前提を外している。設計が間違っている合図として扱う
4. **(h) を割ったら中止する。** 既定の build が重くなるなら `segment` と同じ
   feature 化の議論に戻るが、そのとき (g) の「既定で検査できる」が立たなくなる。
   **両立しないなら入れない**
5. **(i) が守れないなら中止する。** 収まらない文字を黙って縮める・折り返すところへ
   一度行くと、この段は合成器ではなく組版器になる。**範囲を決めているのは
   利用者の「あくまで素材を組み合わせるだけ」である**

## 10.9 却下した代替案

- ※ **生の SVG を受ける。** エージェントが SVG を書けるのは本当だが、kiri が
  要素の役割を知らないので**何も測れない**。「見出しが商品に重なっている」
  「この文字は読めない」が言えず、`kiri schema` も配れない。**検証できる形に
  したい、という要求そのものと正面からぶつかる**
- ※ **自前で組版する。** 必要な測定値（行ごとの送り幅、グリフの外接矩形）は
  **まさに組版器が出すもの**なので、自前で書くと同じものを二度払う。禁則と字詰めを
  抱えることにもなる
- ※ **自動折り返し。** 禁則処理を持つと合成器ではなくなる（§10.3.2）。**ただし
  永久に却下ではない**——行ごとの実測幅を返す設計にしてあるので、折り返しが
  必要だと分かった時点で、材料は揃った状態から始められる
- ※ **文字が収まらないときに自動で縮める。** 揃えたくて `size` を書いた側の
  指定が黙って消える。`--fill-ratio` が商品を枠へ合わせるのとは**約束の向きが
  逆である**
- ※ **フォントを同梱する。** 日本語フォントは 5〜20MB で、kiri の 3.26MB に対して
  桁が違う。ライセンスの表示義務も付く。**モデルを同梱しなかったのと同じ判断**で、
  素性（パスと SHA-256）を結果に載せるほうを採る
- ※ **`--profile note` をこの段で足す。** プリセットは「複合指定の別名」で、
  compose の spec が固まる前に別名だけ先に作ると、**指す先が動く**。
  `CanvasChoice` に固定寸法の決め方を足す工事（1280x670 は入力に依らない）も
  含めて、spec が固まった後の独立した段にする
- ※ **`cutout` に `--text` を生やす。** 1 つのコマンドが切り抜きと組版の 2 つの
  契約を持つ。`batch` の `set` を `cutout` の CLI から入れなかったのと同じ理由
- ※ **compose の spec を `batch` の spec へ相乗りさせる。** 向きが逆である
  （N 枚へ配る / N 個を 1 枚へ集める）。同居させると、どちらのキーがどちらで
  効くのかが読む側から見えなくなる
- ※ **`resvg` を feature で囲う。** `segment` を囲った 2 つの理由（MSRV 1.91、
  build 200 秒）のどちらにも当たらない（1.85.0 / 9.7 秒）。囲うと既定の build で
  受け入れ条件が検査できなくなる

## 10.10 実装（2026-10-03）

**受け入れ条件は全部満たした。中止条件はどれも発火していない。** 以下は計画との
差分と、測った値である。計画の本文は直していない——**直すと「何を予定して、
何が違ったか」が残らない**（§8.10 / §9.9 と同じ扱い）。

### 計画と違えた 6 点

1. **画像は resvg へ渡していない。** §10.3.3 の表は「spec を SVG へ落とす」と
   1 行で書いていたが、`raster-images` を有効にすると resvg が自前のデコーダで
   `<image>` を読む。kiri は EXIF の向きと ICC → sRGB を `image_io/load.rs` で
   正規化しているので、**そこを迂回すると色と向きの契約が compose でだけ崩れる**
   ——同じ素材が `cutout` を通ったときと `compose` を通ったときで違う色になる。
   画像は kiri が読んで既存の合成（`transform::canvas::composite`）で重ね、
   resvg へ渡すのは**文字だけ**にした。resvg の feature から `raster-images` と
   `svgz` を外してある
2. **コントラストのために描き直していない。** §10.3.5 は「文字のレイヤを抜いた
   状態で 1 回描き」と書いていたが、**層を spec の順に 1 つずつ重ねる**形にすると、
   重ねる直前のキャンバスがその文字の背後そのものになる。描画が 1 回で済むうえ、
   層の順番も保たれる（文字をまとめて最後に重ねると、文字が必ず画像より上に来る）
3. **`text_overflow` は数 1 つである。** §10.3.5 は `[右, 下]` を想定していたが、
   `--fail-on` が比べられるのは数 1 つなので、配列にすると「どの要素と比べるのか」
   を門の側で決めることになる。**どの向きであれ最も大きい 1 つ**を返し、向きが
   要るなら `rect` と `placed` の差で出る——**同じ事実を 2 つのキーで配らない**
4. **指標名を結果 JSON のキーに合わせた。** §10.3.5 の表は `safe_area` と
   書いていたが、キーは `outside_safe_area` である。`compliance::Metric` の
   「名前は結果 JSON のキーそのまま」という規約をこちらでも守る——`contrast` /
   `overflow` / `subject_overlap` という当初の綴りも、すべて指標名と同じへ直した
5. **`--fail-on` は compose 専用の語彙にした。** §10.3.5 は「`Metric::ALL` へ
   合流させる」と読める書き方をしていたが、混ぜると
   **`cutout --fail-on text_overflow` が書式として通る。** cutout に文字は 1 つも
   無いので、その門は永久に発火しない——書いた本人は合格が出続けるのを見て
   「通っている」と読む。`compliance::Metric::range` が値域を断る理由として
   挙げているのと同じ形の事故である。共有したのは `Operator` だけで、
   **関係の綴り（`>` と `gt`）を 2 通り持たない**ためである
6. **error が 2 つになった。** §10.5 は `FONT_NOT_FOUND` 1 つと書いていたが、
   「ファイルは読めたが字体として解析できない」は別の失敗なので
   `FONT_UNREADABLE` を足した（`MODEL_NOT_FOUND` と `MODEL_UNREADABLE` と同じ
   割り方である）

### 測った費用（受け入れ条件 (h)）

同じ機械で `cargo clean` から `cargo build --release` を 1 回ずつ。

| | clean build | バイナリ |
|---|---|---|
| `main`（compose 無し） | 52.7 秒 | 3.86 MB |
| この段 | 67.6 秒 | 5.86 MB |
| **増分** | **+14.9 秒** | **+2.00 MB** |

条件は「+3MB 以内 / +60 秒以内」なので**どちらも通る。** `segment` を feature で
囲った 2 つの理由（MSRV 1.91、build 50 秒 → 200 秒）のどちらにも当たらない。
`cargo +1.85 check --locked --all-targets` も通る（受け入れ条件 (j)）。

- ※ `Cargo.toml` の `[features]` の doc は素の kiri を 3.26MB と書いているが、
  この機械の `main` は 3.86MB である。**rustc の版が違うだけで、この段の増分とは
  関係が無い。** 直さないのは、あの数が書かれた時点の実測だからで、**後から
  別の機械の値で上書きすると、どの版で測ったのかが分からなくなる**

### 字体のフィクスチャは置いていない（§10.7 の 4 と違う）

計画は「テスト用のフォントをリポジトリに置く」と書いたが、置いていない。
**`tests/segment.rs` がモデルに対して採ったのと同じ扱い**にしてある——日本語の
字体は 5〜20MB あり、ライセンスの表示義務も付く。置いていない機械では、字体を
要する検査だけが黙って飛ぶ。

代わりに、**字体の綴りに依存する数を 1 つも表明していない。** 「この見出しの
外接矩形は 1344px」は字体ごとに違う値になるので、機械をまたいで固定できる約束では
ない。固定したのは関係である。

- 枠より広ければ `text_overflow` が正になる
- 1 行のとき `line_widths[0]` が `placed` の幅と一致する
- 白地に黒は 21 に近く、暗い板の上の黒は 3 を下回る
- 同じ spec は 2 回ともバイト一致し、`family` で引いた実行と `path` で固定した
  実行も一致する（**字体のファイルは 1 回目の結果 JSON が教えてくれる**ので、
  リポジトリに置かずに 2 通りを確かめられる）

**画像の内接だけは数で固定してある。** 200x400 の素材が 160x160 の枠へ
`contain` で入ると 80x160 になり、枠の中央へ寄る——字体に依らないので、
§10.2 の読み取り 3 をそのまま表明にできる。

- ※ **CI で文字の検査が 1 つも走らない機械がありうる。** 字体を 1 本も持たない
  環境では `any_font()` が `None` を返し、文字を伴う 9 件が飛ぶ。字体を
  リポジトリへ置くかどうかは**ライセンスの表示義務を負うかどうかの判断**なので、
  この段では決めずに残した
