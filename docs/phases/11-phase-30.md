# 11. Phase 30: 切り抜きを速く、軽くする

節番号は分割前のまま変えていない。`計画 §8.6` のような参照が他の節・src / tests から
張られていて、**番号が識別子として働いている**からである。どの節がどのファイルに
あるかは [実装計画](../implementation-plan.md) の索引で引く。

Phase 29 までに積んだのは品質と契約の段である。**速さと軽さを正面から測った段は
1 つも無い。** §6 が「P1 性能 9 件」として片付けたと書いているものは推論（f16 へ
畳む）・見立ての持ち回り・`batch` の並列で、**切り抜きそのものの経路は 1 度も
測られていない**。この段はそこを埋める。

**この段は品質の的を 1 つも動かさない。** 受け入れ条件は「同じ入力から同じ品質
指標が出ること」で、速さと RSS だけが動く（§11.6）。

## 11.1 なぜここか

1. **品質の的が §9 で選び直しになっている。** 帯は真の遷移を既に覆っていた、が
   §9 の結論で、次の品質の工事は「何を測るか」から決め直す必要がある。その答えを
   待たずに進められる工事がこれである
2. **測る道具が無い。** 結果 JSON の `elapsed_ms` は 1 回の実行の合計しか言わない。
   どの段が重いかを言える道具が無いまま「速くする」に着手すると、効いたかどうかを
   実行の合計でしか見られない。**最初の作業は道具を作ることである**（§11.4）
3. **現場で効く大きさの数字が出ている。** 24.5MP 1 枚で 5.7 秒・872MB は、EC の
   数百点を回す使い方では素通りできない。しかも**本体の 5 秒の間、14 コアのうち
   1 つしか動いていない**（§11.2 の読み取り 1）
4. **出力を動かさずに進められる。** §7.1 の「バイト列を動かす変更はバイト列に
   依存する機能より前に置く」という順序規則に対して、この段は**バイト列を動かさ
   ないことを受け入れ条件に持つ**ので、順序の制約を受けない

4. **形態素処理は単独では 1.8% しかない。** `sample` の自己時間では `separable`

5. **メモリは 1 枚あたり 872MB で、RGBA 1 枚（98MB）の 8.9 倍である。**

## 11.3 段の分け方

**プロファイルの山で切る。** 機能やファイルの大きさで切ると、1 回のレビューに山と
平地が混ざり、効いたのがどれか分からなくなる。1 バッチ 1 コミット、各コミットで
§11.6 の受け入れ条件を満たすこと。

| # | 的 | 主な対象 |
|---|---|---|
| 0 | 計測の土台と方針 | この文書、`cutout/stage.rs` |
| 1 | フィルの下ごしらえを 1 度だけにする | `cutout/floodfill.rs`、`cutout/mod.rs` の `second_pass` |
| 2 | 一時確保を削る（ピーク RSS が的） | `cutout/edges.rs` の Sobel、`floodfill` の測地的オープニング |
| 3 | 画素独立の段を並列化する | Lab の表 / 分類 / 堤防 / 形態素 / マスクの組み立て / 診断 |
| 4 | `morphology::separable` を語単位にする | `cutout/morphology.rs`（フィルと `refine` の両方から引かれる） |
| 5 | 場の推定 | `cutout/background.rs` |
| 6 | 境界の帯 | `cutout/refine.rs` |
| 7 | 命令経路 | `commands/cutout.rs`、`cutout/optimize.rs`、`commands/batch.rs` |

**当初ここに 4 つ並べていたものを 8 つへ割り直した。** バッチ 1 を測ったら、
分け方の前提が 2 つ崩れたためである（§11.8）。

**バッチ 1 から始める。** 時間の最大（50.8%）とメモリの最大の単体（147MB × 2）が
同じ場所にあり、しかも「2 回走る」という形のはっきりした的が 1 つ立っている。

**形態素処理は独立のバッチにしない。** §11.2 の読み取り 4 のとおり、単独では
1.8% しかなく、効く場所は `refine` と診断の中である。バッチ 2 と 3 の内側として扱う。

**バッチ 4 は最後である。** 単枚を並列化すると `--jobs` の意味が変わる（§11.5）ので、
中身を決めてから外周の契約を直す。

## 11.4 計測のやり方

**段ごとの時間は本体が持つ。** テスト側で測ろうとすると `cutout_seen` の順序を
写し取るほかになく、写しは必ず本体から遅れる。2 回目のフィルのように「同じ段が
条件付きで 2 度走る」構造は、写しでは最も再現しにくい。

```
KIRI_STAGE_MS=1 /usr/bin/time -l \
  kiri cutout <入力> --output /tmp/a.png --force --tolerance 60 --json > /tmp/a.json
```

1 度の実行で 3 つとも採れる。段ごとの時間とピーク RSS は stderr、品質の基準値は
stdout の JSON（`mask` と `warnings`）である。`/usr/bin/time -l` は macOS の綴り。

**素材はリポジトリに置かない。** 24.5MP の実写は大きすぎるし、`KIRI_BENCH_DIR` が
「実写に正解アルファを付けるのは人にしかできない作業なので、リポジトリには置かず、
環境変数で差し込めるようにしておく」と決めた筋をここでも通す。性能だけを見るなら
正解アルファは要らないので、素の写真 1 枚を手元に置いて絶対パスで渡す。

**段より細かく見たいときは `sample` を使う。** 既定の `--release` は strip する
ので、記号を残して建て直す。

```
cargo build --release --config profile.release.strip=false --config profile.release.debug=true
```

ただし §11.2 の読み取り 4 のとおり、**自己時間だけを見て段を切らないこと。**

## 11.5 並列化の方針

本体が単一スレッドなので、段の中身を削るより並列化のほうが大きく効きうる。
**先に決めておかないと `batch --jobs` の意味が静かに変わる。**

いま `commands/batch.rs` は `--jobs` 本のプールを建て、`jobs == 1` では建てない
（「1 スレッドのプールで回すのと結果は同じだが、費用を払う理由が無い」）。
単枚の中に `par_iter` を入れると、ここが 2 通りに割れる。

- `--jobs N`（N ≥ 2）: 内側の `par_iter` は**そのプールの中**で走る。スレッドの
  総数は N のままで、増えない
- `--jobs 1`: プールが無いので内側は**大域プールを掴み、全コアを使う**。
  「1 スレッドで回すのと同じ」という現在のコメントが**偽になる**

**方針はこうする。**

1. **`--jobs` の意味を「同時に開く画像の枚数」へ寄せる。** メモリは 1 枚 872MB で、
   同時に開く枚数が支配因子である。スレッド数を絞ってもメモリは減らない。逆に
   「1 枚ずつ・全コアで」が**最も軽くて最も速い**構成になる
2. 単枚の並列化で**新しいプールを建てない**。大域プールか、呼び出し元が建てた
   プールに従う
3. **並列化で結果が 1 ビットも変わらないこと。**

   **当初ここに「フィルの連結たどりは順序に依存するので並列化しない」と書いたが、
   これは誤りだった。** `expand` の `visit` が辺を通すかどうかは `candidates`・
   `lab`・進行方向だけで決まり、**フィルの状態を一切見ていない**（`from` は遷移元
   の画素の Lab であって、埋まり具合ではない）。したがって埋まる集合は静的な
   有向グラフの到達閉包で、訪問順に依らない。影の段の距離も FIFO の BFS が与える
   最短ホップ数なので、層同期の並列 BFS で同じ値が出る。

   **ただし「順序に依らないから並列化してよい」と「並列化する価値がある」は別**
   である。フィルの BFS は 2 回で約 320ms（6%）で、画素独立の段（Lab の表・分類・
   堤防・形態素・マスクの組み立て）のほうがはるかに大きい。並列化はそちらから
   当て、BFS は後回しにする。

   浮動小数の和を並列に畳む箇所は作らない——加算の順序で最下位ビットが動くため。
   並列化してよいのは、出力の添字ごとに書くか、整数の和だけを取る段に限る
4. `--jobs` のヘルプと README の文面を直すのは**バッチ 4** で行う。文面と実態が
   食い違う期間を作らないため、バッチ 1〜3 では `batch` の挙動に触れない

## 11.6 受け入れ条件

各バッチが満たすこと。

1. **品質の基準値（§11.2）が 1 つも動かない。** `foreground_ratio` / `separability`
   / `halo_ratio` / `edge_width` / `contour_roughness` と警告の 4 本
2. `cargo test` が通る。とくに `tests/edge_quality.rs` と `tests/real_backgrounds.rs`
3. `cargo clippy --all-targets -- -D warnings` と `cargo fmt --check` が通る
4. **段の表で、狙った段が実際に縮んでいる。** 全体が縮んでも狙った段が動いて
   いなければ、効いたのは別の何かなので原因を書く
5. ~~ピーク RSS が増えない~~ **差し替えた（バッチ 4）。** ピーク RSS を増やす
   判断をしてよい。ただし**増える理由と、増えた分を取り戻す道筋を文書に
   書き残すこと**を条件にする。
   - 元の条件は「並列化の費用をメモリで払わない」という良い縛りだったが、
     refine の並列化で**-0.77 秒と +85MB が同じ変更から出てきた**。片方だけを
     取る手が無く、どちらを優先するかは kiri の外（利用者が何に困っているか）
     でしか決まらない。**条件が判断を代わりにするのは、判断が要らない場合
     だけである**
   - 判断は時間を優先する側に置いた（§11.11）

段の合計が実測の全体と食い違ったら、`mark` の置き忘れである（表の最終行が
「うち段に数えていない」を出す）。

## 11.8 バッチ 1 の結果（2026-10-05）

**下ごしらえ（Lab の表・堤防・種の保護円）を 1 度だけ作るようにした。**
`foreground_mask` を `prepare` と `fill` に割り、2 回のフィルで使い回す。
あわせて、1 画素も変えない全画素走査を 3 本（確定背景の塗り直し、bbox の内側、
最後の中間 `Vec<bool>`）を削った。

| | 基準 | バッチ 1 | 差 |
|---|---|---|---|
| 合計 | 5058.0 ms | 4817.7 ms | **-240.3 ms (-4.7%)** |
| 背景の推定 | 269.1 | 273.4 | +4.3 |
| フィルの下ごしらえ | （各フィルの中） | 420.9 | — |
| フィル 1 回目 | 1159.6 | 784.7 | — |
| フィル 2 回目 | 1411.9 | 1065.8 | **-346.1** |
| 境界の帯 | 1794.4 | 1848.4 | +54.0 |
| 診断 | 303.4 | 303.9 | +0.5 |
| ピーク RSS | 872.4 MB | 869.8 MB | -2.6 MB |

出力の PNG は基準と**バイト単位で完全一致**。`mask` の 7 項目と警告 4 本も同一。

### 読み取り

1. **効いたのは 2 回目のフィルだけで、それは狙いどおりである。** 1 回目は
   仕事が同じなので動かない（下ごしらえ 420.9 + フィル 784.7 = 1205.6 に対し、
   もとは 1159.6。差 46ms は実行ごとの揺れの範囲で、同じ条件の 2 回の測りが
   4771.2 と 4817.7 だった）
2. **回数を減らしてもピーク RSS は下がらない。** 2 回目の Sobel が消えても
   869.8MB のままなのは、ピークが **1 回目**の Sobel の一時確保（輝度 f32 98MB
   ＋強度 f32 98MB ＋向き 24.5MB）で決まっているからである。**ピークは最大値
   であって総量ではない**——この当たり前を、回数を半分にしてから思い出した。
   メモリを減らすには確保そのものを小さくするほかなく、それをバッチ 2 に立てた
3. **下ごしらえは 2 回のフィルを終えたら手放す。** 最初は `cutout_seen` の最後
   まで生かしていて、Lab の表 147MB が境界の帯と診断に重なり、**ピーク RSS が
   872.4 → 875.9MB と増えた**。受け入れ条件 5 がそれを捕まえた

## 11.9 バッチ 2 の結果（2026-10-05）

**一時確保を削った。** 的は §11.8 の読み取り 2——ピークは最大値であって総量
ではないので、呼ぶ回数ではなく確保そのものを小さくするほかない。

- `edges::edge_ridges` の輝度 → Sobel → 非極大抑制を**行を流しながら 1 回の
  走査**に畳んだ。全画面の表（輝度 f32 98MB・強度 f32 98MB・向き 24.5MB）を
  3 行ずつの環に置き換え、5712px 幅でも合わせて 200KB を切る
- `edge_ridges` の戻り値を `Vec<bool>`（24.5MB）から `BitPlane`（3MB）へ
- 測地的オープニングの収縮の入力も `BitPlane` へ。ここは元の背景マスクと
  同時に生きるので、そのぶんがそのままピークに乗っていた

| | 基準 | バッチ 1 | バッチ 2 | 基準からの差 |
|---|---|---|---|---|
| 合計 | 5058.0 ms | 4817.7 | 4809.3 | -248.7 ms (-4.9%) |
| フィルの下ごしらえ | — | 420.9 | 337.3 | — |
| **ピーク RSS** | **872.4 MB** | 869.8 | **779.3** | **-93.1 MB (-10.7%)** |

出力の PNG は基準と**バイト単位で完全一致**。

### 読み取り

**220MB の一時確保を消して、ピークが下がったのは 90MB だった。** 残りは
別の山が引き受けている——Lab の表 147MB と、候補フラグ・芯・第 2 段・影の
距離が同時に生きるフィルの最中である。**ピークを下げる作業は、最大の山を
削るたびに次の山が顔を出す**ので、1 回では終わらない。次に削るならフィルの
中の `Vec<bool>` 群（1 本 24.5MB）である。

## 11.10 バッチ 3 の結果（2026-10-05）

**画素ごとに独立な段を並列化した。** §11.5 の条件（出力の添字ごとに書くか、
整数の畳み込みだけ）を満たす 3 つに当てた。

- `lab_map`（24.5MP で `cbrt` を 7350 万回）を塊に割る。rayon の `collect` は
  入力順を保つので並びは変わらない
- `classify` を行に割る。影が 1 つでもあったかは行ごとの真偽を OR で畳む
- マスクの組み立てを添字ごとに割る

あわせて `--jobs` の契約の文面を直した（§11.5 の 4 でバッチ 7 へ送っていたが、
**挙動が変わる PR と同じところに置かないと、文面と実態が食い違う期間ができる**）。
`--jobs` はスレッド数ではなく「同時に開く画像の枚数」で、`--jobs 1` は
「1 枚ずつ・全コアで」になる。

### 読み取り

1. **初めて user が real を超えた**（5.42 / 5.01）。14 コアのうち 1 つしか

2. **境界の帯が全体の 42.6% になった。** 1854.6ms は基準からまったく動いて
   いないのに比率だけが上がった——**他が縮んだので、いま最大の的はここ**である
3. 落ちたテストが 1 本あった（`the_published_prose_has_no_stray_spaces`）。
   CLI のヘルプは**段落を 1 行で書く**のがこの綴りの流儀で、折り返すと配る
   文面で日本語の間に半角スペースが入る。検査がそれを捕まえた

## 11.11 バッチ 4 の結果（2026-10-05）

**境界の帯（refine）のタイル走査を並列化した。** タイルは自分のタイルの画素
しか書かない（読みだけが積分画像の余白ぶん外へ伸びる）ので、`TILE` 行ずつの
帯に割れば書き先が重ならない。

- 書き先（出力画像とマスク）を帯ごとの可変スライスに分けた
- 色から決まった画素の印（`guided::Solved`）は 64 画素を 1 語に詰めるので、
  語が行をまたぐ。帯ごとに添字を溜め、帯 1 本を終えたところで錠を取って
  まとめて立てる
- 代役前景の受け皿を `OnceCell` から `OnceLock` へ（スレッド間で 1 度だけ作る）

あわせてフィルの真偽表（`fill_from_border` / `expand` / 測地的オープニング）を
`BitPlane` へ寄せた。1 本 24.5MB が 3MB になる。

### ピーク RSS が増える理由

**refine の作業領域をスレッドごとに持つため**で、1 スレッドあたり約 6MB
ある。中身は、積分画像を張る領域（タイル 128px に窓と代役前景の近傍ぶんの
余白を足した正方形）に対する

- 確定前景と確定背景の色の積分画像 2 本（セルあたり f64 の色 3 成分と個数）
- 線形 RGB の写し（セルあたり f32 の 3 成分）
- 真偽の面 3 本

で、どれもタイル 1 枚を解くのに要る。**f32 へ落とせば半分になるが、積分画像の
足し込みを f32 でやると桁落ちで値が変わる**ので、出力をビット単位で保つという
この段の前提と両立しない。

**フィルの真偽表をビット面へ寄せてもピークは下がらなかった**（1 スレッドで
771.6 → 775.2 MB）。フィル期の高水位はもともと refine 期の山より低く、削ったのは
最大値ではなかったからである。§11.8 の読み取り 2 とまったく同じ形の勘違いを
2 度した——**ピークを下げたいなら、まずどの段が山かを測ること。**

### 増えた分を取り戻す道筋

大きい順に 3 つある。どれもこの段では手を付けない。

1. **refine の `image.clone()`（98MB）。** いま refine は出力用に画像を丸ごと
   複製している。元画像は `boundary_separability` と診断が読むので、元と出力の
   2 枚が同時に必要なのは避けられない——**ように見える**。しかし despill が
   書き換えるのは帯の画素だけで、24.5MP の実写では全体の数 % しかない。
   「書き換えた画素だけを持つ重ね合わせ」にすれば、98MB が帯の画素ぶん
   （数 MB）になる。アルファの適用（`apply_alpha`）まで含めて出口を 1 本に
   畳む工事になるので、独立した段として立てるのが筋である
2. **積分画像の余白。** `plan_tile` は帯の外接矩形から余白を取るので細い帯では
   既に小さいが、窓の最大（`window_for(band_max)`）と代役前景の近傍半径を
   足した分だけ四方へ広げている。帯幅の分布（`band_width_histogram`）は
   すでに測ってあるので、**タイルごとの窓を帯幅の分布から決める**余地がある
3. **スレッド数の上限。** rayon のスレッド数を決める環境変数を絞れば、その
   ぶんピークも下がる（上の表はそれで測った）。メモリが足りない環境向けの弁
   としては今すぐ使えるが、**kiri の契約にはしていない**——環境変数で挙動が
   変わることを `kiri schema` が言えないので、必要になったら `--jobs` と同じ
   考え方の旗として入れること

### 判断

**時間を優先した。** 1.19 秒（-20.7%）と 85MB（+11%）の取引で、EC の現場では
数百点を回す待ち時間のほうが効く。メモリは基準（872.4MB）をまだ下回っている
（860.2MB）ので、**この段を通しても出発点より悪くはなっていない**。

## 11.12 バッチ 5 の結果（2026-10-05）

**形態素処理を語単位にした。** `morphology::separable` は 1 画素ずつ窓を舐めて
いて、24.5MP・半径 1 では横と縦で 1 億 4700 万回の読みになっていた。

- 1 語 64 画素を一度に畳む。横はビット列をずらして AND/OR、縦は行どうしを
  そのまま AND/OR
- **窓の外は単位元で埋める**（収縮なら全ビット 1、膨張なら 0）。畳んだ答えが
  「窓に含めない」と同じになるので、枠の外の扱いを分岐で書き分けずに済む
- 入口と出口に `BitPlane::read_bits` / `insert_bits` を足した。面は画素の添字を
  そのまま詰めて行で揃えないので、行ごとに作った結果はずらして重ねる

### 読み取り

**1 つの関数を直して 3 つの段が縮んだ。** `separable` はフィルの測地的
オープニング（1 回のフィルで 2 回）と refine の隙間の閉じ直しから引かれる。
§11.8 の読み取り 4 で「面積フィルタは単独では 1.8% しかない」と書いたのは
段の表の読み方としては正しかったが、**`separable` という関数で見ると全体の
20% 近くあった**。段で切るか関数で切るかで的が変わる——どちらか一方だけを
見ていると取り逃がす。

## 11.7 中止条件

- **並列化しても速くならない。** メモリ帯域で頭打ちなら、コアを足しても縮まない。
  バッチ 1 の最初の測りでそれが出たら、段の中身（Lab の表の作り方、2 回目の
  フィルの要否）へ寄せて並列化は捨てる
- **品質の基準値が動く打ち手しか残らない。** その場合はこの段を止め、「品質を
  動かしてよいか」を別の段として立て直す。速さのために黙って品質を動かさない
