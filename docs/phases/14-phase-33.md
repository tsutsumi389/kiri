# 14. Phase 33: 文字を置ける空き領域を返す（`--free-regions`）

節番号は分割前のまま変えていない。どの節がどのファイルにあるかは
[実装計画](../implementation-plan.md) の索引で引く。

compose は**置いて、測って、言う**。言えるのは「置いた結果がまずい」ことだけで、
**どこへ置けばよかったか**は言わない。エージェントは文字の `rect` を当て推量で
書き、`LAYERS_OVERLAP` や `OUTSIDE_SAFE_AREA` が出たら書き直す。この往復は
spec を書く側が**商品の形を知らない**ことから生じる。`opaque_rect` は外接矩形
にすぎず、瓶や斜めに置いたリモコンでは、矩形の内側にも文字を置ける場所が大きく
残っている。

この段では、**商品の不透明な画素と既存の文字を避けた、空いている矩形の候補**を
返す。置くかどうかを決めるのは spec の側で、kiri は自動では配置しない
（合成器であって組版器ではない、という §10 の線を守る）。

## 14.1 なぜここか

1. **kiri にしかできない。** 空きは切り抜いた alpha の形で決まる。外接矩形しか
   知らないエージェントには、画素単位の空きを出せない
2. **測りの材料はすでに揃っている。** `build` は `subject` の不透明マスクと、
   文字ごとの `placed` を持っている。足すのは、それを最後に 1 回歩く処理だけである
3. **往復が一番減る。** 「`--dry-run --free-regions` → 候補の 1 つに `rect` を
   書く → 組む」の 2 手で済み、重なりの警告で書き直すループがなくなる
4. **既存の出力を 1 バイトも動かさない。** フラグを渡さなければキーごと出さない
   （`profile` / `previews` と同じ扱い）

## 14.2 作るもの

### 14.2.1 使い方

```
$ kiri compose layout.json -o thumb.png --dry-run --free-regions --json | jq .free_regions
```

```json
{
  "within": [0, 108, 1280, 454],
  "margin": 24,
  "min_size": [196, 98],
  "cell": 8,
  "regions": [
    { "rect": [0, 108, 472, 454], "area_ratio": 0.36875 },
    { "rect": [1072, 108, 208, 128], "area_ratio": 0.04581497797356828 }
  ]
}
```

（`--profile note` で、傾けた楕円の商品を `[500, 40, 700, 600]` に置いた spec の
実際の出力。`within` の縁は障害物ではないので、そこからは `margin` を空けない。
2 つ目は商品の外接矩形の右上の内側にかかる候補である）

| キー | 意味 |
|---|---|
| `within` | 探した範囲。`safe_area` があればそれ、無ければキャンバス全体 |
| `margin` | 障害物から空けた距離（px）。候補と障害物の画素の間に、少なくともこの数の画素が挟まる |
| `min_size` | これより小さい候補は捨てた `[幅, 高さ]`（§14.2.4） |
| `cell` | 探索に使った格子の大きさ（px）。候補の座標は `within` の左上からこの倍数へ**内向きに**丸める（右端と下端だけは `within` の端に一致しうる。§14.6 の 1） |
| `regions[].rect` | 空いている矩形 `[x, y, 幅, 高さ]`。**中のどの画素も、障害物の画素からチェビシェフ距離で `margin` を超えて離れている**（間に `margin` 画素以上を挟む） |
| `regions[].area_ratio` | `within` に対する面積の比 |

並びは面積の大きい順で、面積が同じなら `(y, x)` の小さい順、それも同じなら幅の
小さい順にする（決定性のため。同じ左上・同じ面積の縦長と横長は縦長が先）。

### 14.2.2 何を障害物と数えるか

| 層 | 障害物の形 | 理由 |
|---|---|---|
| 画像で `role` が `decoration` でないもの | **不透明度が 0 でない画素** | 外接矩形で数えると、瓶の肩の横のような空きが消える。`layer_overlap` が `subject` の画素で数えるのと同じ考え方 |
| 文字（すべての role） | `placed` の矩形 | 文字は行間ごと 1 つの塊として読まれる。グリフの画素だけを避けると、行間に別の文字を差し込む候補が出てしまう |
| 図形 / `decoration` の画像 | 数えない | 帯や背景の写真は**文字を載せる下地**であって、避ける相手ではない |

`subject` 以外の画像（`heading` の役割を持つロゴなど）も障害物に数える。
`layer_overlap` は `subject` だけを数えるので、ここは線引きが違う。重ならない
ことを望まない画像は `decoration` と書けばよい。

### 14.2.3 求め方

1. 障害物マスクを原寸で作る（上の表。1 画素 1 ビット）
2. `margin` だけ膨らませる（正方形の近傍）。**膨らませたマスクは作らない**——
   セルに膨らませた障害物が掛かるかは「セルを `margin` だけ広げた範囲に障害物の
   画素があるか」と同じなので、横と縦に分けた 2 回の累積で問う（§14.6 の 2）
3. `cell` px の格子へ**保守的に**畳む。広げた範囲に障害物の画素が 1 つでもあれば
   そのセルは埋まっていると数える。格子は `within` の左上から引き、右端と下端の
   端数のセルは `within` の内側へ切り詰める（`within` の外の画素は含めない。
   §14.6 の 1）
4. 格子の上で**極大な空き矩形**（どの方向にも広げられない矩形）をすべて列挙する。
   行ごとにヒストグラムとスタックを使う標準的な方法で、計算量は O(セル数)
5. `min_size` より小さいものを捨てる
6. 面積の大きい順に並べ、**面積の 70% 以上がすでに残した候補のどれか 1 つの
   中に入るもの**を捨てる。最大 8 個で止める（§14.6 の 3）

ステップ 6 で「重なったら捨てる」としないのは、L 字型の空きでは横長と縦長の
2 つの極大矩形が角で重なり、**どちらも別の使い道がある**からである
（横長は 1 行の見出し、縦長は箇条書きに向く）。

格子に畳むのは、極大矩形の数が輪郭のギザギザの数に比例して増えるからである。
原寸のまま列挙すると、切り抜きの縁の 1 画素ごとに矩形が生まれる。
1280 × 670 を 8px で畳むと 160 × 84 = 13,440 セルになる。

### 14.2.4 既定値

| 値 | 既定 | 根拠 |
|---|---|---|
| `margin` | `round(canvas.width × 24 / 1280)`。`--free-margin <px>` で上書きできる | 文字が商品に触れて見えない距離。note の 1280 幅で 24px（実写で確かめ、§14.7 で必要なら直す） |
| `min_size` の高さ | `--profile` があれば、最も狭い表示で 11px になる文字 1 行の高さ（`11 × canvas.width / 表示幅`。note なら 98px）。無ければ `canvas` の短辺の 8% | 読めない大きさの文字しか入らない候補は、出しても使い道がない |
| `min_size` の幅 | 高さの 2 倍 | 2 文字を下回る幅に見出しは入らない |
| `cell` | 8px（固定。公開はするが変えられない） | §14.2.3 の 3。`margin` より十分小さい |

## 14.3 契約への影響

| 場所 | 変更 |
|---|---|
| CLI | `--free-regions`（旗）、`--free-margin <px>`（`--free-regions` が無いと exit 2） |
| `ComposeReport` | `free_regions`。**渡さなければキーごと出さない** |
| `kiri schema` | `compose` のオプションに上の 2 つ、出力に `free_regions` の形 |
| `schema_version` | **2 のまま。** キーが増えるだけ |
| error / warning | 新しい code は無い。`--free-margin` の範囲外（負・有限でない）と `--free-regions` の欠けは clap の引数検査で断る（exit 2。`--preview` に `--profile` が無いときと同じ扱いで、kiri の code は付かない） |

## 14.4 受け入れ条件

1. `--free-regions` を渡さない実行の結果 JSON（`elapsed_ms` を除く）と出力の
   バイト列が main と一致する（`tests/compose.rs` の釘を含む）
2. 層が無い spec では、**`within` そのもの**が候補として 1 つだけ返る
   （障害物が無いので、`margin` を空ける相手も無い）
3. 中央に正方形の不透明な `subject` を置くと、左右の帯と上下の帯の 4 つが返り、
   どの候補も `subject` の `opaque_rect` から `margin` を超えて離れている
   （間に `margin` 画素以上を挟む）
4. **L 字型の `subject`**（外接矩形の右上が透明）では、外接矩形の内側の空きに
   かかる候補が返る。`opaque_rect` だけで計算した場合には返らない候補であることを
   テストで示す
5. 既存の文字の `placed` と交わる候補が無い。図形と `decoration` の画像の上には候補が出る
6. どの候補についても、中の全画素で障害物までの距離が `margin` を超える
   （原寸のマスクで総当たりして確かめる性質テスト）
7. `--profile note` では `min_size` の高さが 98、無ければ短辺の 8%
8. `--free-margin` を `--free-regions` 無しで渡すと exit 2。負の値も exit 2
9. 同じ入力から同じ結果（決定性。候補の並びも含む）
10. 1280 × 670 で `--free-regions` による増加が 10ms 以下（`--release`）
11. `cargo test`（`ci-test` プロファイル、feature 有無を直列で）、clippy（両系統、
    `-D warnings`）、fmt、MSRV 1.85 がすべて通る
12. 08-compose.md・`kiri schema`・Skill（「rect を書く前に `--free-regions` を引く」
    手順）・implementation-plan.md の索引を更新する

## 14.5 この段でやらないこと

- **候補の中へ自動で配置する。** 置くのは spec の仕事である（§10.9 のまま）
- 候補ごとの「入る文字の最大サイズ」。これは次の案（収まるサイズの助言）で
  文字の層ごとに返す
- 候補の下地の色やごちゃつき。背景の写真の上では空いていても読めないことがあるが、
  それは `TEXT_BACKGROUND_BUSY` の段で測る
- 矩形以外の空き（円・多角形）
- `--preview` に候補を重ねて描くこと

## 14.6 実装で決めたこと

1. **格子は `within` の左上から引き、右端と下端だけは `within` の端そのものを
   線にする**（最後のセルが 8px より狭くなる）。§14.2.3 の 3 の「`within` の外に
   はみ出すセルは埋まり扱い」のままだと、高さ 454 のように 8 の倍数でない `within`
   で条件 2（`within` そのものを返す）を満たせない。端数のセルも `within` の外の
   画素は含まないので、候補が `within` の外へ出ないことは変わらない。§14.2.1 の
   例の 132 = 108 + 24 とも合う原点である
2. **膨張は max フィルタではなく、横と縦に分けた累積で問う**（`Obstacles::free_cells`）。
   答えは正方形の近傍で膨らませたマスクと同じで、総当たりと突き合わせるテストが
   ある（`free_cells_match_a_brute_force_dilation`）。最初は原寸の 2 次元累積和
   （`u32`）と `bool` のマスクで持ったが、上限の 16384 x 16384 で 1GiB + 256MiB を
   要るので**レビューの指摘で改めた**。いまはマスクを 1 画素 1 ビット（32MiB）で
   持ち、行ごとに `w + 1` の累積を使い回して「列のセルを横に広げた範囲に当たりが
   あるか」を列のセル × 行の表（`bool`。2048 x 16384 = 32MiB）へ書き、列のセルごとに
   `h + 1` の縦の累積で縦に広げた範囲を問う。増える確保は上限で約 64MiB で、
   16384 x 16384 の実測ではピーク RSS が 3845MB → 3912MB（+67MB）、時間は +38ms だった
3. **70% は残した候補の和ではなく、どれか 1 つに入るかで見る。** 和で数えると、
   条件 3（中央の正方形で 4 本の帯）で下の帯が左右の帯の角 2 つで 72% 覆われて
   消えた
4. **層が 0 の spec は既存の検査が `SPEC_EMPTY` で断る。** 条件 2 は、障害物の無い
   単体テストと、図形と `decoration` の画像だけを置いた spec で確かめた
5. **`margin` は「チェビシェフ距離で margin を超える」で読む**——候補と障害物の
   画素の間に `margin` 画素以上が挟まる。条件 3 の「矩形同士が margin 以上離れる」
   と一致する読み方で、文書の「以上」は「超えて」に揃えた
6. **丸めの細部。**
   - `--free-margin` の端数は切り上げ、結果の `margin` は効いた整数（12.5 → 13）
   - `min_size` の高さは整数で切り上げる（note で 98、無ければ短辺の 8%。670 → 54）。
     「最も狭い表示」は profile の `displays` 全体の最小幅
   - `within` はキャンバスへ切り詰めて内向きに、文字の `placed` は外向きに整数へ
     丸める。どちらも 1/64px（`SUBPIXEL_TOLERANCE`）までの端数は見逃す——usvg の
     f32 の `189.99998` で 1 行上まで埋めない
   - 面積と `(y, x)` が同じなら幅の小さい順（同じ左上の縦長と横長の並びを列挙の
     順に依らせない）
7. **不透明度 1〜3 の Lanczos の裾も避ける。** 「不透明度が 0 でない画素」の文言
   どおりで、候補が商品に近づく向きには倒れない
8. **`--free-margin` の範囲外は clap の引数検査で断る**（exit 2、kiri の code は
   付かない。§14.3 の初稿が名指しした code は実在しなかった）。上限は
   キャンバスの辺の上限 16384 で、**それを超える値は断る**——どのキャンバスでも
   16384 より広い距離は 16384 と同じ答えになり、受け取れば効いた値を返すために
   切り詰めるしかない（レビューの指摘）。上限の内側では、キャンバスの辺より広い
   値も切り詰めずに空け、渡した値のまま返す（障害物が 1 つでもあれば候補は無く、
   無ければ `within` そのもの）
9. **動かしたい文字は spec から抜いて引く**（レビューの指摘。旗は足さない）。
   文字はどの role でも `placed` で避けるので、位置を決めたい文字の層を残したまま
   引くと、その文字自身が移動先を塞ぐ。`jq 'del(.layers[] | select(.id == "heading"))'`
   のように外した spec で引き、残した文字は障害物として扱われる。08-compose.md と
   Skill に書いた
10. **増える時間は 1280 x 670 で 1ms 前後**（`--release`）。本体（マスクの確保・
    押し込み・空き判定・列挙）だけを 50 回回して 1 回 0.6〜0.7ms、CLI の
    `elapsed_ms` の 30 回の合計の差で 1 回 0.5〜1.1ms だった（2 の改めの前後とも）。旗を渡さない実行は
    main と結果 JSON（`elapsed_ms` を除く）も出力とプレビューのバイト列も一致した

## 14.7 実写での検証（2026-10-18）

白い不織布の上の黒いリモコン（4284 × 5712）を `--optimize` で切り抜き、2 通りの
出力を作った。1 つは `--rotate -91.023` で縦に立てたもの（5788 × 4386）、もう 1 つは
`--rotate -1.023 --canvas 1400` で横に寝かせたもの。どちらも 1280 × 670 の
`[760, 40, 480, 590]` へ `subject` として置き、`--profile note --free-regions` で
候補を出した。

| 素材 | `opaque_rect` | 候補 |
|---|---|---|
| 縦 | `[904, 40, 192, 590]` | `[0, 108, 880, 454]` の 1 つ。右の空きは幅 160 で `min_size` の 196 に届かず落ちる |
| 横 | `[760, 257, 480, 156]` | `[0, 108, 736, 454]`、`[0, 108, 1280, 120]`、`[0, 444, 1280, 118]` |

縦の素材では 1 位の候補に 2 行・110px の見出しを置き、横の素材では 2 位（上の帯）に
1 行・100px の見出しを置いた。どちらも見出しには `LAYERS_OVERLAP` も
`OUTSIDE_SAFE_AREA` も出ず、`layer_overlap` は 0 だった（縦の spec で出た
`OUTSIDE_SAFE_AREA` は、`subject` の層を `safe_area` の外まで置いたことによるもの）。
目で見ても、margin の 24px が狭すぎるとは感じなかった。

同じ 2 つの spec で、`--free-regions` を渡さない実行を main のバイナリと比べた
（main を別の worktree でビルドした）。結果 JSON（`elapsed_ms` とパスを除く）、
出力、2 枚のプレビューのいずれも一致した。

## 14.8 決めたこと（§14.7 の旧版で「決めておくこと」とした 3 点）

1. **フラグ名は `--free-regions` にした。** spec の側に書かせる案（`"report":
   ["free_regions"]`）もあったが、何を測るかは実行ごとに変わるので CLI に置く
2. **文字は `placed` で数える**（§14.2.2）
3. **`margin` の既定は 24px（1280 幅）にした**
