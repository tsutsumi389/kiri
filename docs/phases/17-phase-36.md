# 17. Phase 36: 切り抜きのピーク RSS を下げる

節番号は分割前のまま変えていない。どの節がどのファイルにあるかは
[実装計画](../implementation-plan.md) の索引で引く。

[Phase 35](16-phase-35.md) は 24.5MP の実写 1 枚を 3.02 秒から 0.90 秒にしたが、
§16.8 に書いたとおり**ピーク RSS は 856 → 845MB のまま**だった。この段はその続きで、
時間はほぼ据え置いたまま RSS を半分以下にした。

**この段も出力のバイト列を 1 つも動かさない。** 受け入れ条件は §16.6 と同じで、
それに「real が基準から 5% 以上遅くならない」と「`--optimize`・`--segment`・
`batch` のピーク RSS を悪化させない」を足した（§17.5）。

## 17.1 測る道具（コミットには入れていない）

推測で手を入れないために、まず「どの時点で何が同時に生きているか」を数える
道具を作った。すべて一時的なもので、最後に取り除いてある。

- **数えるアロケータ。** `System` を包む `GlobalAlloc` で、生きている確保の和と
  その最大を数える。1MB 以上の確保だけはバックトレースを採って番地ごとに帳簿へ
  載せ、生きている量が最大を更新するたびに帳簿の写しを撮る。終了時に「最大の
  瞬間に生きていた大きな確保」を呼び出し元ごとに集計して出す。アロケータの中で
  バックトレースを採ると確保が起きるので、スレッドごとの再入の印で 2 度目を
  素通しにする
- **段の印での RSS。** `Stages::mark` に同じ印を差し、その時点の「生きている量」
  「最大」と、`proc_pid_rusage` で読む**いまの** RSS / phys footprint、
  `getrusage` の最大 RSS を並べて出す。`ps` のサンプリング（`rss.py`）は山を
  取りこぼすが、印の位置では取りこぼさない
- **止めて vmmap。** 指定した印で数秒止め、その間に `vmmap -summary` を当てて、
  RSS の中身を malloc の領域ごとに見る

| 背景の推定 | 94.6 | 201.3 | 365 |
| フィルの下ごしらえ | 237.5 | 237.5 | 511 |

### 読み取り

1. **生きている量の最大は 384MB しかないのに、RSS は 800MB を超える。**
   「フィル 2 回目」では生きている量が 118MB まで下がっているのに、RSS は
   613MB のまま一度も下がらない。差は**解放したのに返っていない**ものである
2. 書き出し前に止めて vmmap を当てると、`Malloc Large (empty)` が 34 領域・
   462MB 常駐していた。生きている大きな確保（`Malloc Large`）は 210MB。
   `malloc_zone_pressure_relief` を段ごとに呼んでも、返ったのは 0 バイトだった
3. 小さな試験で macOS の malloc の振る舞いを確かめた。98MB を取って捨てた後の
   50MB と 98MB は捨てた塊を使い回すが、140MB・23MB・4〜22MB の 19 本は使い
   回さずに新しく取り、捨てた塊はすべて常駐したまま残る。**大きさの近い確保が
   来たときだけ使い回し、そうでなければ積もる。** 切り抜きは段ごとに大きさの
   違う 3 桁 MB の作業域を取っては捨てるので、捨てた塊が積もるばかりになる
4. 生きている量が最大（383.7MB）になった瞬間、1MB 以上の確保は合わせて
   362MB 生きていた。内訳は元画像 93、refine が入口で取る出力の写し 93、refine の
   帯・印・塗り直しの写し 52、guided の作業域 54、マスク 3 本 70。残りの約 22MB は
   道具が呼び出し元を記録しない 1MB 未満の確保（帯ごとの作業域など）である

**最大の山は「生きている量」ではなく「返っていない量」である。** ここを
直さずに生きている量を削っても、捨てた塊が積もる限り RSS はほとんど動かない。

## 17.3 手と、1 手ごとの結果

上位から 1 手ずつ削り、1 手ごとに測り直した。RSS は remote tol60 の
`/usr/bin/time -l`、生きている量の最大は §17.1 の道具の値。

|---|---|---|---|---|
| 基準 | origin/main | 384 MB | 800〜805 MB | 440〜451 MB |
| 1 | 大きな確保を mmap で取り、捨てた塊は上限つきの棚に置く | 384 | 398〜417 | 243〜252 |
| 2 | refine の出力画像を、色を書く段の直前まで複製しない | 356 | 385〜401 | 235〜242 |
| 3 | refine が復元した色を帯の画素ぶんだけ溜め、出力は最後に作る | 348（書き出し） | 384〜387 | 228 |
| 4 | 伸びる大きな塊は、写像の尻へ足してその場で伸ばす | 320（フィル） | 358〜388 | 224〜232 |

3 の行の 348MB は書き出しの段（PNG の `Vec` の写し直し）、4 の行の 320MB は

レビューを受けて足した手と直しは §17.8 にある。

### 1. 大きな確保を mmap で取る（`src/large_alloc.rs`）

1MB 以上の確保をバイナリ側のアロケータで `mmap` へ回し、手放すときは `munmap`
で OS へ返す。**ライブラリには置かない**——どのアロケータで動かすかは組み込む
側が決めることで、`kiri` を使う他のプログラムに押し付けない。macOS に限る
（測ったのが macOS だけで、Linux の glibc は大きな確保をもともと `mmap` で
取って返す）。`libc` は `memmap2` と `rav1e` が既に引いているので、依存の木は
増えない。

境目は振って決めた（棚を持たない版、tol60 のピーク RSS）。

| 境目 | 16MB | 4MB | 1MB | 256KB | 64KB |
|---|---|---|---|---|---|
| ピーク RSS | 548 MB | 486 MB | 410 MB | 412 MB | 398 MB |

**何も取っておかないと遅い。** 毎回まっさらなページから始まるので、初めて
触るときの 0 埋めを払う。1 回の切り抜きで 1MB 以上の確保は合わせて 1.7GB
あり、real が tol60 で +5%、キーボードで +8%、`--optimize` で +6% になった
（段の表では境界の帯が 204 → 225ms）。受け入れ条件を割る。

そこで捨てた塊を棚（固定長 64 枠）に置いて使い回し、**生きている量と棚の和が、
これまでに生きていた量の最大を超えない**ように保つ。解放は和を変えない
（生きている側から棚へ移るだけ）ので常に棚へ置き、新しく写像を取るときに
和が最大を超えるぶんだけ古い順に返す。大きな塊の RSS は「同時に生きていた
量の最大」で頭打ちになり、その手前では malloc と同じく使い回しが効く。
棚の塊を `alloc_zeroed` へ回すときだけ 0 で埋め直す。real の差は +1〜3% に
収まった。

### 2・3. refine の出力の写し

refine は入口で元画像を丸ごと複製し（98MB）、(e) の作業域と (f) の走査の間ずっと
元画像と 2 枚で抱えていた。2 で複製を (f) の直前まで遅らせ、3 で (d)/(f) の走査が
画像へ書かずに帯ごとの `(添字, sRGB)` の列を返す形にした。帯・印・塗り直しの
写しを手放してから元画像を 1 度だけ複製し、列を書き込む（`paint`）。同じ画素を
2 度書くことは無い（1 つの段の中でタイルは重ならず、色を書く段は 1 回の
`refine` で 1 つしか走らない）ので、書く順序は結果に影響しない。

§11.11 の 1（書き換えた画素だけの重ね合わせ）を、`cutout_seen` の出口と
`apply_alpha` には触らずに refine の中だけで済ませた形である。

### 4. 伸びる塊をその場で伸ばす

3 の後、生きている量の最大は PNG の書き出しへ移った。1 のアロケータは伸ばす
たびに新しい写像へ写し直すので、PNG の `Vec` が 45MB から 91MB へ伸びる瞬間に
新旧 136MB を抱えていた。尻のすぐ後ろへ番地の希望つきで `mmap` し、そこに取れた
ときは写さずに伸ばす（既存の写像を潰す固定番地の指定は使わない。取れなければ
返して写し直す）。

## 17.4 結果

§17.8 の直しまで入れたバイナリで、5 回（segment は 2 回）を基準と交互に測った
平均。RSS は範囲。出力の PNG と結果 JSON（経過時間を除く）は、どの設定でも
基準と一致した。

| 素材と設定 | 基準 real | 基準 RSS | 結果 real | 結果 RSS |
|---|---|---|---|---|
| 実写リモコン `--tolerance 60` | 0.898 s | 799〜808 MB | 0.910 s（+1.3%） | **362〜390 MB** |
| 実写キーボード（既定） | 0.504 s | 440〜447 MB | 0.516 s（+2.4%） | **226〜229 MB** |
| 実写リモコン `--optimize` | 2.216 s | 856〜865 MB | 2.242 s（+1.2%） | **487〜497 MB** |
| `batch`（4 枚、既定の並列） | 1.752 s | 1631〜1795 MB | 1.762 s（+0.6%） | **948〜983 MB** |
| 実写リモコン `--segment isnet` | 2.23〜2.27 s | 1159〜1161 MB | 2.28 s | **525 MB** |
| 実写キーボード `--segment isnet` | 1.92 s | 1049〜1052 MB | 1.95〜1.96 s | **449〜454 MB** |

segment の初回だけは 2.81 秒かかった（モデルのファイルがページキャッシュに
載っていない 1 回目）ので、表から外した。

`batch` は remote tol60・キーボード既定・remote 既定・キーボードの bbox の 4 項目。
segment の 2 つの経路はどちらも `--features segment` の基準（origin/main を
同じ feature で建てたもの）と比べた。

依頼時の基準（ピーク RSS 837〜843MB）とこの段の基準（800〜805MB）が食い違うのは、
同じバイナリでも機械の状態で変わるためである（§17.6 の 6）。比べるのは同じ
時間帯に交互に測ったものどうしにした。

## 17.5 受け入れ条件

1. `check.sh` の 10 設定の PNG の md5 が基準と一致し、結果 JSON も経過時間を
   除いて一致する。加えて `check.sh` が通らない経路（`--no-despill`、
   `--matting projection`（`--no-despill` の有無）、`closed-form --no-despill`、
   3 段を切った経路、`--no-refine`、`--seal 6`、`--edge-repair auto`、
   `--preview`、`--canvas`、`--shadow synth`）をキーボードで回し、基準と一致した
2. real が基準から 5% 以上遅くならない（remote tol60、キーボード既定、
   remote `--optimize`）
3. `--optimize`・`--segment`（feature あり）・`batch` のピーク RSS を悪化させない
4. `cargo test --release` と `cargo test --release --features segment` を直列で
   全緑、`cargo clippy --all-targets`（feature の有無）と `cargo fmt --check` が通る

アロケータの単体試験は 14 本ある（§17.8 の M3）。macOS でしか建たないので、
CI に macOS のジョブを足してアロケータの試験と clippy を回す（§17.8 の M1）。

## 17.6 踏んだ罠

1. **RSS は生きている量ではない。** macOS の malloc は捨てた大きな塊を常駐させた
   まま抱え、`malloc_zone_pressure_relief` でも返さない。§16.5 の表（段ごとの
   最大 RSS）は「積もった量」を読んでいたので、どの段で何を削っても山が
   動かないように見えた。**生きている量と RSS を同じ印で並べる**まで、
   削るべき相手が分からなかった
2. **返すだけでは遅くなる。** `munmap` で返すと、次の確保は 0 埋めのページ
   フォールトから始まる。sys 時間が 0.13 秒ほど増え、受け入れ条件（5%）を
   割った。返す量に上限（生きていた量の最大）を付けた棚で両立させた
3. **写し直す realloc は新しい山を作る。** 棚の版でも、伸びる `Vec` は新旧を
   一瞬 2 本抱える。refine の山を削った直後、PNG の書き出しの 136MB が全体の
   ピークとして顔を出した
4. **ピークは最大値である。** 2 は生きている量を 23MB しか下げなかった
   （出力の写しが (f) の走査と重なったまま）。3 で refine の山が消えると、
   次は書き出し、その次はフィルが顔を出した。1 手ごとに測り直さないと、
   効いた手と効かなかった手の区別がつかない
5. **生きている量を削っても RSS が下がるとは限らない。** 4 の後に、書き出しの前に
   元画像（98MB）を手放す手を試した。書き出しの段の生きている量は 93MB 下がったが、
   実行全体の最大はすでにフィルの 320MB にあり、ピーク RSS は 362MB のまま
   動かなかった。フィルと境界の帯では、1MB 未満の確保（帯ごとの作業域など、
   malloc の小さな領域）と棚の和が効いている。効かなかったのでコミットしていない
6. **機械の状態で基準が動く。** 依頼時に 837〜843MB だった基準のピーク RSS が、
   この段では 800〜805MB だった。測っている最中に別のビルドを走らせると時間も
   RSS も揺れる（segment の基準を建てている間の測りは捨てた）
7. **計測用のアロケータが自分を呼ぶ。** 境目を環境変数から読む版は、変数を
   読むときの確保がアロケータへ戻って無限に再帰し、起動直後に落ちた。読む前に
   「読み中」の値を置いて、その間は既定へ回す
8. **`drop` の付け外しは clippy が見る。** 参照しか持たない構造体を `drop` すると
   `drop_non_drop` で落ちる。借用は最後の使用で切れるので、書く必要が無い
9. **文書に定数の綴りを書くと、code の検査が実在しない code として落とす。**
   §16.7 の 5 と同じ罠で、`mmap` の旗の名前は libc の定数で kiri の中に無い。
   名前ではなく何をする旗かで書いた

### 試して捨てたもの

- **`malloc_zone_pressure_relief` を段ごとに呼ぶ。** 1 バイトも返らない
- **棚を持たずに毎回返す。** §17.6 の 2
- **境目を 64KB まで下げる。** 13MB しか下がらず、`mmap` の回数が増える
- **書き出しの前に元画像を手放す。** §17.6 の 5

## 17.7 残っている山

結果のバイナリで、生きている量の最大はフィルの 2 回目（320MB）にある。

| 段 | 生きている量 | 中身 |
|---|---|---|
| フィル 2 回目 | 320 MB | Lab の表 140、元画像 93、マスク 3 本 70 |
| 境界の帯（(f) の走査） | 約 260 MB | 元画像 93、マスク 3 本（入力・塗り直しの写し・guided の出力）70、帯と印 29、帯ごとの作業域 53、それに 1MB 未満の確保 |
| 書き出し | 約 300 MB | 元画像 93、出力 93、マスク 23、PNG の `Vec` 91 |

次にやるなら次の順になる。

1. **Lab の表（140MB）。** 2 回のフィルで使い回す下ごしらえ（§11.8）で、
   画素あたり 6 バイトある。持ち方を変えると堤防とフィルの判定が 1 ビットでも
   動きうるので、出力を動かさない段の範囲では手を付けなかった
2. **書き出しの元画像。** preview を書かない実行では書き出しの前に手放せる
   （§17.6 の 5）。フィルと帯の山を削った後なら効く
3. **`--optimize` の最終段。** 2 つ目の候補を原寸で回す間、1 つ目の結果
   （画像 93 + マスク 23）を「いまの最良」として抱えている（生きている量の
   最大 437MB）。抱えずに勝った候補を回し直すと時間が増える
4. **1MB 未満の確保。** 帯ごとの作業域などは malloc の小さな領域に残る。
   境目を下げても §17.3 の表のとおり大きくは効かない

## 17.8 レビューの指摘への対応（2026-11-01）

独立したレビュー（CRITICAL / HIGH は 0 件）から受けた指摘を直した。

### M1: アロケータが CI で 1 度も回らない

CI のジョブはすべて ubuntu で、macOS でしか建たないアロケータは試験も clippy も
通っていなかった。macOS の標準ランナーでアロケータの単体試験と
`clippy --all-targets -D warnings` を回すジョブを足した。プロファイルは他のジョブと
同じ `ci-test` で、debug-assertions が残るので `munmap` の戻り値の表明（L1）も効く。

### M2: 失敗した写像で棚の上限が膨らむ

`reserve` が `mmap` の前に最大を上げ、失敗したときは `live` しか戻していなかった。
`try_reserve` の巨大な確保が失敗すると最大が恒久的に膨らみ、棚の頭打ちが外れる。
最大は写像が取れてから上げる形に直した。

**直した版にも穴があった。** 待っている確保を `live` に混ぜたままにしたので、待つ
間に別のスレッドが解放すると `live` が減って上限が縮み、取れた後に縮んだ `live` で
最大を上げることになる。M3 の並行の負荷試験で、不変条件が破れて見つかった。
待っている確保は `pending` として別に数え、

```text
live + pending + cached <= max(high, live + pending)
```

を保つ。取れたら `pending` から `live` へ移して最大を上げ、取れなければ `pending`
から消す。解放は、棚へ置くと上限を超えるときは置かずに返す。

### M3: 単体試験が肝を捉えていない

- 「同じページの内で縮める」はずの試験が実際にはページをまたいでおり、何もしない
  枝を通っていなかった。組がそれぞれの枝に当たることを `round_up` で表明して分けた
- `extend` の成否が運任せだった。尻が自分の写像で埋まっているときに断る（写像は
  壊さない）ことと、空けた尻へその場で伸ばせることを別々に試す
- 0 埋めの使い回しの試験は、並行の別試験に棚を取られると使い回しが起きずに
  素通りで緑になっていた。使い回しが起きたことを確かめるまで繰り返す
- `Pool` を偽の番地で直接回し、best-fit と尻の切り出し、満杯の棚、古い順の
  追い出し、失敗した予約の後始末、待つ間の解放を決定的に確かめる
- 16 スレッドで確保・0 埋め・伸び縮み・解放を混ぜ、中身で照らす負荷試験
  （0.3 秒ほど）。手元で 40 回続けて回して落ちないことを確かめた

### M4: 色の列が画像の複製より大きくなりうる

`(u32, [u8; 3])` は詰め物込みで 1 画素 8 バイトあり、`Vec` の伸び代で最大 2 倍に
なる。実写では帯は画素数の 2.5〜3.6% だが、四角い斑点を敷き詰めた合成画像
（5000x4000、斑点 30〜60px）では 70〜93% に達し、列（容量 1630 万件・130MB）が
画像の複製（80MB）を超えた。

| 案 | 合成画像（斑点 30px）での列 | 実写 |
|---|---|---|
| そのまま（8 バイト） | 130 MB | 5〜8 MB |
| 添字と色を別の `Vec`（7 バイト） | 114 MB（伸び代込み） | 5〜7 MB |
| 帯が 1/4 を超えたら直接書く | 0（複製 80MB へ直接） | 5〜8 MB |

7 バイトにしても伸び代込みで複製を超えるので、帯の画素数を数えて 1/4 を超えたら
色を書く段の直前に複製してそこへ直接書く（2 の形）ことにした。1/4 以下なら伸び代
込みでも列は複製を超えない。合成画像（斑点 30px）のピーク RSS は 406MB → 390MB
（列にする前の 2 の版は 397MB、基準は 564MB）。実写は列の経路のままで変わらない。
2 つの書き方が同じバイト列を出すことは、書き方を決め打ちできる入口で guided /
projection / closed-form と despill の有無の 6 通りを比べて確かめる。
